* System Architecture

** Core Philosophy

Ever is a single-binary event storage system. One store process, many client processes, no external dependencies. Events are immutable, topics are logical, and the shared log is the source of truth.

** Design Principles

*** Single Shared Log
- All events from all topics write sequentially to one log file
- Topics are an in-memory index over the shared log, not separate files
- Each event record includes its topic name (2-byte topic_len header field)
- Segment rotation at configurable size (default 64MB)
- In-memory position index rebuilt from log on startup — O(1) reads

*** One Store, Many Clients
- One =ever store start= process owns the data directory
- Any number of =ever pub/sub/on/wait/hook/topic= clients connect via TCP
- Lockfile (=ever.lock= with =flock=) prevents multiple stores on same data dir
- =reuse_address=false= prevents multiple stores on same port

*** Thread Safety
- =TopicManager= mutex serializes all topic/publish/fetch operations
- =Log= mutex serializes appends (nested under TopicManager mutex)
- =HookTable= mutex serializes hook registration/removal
- Server tracks =active_connections= with atomic counter
- Hook and timer daemons are separate threads sharing =TopicManager=

*** Event-Driven Automation
- *Hooks*: =ever hook add <pattern> -- <cmd>= — persistent server-side triggers
- *Triggers*: =ever on <pattern> -- <cmd>= — ephemeral client-side triggers
- *Timers* (planned): =ever timer add --every 5m <topic> <payload>= — scheduled publishing
- Separation: timers are "when", hooks are "what", events are the glue

** Storage Layout

#+begin_src
data/
├── 00000000000000000000.log   # Shared log segment 0
├── 00000000000000065536.log   # Segment 1 (after rotation)
├── hooks.json                 # Persistent hook registrations
├── timers.json                # Persistent timer schedules (planned)
└── ever.lock                  # flock-based lockfile
#+end_src

No per-topic directories. All events interleaved in the shared log.

** Event Record Format

#+begin_src
┌──────────┬───────────┬───────────┬──────────┬──────────┬─────────────────────┐
│ offset   │ timestamp │ topic_len │ key_len  │ val_len  │ topic | key | value │
│ u64 LE   │ i64 LE    │ u16 LE    │ u32 LE   │ u32 LE   │ variable bytes      │
└──────────┴───────────┴───────────┴──────────┴──────────┴─────────────────────┘
#+end_src

Header: 26 bytes. Topic name embedded in every record (max 255 bytes). Key is optional (key_len=0). Value is the user's JSON payload. Empty value (val_len=0) indicates a topic creation marker — filtered from user-facing fetch results.

** Wire Protocol

#+begin_src
┌───────────┬──────────┬──────────┬──────────────────┐
│ version   │ msg_type │ body_len │ body             │
│ u8 (=1)   │ u8       │ u32 LE   │ JSON bytes       │
└───────────┴──────────┴──────────┴──────────────────┘
#+end_src

6-byte frame header. Bodies are JSON. Message types:

| Range     | Purpose        | Types                                                |
|-----------+----------------+------------------------------------------------------|
| 0x01-0x05 | Core requests  | publish, fetch, create/delete/list topics            |
| 0x06      | Retired        | was =ack=; never implemented, must not be reused     |
| 0x07-0x09 | Hook requests  | register/unregister/list hooks                       |
| 0x0A-0x0D | Timer requests | add/remove/list/info timers                          |
| 0x0E-0x10 | Inspection     | hook ps, hook logs, status                           |
| 0x81-0x90 | OK responses   | Mirrors of requests (0x86 retired with 0x06)         |
| 0xFF      | Error          | Code + message                                       |
| any other | Unassigned     | =400 unknown request type=; the connection stays open |

=MessageType= is *non-exhaustive* (=_=) and this is load-bearing, not stylistic. =readFrame= converts the opcode byte with =@enumFromInt= straight off the wire; on an exhaustive enum every unassigned byte is illegal behaviour, i.e. a panic on the connection thread, i.e. the whole store process — listener, hook daemon and timer daemon — gone on one six-byte frame from anything that can reach the port. Non-exhaustive makes the decode total, so unassigned opcodes reach the server's =else= arm and are answered instead of being fatal. See =air/v0.1/protocol-unknown-opcode.org=.

Fetch supports =block_ms= for blocking long-poll (server delays response until events arrive or timeout).

** Durability: what fsync costs, measured

=Log.append= calls =file.sync()= per record when =sync_on_append= is set, and it is set: =ever start= constructs the store with =.{}=, the default is =true=, and *there is no CLI flag, environment variable or config file that changes it* — the only places in the tree that set it false are tests. A decision to run without sync cannot currently be enacted.

Measured on this hardware (ZFS, both the dataset the live store uses and =/tmp=, 5,000-20,000 appends each way, repeated):

| Mode                        | Throughput           | Avg per append | p99      |
|-----------------------------+----------------------+----------------+----------|
| =sync_on_append = false=    | 287,000-386,000 /sec | 2.6-3.5 us     | 5-7 us   |
| =sync_on_append = true=     | 1,950-2,430 /sec     | 411-512 us     | 496-617 us |

So durability costs about *0.41 ms per append* and a *130-160x* throughput reduction. Reproduce with =zig build bench -- --filter log_append=; the benchmark predates this note.

*The decision is that durability stays on* (owner, 2026-08-09, on the strength of these numbers). The ceiling is therefore something to raise, not to trade away. Four things follow, three of them defects:

- *The ceiling is store-wide, not per-client.* =Log.append= holds =Log.mutex= across the fsync, so publishers serialise behind each other's disk sync. Measured: 1 publisher 2,340/sec, 8 publishers 2,409/sec *between them*. Adding publishers adds nothing.
- *There is no group commit, and that is the whole gap.* One sync covering a batch is measured at 31,700 appends/sec for a batch of 16 and 203,000 for 1024, against 2,389 for a batch of 1 — and under concurrency the batch forms from publishers already waiting, so it costs no added latency. The apparent durability-versus-throughput choice is an artefact of this missing feature. Owned by =v0.1/log-group-commit.org=.
- *A failed sync is silent.* =seg.file.sync(self.io) catch {}= — the append still returns its offset and reports success, five lines after the *write* failure is correctly propagated. Owned by =v0.1/sync-failure-reporting.org=.
- *The directory entry is never synced, and this one has no owner.* =createSegment= creates a =.log= file and nothing ever fsyncs the containing directory — =file.sync= appears exactly once in the tree, on the record path. On a filesystem that does not journal the create alongside the data (ext4 =data=ordered=, xfs), a power cut can lose a newly created segment *and every record fsynced into it*. ZFS, which is what this machine runs, logs the create in the same intent-log stream and is very likely safe — which is the problem: *the guarantee currently depends on a filesystem property Ever does not state, does not check, and cannot rely on elsewhere*. Recorded here rather than specced; it needs a decision before Ever claims durability on arbitrary storage.

Historical note, because a decision was once made on a wrong number: publish latency was for a time believed to be ~42 ms and attributed to fsync. It was the TCP delayed-ACK stall from writing a frame in two syscalls (=protocol-frame-single-write.org=). The same publish now round-trips in 0.62 ms with sync unchanged. *Re-measure before believing any claim in this project that blames publish latency on the disk.*

** Recovery Model

On startup, =ever store start=:
1. Acquire =ever.lock= (fail if another store running)
2. Scan =*.log= segment files, build position index
3. Replay log to rebuild topic index (=rebuildIndex=)
   - Topics discovered from event records (including empty-value markers from =createTopic=)
4. Load =hooks.json= → start hook daemon
5. Load =timers.json= → start timer daemon (planned)
6. Start TCP listener

Everything reconstructs from the log + JSON config files. No separate database.

** Subscription Model

Three patterns, common cases need no shell quoting:

| Input           | Mode    | Matches                             |
|-----------------+---------+-------------------------------------|
| =agent.tasks=   | Exact   | Only =agent.tasks=                  |
| =agent.=        | Prefix  | =agent.tasks=, =agent.build=, etc.  |
| =.=             | All     | Every topic                         |
| =agent.*.done=  | Pattern | =agent.build.done=, =agent.X.done=  |

Trailing dot is shell-safe (no quoting needed). The =*= wildcard matches exactly one segment.

*** Delivery is notified, not polled

A blocking fetch (=block_ms > 0=) parks on a condition variable and is woken by the append. It does not sleep on a timer, and an idle subscriber costs no CPU and no wakeups.

The wait predicate is =TopicManager.append_epoch=, bumped inside the same critical section that updates the topic index. *The condition variable is only the notification; the epoch is the state.* A reader takes the epoch before it looks for events, so an append landing between the look and the wait leaves the epoch already moved and the wait returns without parking — that is what makes a wakeup impossible to lose, and reading the epoch after the look instead of before is the one way to break it.

A wake means "look again", never "here is your event": the first version broadcasts to every waiter on any append, so spurious wakes, wakes for another topic and events taken by another reader all resolve by re-reading. Per-topic wait queues are a deliberate later refinement.

Shutdown must call =wakeAllWaiters=. Parking is the one property that replacing a poll with a wait takes away — a poller noticed the shutdown flag within its tick — so it has to be given back explicitly or every subscriber waits out its full =block_ms=.

** Concurrency Model

- TCP server: thread-per-connection (detached). This is why no event loop is needed for notification: the thread that would sleep can wait on anything it likes.
- TopicManager: single blocking mutex (=std.Io.Mutex=) guards all operations, plus a condition variable for append notification
- Log: nested mutex (redundant under TopicManager mutex, but safe)
- Hook daemon: separate thread, polls TopicManager
- Timer daemon: separate thread, publishes to TopicManager (planned)
- Client commands: single-threaded, one TCP connection

*** Mutex Scope for I/O
Copy index data under the lock, release it, then do disk I/O without the lock. =Log.append= has its own mutex, so =TopicManager= doesn't need to hold its mutex during writes. This reduces lock contention on I/O-bound operations.

*** Signal Handling
Only async-signal-safe operations in signal handlers. To unblock a blocking =accept()= call on shutdown, use a dummy self-connection (socket+connect+close) — raw syscalls are signal-safe. Never call =deinit()= or manipulate complex structs in a signal handler.

Known limitation: detached threads not joined on shutdown (=graceful-shutdown.org= spec exists).

** Key Learnings

*** Shared log > per-topic files
Originally each topic had its own directory with segment files. Cross-topic queries (=ever sub agent.=) required N separate readBatch calls. The shared log eliminated this — all reads are sequential from one file, and the OS page cache works optimally since recent events from all topics are physically adjacent.

*** Topic creation must be durable
Topics created with =createTopic= but never published to would vanish on restart because =rebuildIndex= only discovers topics from event records. Fix: =createTopic= writes a marker event (empty value) to the log.

*** freeEvent contract
=Log.read/readBatch= returns events where topic+key+value are a single contiguous allocation. Always use =store.freeEvent()= to free — never free individual fields. This reduces allocator pressure from 3 allocs per read to 1.

*** Blocking fetch over polling
=ever on= and =ever sub --follow= use =block_ms= in =FetchRequest=. The server holds the connection (poll+sleep loop) until events arrive or timeout. This eliminates idle CPU from client-side polling loops.

*** Hook background execution
Hooks execute via fork/exec in a background daemon thread. Each hook invocation gets event data via environment variables and stdin (temp file). PID-based temp file paths (=/tmp/.ever-hook-stdin-{pid}=) avoid collisions. The hook daemon thread shares =TopicManager= with the server — snapshot hook state under the =HookTable= mutex before executing.

*** Double mutex is acceptable
=TopicManager.publish= holds its mutex, then calls =Log.append= which acquires the Log mutex. This is redundant but not a bug — the Log mutex ensures correctness if Log is ever used without TopicManager. The overhead is one extra spinlock acquisition per write (~nanoseconds).

** Performance Profile (ReleaseFast, single node)

| Operation        | Throughput     | Avg latency |
|------------------+----------------+-------------|
| Log append       | ~340k ops/sec  | ~3µs        |
| Log read         | ~450k ops/sec  | ~2µs        |
| Batch read (100) | ~460k evts/sec | ~220µs      |
| Topic publish    | ~340k ops/sec  | ~3µs        |

Bottleneck is syscall overhead (pwrite/pread), not CPU. fsync-on-append drops to ~1.8k ops/sec (disk-bound).
