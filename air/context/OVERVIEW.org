* Project Overview

** Description
Ever is a lightweight, high-performance event storage system written in Zig. Inspired by systems like NATS and Kafka, Ever provides at-least-once delivery semantics for event-driven architectures. It is designed as a single-node storage interface — not a distributed cluster — where events (agent task completions, file edits, process exits, etc.) can be easily tracked, reported, and subscribed to by interested consumers.

** Core Principles
- *Performance First*: Zig's zero-overhead abstractions, explicit memory management, and no hidden allocations make it ideal for high-throughput event processing
- *Simplicity Over Distribution*: Single-node focus — no distributed consensus, no replication overhead. Clean, fast, reliable
- *At-Least-Once Semantics*: Kafka-like delivery guarantees without Kafka-like complexity
- *Planning-First Methodology*: Air documents serve as single source of truth for specifications
- *Composable Processes*: Distinct roles (store, publisher, subscriber, orchestrator, transformer) communicate via well-defined protocols

** Technology Stack
- *Language*: Zig 0.17 development line. The exact snapshot the project is verified against is pinned in =nix/zig.nix= (currently =0.17.0-dev.607+456b2ec07=) and declared as =minimum_zig_version= in =build.zig.zon=. Zig 0.16.0 is retired — the source uses std APIs it lacks — but the toolchain path remains reachable via =channel = "0.16.0"= so behaviour can be compared against a tagged release when the dev line shifts.
- *Build System*: Zig build system (=build.zig=)
- *Dependencies*: Minimal — prefer Zig standard library
- *Testing*: Zig's built-in testing framework
- *Development Environment*: Nix flake for reproducible builds
- *Data Format*: JSON initially, with path to more efficient binary encoding

** Architecture
Ever is built around an append-only log as the core storage primitive. Events are organized into topics, each backed by segmented log files. Processes communicate over a simple binary or JSON-based protocol via TCP or Unix domain sockets.

*** Core Components

**** Store
The storage engine manages append-only logs, segment rotation, and offset tracking. It is the single source of truth for event data.

**** Publisher
Sends events to the store. Can be a library call or a separate process. Supports batching for throughput.

**** Subscriber
Reads events from the store, tracking consumer offsets for at-least-once delivery. Supports both pull-based polling and push-based streaming.

**** Orchestrator
Manages lifecycle of store, publisher, and subscriber processes. Handles configuration, health checks, and graceful shutdown.

**** Transformer
A combined publisher + subscriber that consumes events from one topic, applies a transformation, and publishes results to another topic. Useful for event pipelines.

** Downstream Consumers

Ever is embedded by other projects. They pin a revision rather than tracking main, so any claim
about "current behaviour" — theirs or ours — must be checked against the revision actually
held, not against main. A defect reported from a pinned tree may already be fixed; a workaround
built there may already be unnecessary.

*** Announcing changes

Anything landing in Ever that changes behaviour a consumer depends on gets published to topic
=ever.landed= at the time it happens: what changed, the commit, one line on the consequence. Do not
ask permission and do not gate their work on it; the failure this addresses is *discovery*, not
authority. Include what has already been verified so they do not repeat it, and what has not, so
they know what is still open.

*** Publishing is not delivering

Which channel is used decides whether anyone acts, and choosing wrong looks like success from the
sending side:

- =ever.landed= is an announcement channel. A consumer hooking it typically routes it as a *meta*
  message — read, but it does not start a turn. An idle recipient sees it whenever something else
  wakes them. Right for "this changed"; wrong for "should we do X".
- Topics shaped =*.done= / =*.failed=, and payloads saying =blocked= / =failed= / =needs-input=,
  arrive as a turn.
- Direct =pi-crosstalk send --kind user= is the channel for anything that needs an answer. =--from=
  must be namespaced (=@ever:landed=); a bare handle is rejected as an unknown sender.

A message on an unhooked topic, or one that arrives without waking anyone, is indistinguishable from
no message at all.

*** Evaluating proposals from a consumer

Recorded in =architecture.org= and repeated because it is easy to skip: check the claim against
current =main= first, since they pin. Then check what the argument rests on — a performance
argument built on someone else's unfixed defect points at whichever design lacks that defect, not at
the better design. Only then judge it against the scope rule.

When declining, say what would change the answer. When accepting, say what you did not verify.

*** External verification is worth asking for

Our toolchain is pinned to a Zig dev build whose tarball 404s, so we cannot easily test against
another. A consumer building at a *different* toolchain is therefore the only external check
available, and the standing arrangement is mutual: build, read, and measure against each other's
trees and report verbatim, failures included — especially unpredicted ones. Ask for it on any
change where a single compiler is worth little, which means anything concurrent. Say explicitly what
you have already covered, so their run tests something yours did not.
