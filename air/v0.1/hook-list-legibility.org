#+title: Hook List Legibility: Pending and Fired Columns
#+state: ready
#+FILETAGS: :cli:subscriber:orchestrator:

* Summary
=ever hook list= shows a =Last Offset= column that prints the hook's raw cursor — a value whose meaning depends on pattern shape (topic-local skip count for exact topics, global log offset for prefix/wildcard patterns, per =v0.1/hook-registration-cursor.org=). Two hooks armed in the same second with zero firings each can show =4= and =164= in the same column, and both read as "already fired N times". This doc replaces the raw cursor in the human table with two derived, uniform columns — =Pending= (matching events not yet processed) and =Fired= (lifetime execution count, consuming the persisted =fired_count= counter defined by =v0.1/hook-failure-visibility.org=) — moves the overflow-prone =Command= column last so the table stays positionally parseable, and keeps raw cursors available in =hook list --json= as =cursor= + =cursor_kind=.

* Motivation
From the ever field report (=docs/ever.org=, Incident 2 "=Last Offset= dual semantics", verified at =142d5e6=). Two hooks registered in the same second, /zero/ firings each (columns compressed for layout; the binary renders wider NAME/Pattern columns):

#+begin_example
ID   NAME             Pattern                Command                  Last Offset
#47  wutest-wever-h1  wutest.wever.subtest   sh -c cat >> /tmp/a.log  4
#48  wutest-wever-h2  wutest.wever.          sh -c cat >> /tmp/b.log  164
#+end_example

An operator triaging lost notifications reads "Last Offset 4" on a freshly armed hook as "this hook already processed 4 events". During the report's Incident-1 CLI blackout this column was one of the two fallback read paths ("has the done event arrived past the cursor?") — precisely the moment misreading it is most expensive. Two hooks armed at the same instant differing by a factor of 40 in the same column make it uninterpretable without the manual open. The round-1 review independently reproduced both claims (exact-topic hook fresh over 3 prior events showed =3=; a same-second prefix hook showed =296=).

Code facts, verified in this workspace:
- =handleHookList= (=src/main.zig= line 445) renders =Last Offset= as the raw =hook.cursor= with format ={s:<4} {s:<20} {s:<25} {s:<30} {s:<12}= (line 460). Zig's =<30= pads but never truncates, so a command longer than 30 characters shifts =Last Offset= out of alignment — the table cannot be parsed positionally (also observed live in the report and round-1 review with a 37-char command).
- The cursor's polymorphic interpretation is by design (=src/store/hooks.zig= =Hook.cursor= doc comment; =v0.1/hook-registration-cursor.org= B1 decision): exact → topic-local skip count consumed by =TopicManager.fetch=; prefix/wildcard → global log offset consumed by =fetchPatternByOffset=. The design is sound; the problem is purely presentational.
- Hooks track no execution count. Timers do: =fire_count= is persisted per timer (=src/store/timers.zig=, =TimerInfoData.fire_count=, incremented on fire at line 419) and displayed as the =FIRES= column (=src/main.zig= line 712). The precedent for "lifetime count as the headline number" already exists in the same binary.

** Goals
- The human =hook list= table shows only values with a single, uniform meaning across all hooks: =Pending= and =Fired=.
- A freshly armed hook reads =Pending: 0, Fired: 0= at a glance, regardless of pattern shape.
- The table stays column-aligned for arbitrarily long commands.
- Raw cursors remain available for debugging in =hook list --json= as =cursor= + =cursor_kind=.
- The =Fired= column consumes the =fired_count= counter defined by =v0.1/hook-failure-visibility.org= (P7) — one data design, owned there; this doc owns the presentation.

** Non-Goals
- Changing cursor semantics or the hook daemon's delivery behaviour (=v0.1/hook-registration-cursor.org= stands).
- The execution-counter data model — field definitions, increment points, persistence, compatibility — is owned by =v0.1/hook-failure-visibility.org= (P7): "this doc owns the data; P4 owns the presentation". This doc only consumes =fired_count= and specs how the table renders it.
- Re-specifying =hook list --json= — owned by =v0.1/cli-json-list-output.org= (in-flight draft, uncommitted at time of writing); this doc proposes additions to that schema by reference only.
- The output-stream fix (=v0.1/stdout-stderr-split.org=, P1) — table rendering rides on it.

* Proposal

** Human table
Replace =Last Offset= with two derived columns and move =Command= last:

#+begin_example
ID   NAME                 Pattern                   Pending   Fired     Command
#47  wutest-wever-h1      wutest.wever.subtest      0         0         sh -c cat >> /tmp/a.log
#48  wutest-wever-h2      wutest.wever.             0         0         sh -c cat >> /tmp/b.log
#+end_example

- =Pending= — number of events matching the pattern that the hook has not yet processed. Uniform meaning for both cursor kinds (computation below).
- =Fired= — lifetime number of events delivered to the hook, rendering the =fired_count= counter from =v0.1/hook-failure-visibility.org= (P7). Mirrors the timers' =FIRES= precedent.
- Column-overflow fix (explicit decision): =Command= — the only unbounded-width field — moves to the /last/ position and is printed un-padded, the classic =ps= layout. All preceding columns keep fixed widths, so the table is positionally parseable no matter how long the command is. No truncation.

** =Pending= computation (server-side, at =list_hooks= time)
The server handler (=src/net/server.zig handleListHooks=) has both the =HookTable= and the =TopicManager=; it computes =Pending= per hook by cursor kind (the same pattern-shape dispatch =processHook= in =src/store/hooks.zig= uses):
- /Exact topic/ (cursor = topic-local skip count): =pending = saturating_sub(topic.non_marker_count, cursor)= from the topic index (=src/store/topic.zig=); =0= if the topic does not exist yet.
- /Prefix or wildcard/ (cursor = global log offset): count of non-marker events with =offset >= cursor= whose topic matches the pattern. Implemented as a count-only variant of =fetchPatternByOffset= (same scan-from-cursor loop: skip markers, =matchTopic=, tally instead of allocating event bodies). To bound the scan on a hook that is far behind a large log, the count caps at 1000 and renders as =1000+=. (The per-topic offset lists alone cannot answer this — they include marker offsets — so the log scan is the honest computation.)
=Pending= is a point-in-time snapshot racing live publishes; that is fine for a status display and worth a one-line note in the column legend.

** =Fired= column (counter owned by P7)
The field definition, increment point, and persistence of =fired_count= are OWNED by =v0.1/hook-failure-visibility.org= (P7) and are not re-specified here — see its "New fields" table and "Update points". One-line semantics summary for readers of this doc: =fired_count= counts /execution attempts/, i.e. every delivered event that advanced the cursor, including spawn failures and nonzero exits (only =ConcurrentLimitReached= leaves cursor and counter untouched) — P7 subdivides it with =failure_count= and friends.

What this doc adds on top: the =Fired= human-table column renders =fired_count= (and, once P7's =failure_count= is nonzero, P7's =12 (2 failed)= annotation style applies in this table unchanged). Implementation dependency, stated honestly: the =Fired= column depends on P7's counters landing — if this doc is implemented first, the column renders =0= for all hooks until P7 ships.

** Wire and JSON
- =HookInfo= (=src/protocol/message.zig=) gains additive fields from this doc: =pending: u64= and =cursor_kind: []const u8= (="topic_local"= | ="global"=). Existing =cursor= stays. =fired_count= (and the other counter fields) are added to =HookInfo= by =v0.1/hook-failure-visibility.org=, not here.
- =hook list --json=: =v0.1/cli-json-list-output.org= (in-flight draft, uncommitted at time of writing) specs the hook object with a bare =cursor= field. Proposed additions to that schema, by reference: =cursor_kind= and =pending= from this doc; =fired_count= per P7. Rationale for =cursor_kind=: a bare =cursor= number reproduces the dual-semantics trap in machine-readable form; the kind tag makes it self-describing.

* Design Details
- =src/store/hooks.zig= — no changes owned by this doc; the =fired_count= field, its increment in =processHook=, and =hooks.json= persistence are specced in =v0.1/hook-failure-visibility.org=. This doc only requires the counter be exposed in the table snapshot used by =list_hooks=.
- =src/store/topic.zig= — =countPatternByOffset= (count-only sibling of =fetchPatternByOffset=, with cap parameter); exact-topic pending needs no new code (=non_marker_count= is public state).
- =src/net/server.zig handleListHooks= — populate =pending= / =fired_count= / =cursor_kind= per hook under the manager lock (=fired_count= copied from the P7-owned counter).
- =src/net/client.zig= — carry the new fields through =HookInfoOwned=.
- =src/main.zig handleHookList= — new header/row rendering: fixed-width =ID NAME Pattern Pending Fired=, then un-padded =Command= last. =1000+= rendering for the capped count.
- Tests (presentation-side only; counter persistence/increment tests live in P7): unit — count-only pattern scan (markers excluded, cap honoured); integration — fresh exact + prefix hooks both list =Pending 0 / Fired 0=; publish N matching events, wait for the daemon, assert =Fired: N= and =Pending: 0= (consumes =fired_count=); publish while daemon is stopped, assert =Pending= grows identically for both hook kinds; register a hook with a 60-char command and assert header/row column positions still agree.

* Acceptance Criteria
- A freshly armed hook (exact or prefix, with prior events on the log) lists =Pending: 0, Fired: 0= — never a raw cursor.
- A hook that has consumed N matching events lists =Fired: N=; after N more with the handler command broken, =Fired: 2N= (per =fired_count='s execution-attempt semantics; failure subdivision is P7's).
- An exact-topic hook and a prefix hook armed at the same instant show comparable values in every column (the =4= vs =164= discrepancy is impossible by construction).
- With events published while a hook cannot run, =Pending= reports the backlog for both cursor kinds; a backlog beyond the cap renders =1000+=.
- A hook whose command exceeds 30 characters does not shift any column: =Command= is rendered last and un-padded, and all preceding columns remain aligned with the header.
- =hook list --json= (per =v0.1/cli-json-list-output.org= + this doc's additions + P7's fields) carries =cursor=, =cursor_kind=, =pending=, =fired_count= for each hook.
