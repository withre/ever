#+title: Hook Test Harness — exercise a delivery path without waiting for a real event
#+state: draft
#+FILETAGS: :subscriber:orchestrator:cli:testing:

* Summary

=ever hook test= delivers a synthetic event to one registered hook, through the same code the hook daemon uses, and prints exactly what the command received — the bytes on stdin, the environment the store set, the exit status, the output — while appending nothing to the durable log and advancing no cursor.

It exists because a registered hook is not a working hook. A supervisor's notification path failed six times in one session and *every failure was silent*: a =chronoa send= to a session name that no longer existed, a pattern broad enough that ~52 status milestones would have arrived as user turns, a =status: "done"= guard that could never match because Ever nests the payload as an escaped JSON string inside =value=, and an =--on-exit= publishing to the same topic as real completions. The supervisor polled by hand for hours without noticing it was never being woken.

Two consequences of that history shape this document more than the draft it comes from:

1. *The test must execute inside the store process.* Verified live (see [[*Re-verification]]): a hook child inherits the *store's* environment, not the publishing client's. A =hook test= that forked from the CLI would run with the operator's =PATH= and session variables and would therefore have *passed* on failure 1 — the exact bug it was built to catch.
2. *The envelope on stdin must stay byte-identical to production.* Marking the envelope =synthetic: true= would change the bytes a guard is compared against, in a tool whose whole claim is "these are the bytes". The synthetic marker belongs in the environment, where handlers already read =EVER_TOPIC=, and where it perturbs nothing. See [[*Refusability]].

* Motivation

Today the only way to exercise a hook is to publish a real event into a real topic. That appends to the durable log, advances the cursor of *every* hook whose pattern matches, fires all of them, and still does not show what any command received on stdin. So nobody does it, and a delivery path's first real exercise is the moment it is needed.

The escaping failure is worth stating precisely, because it is the shape the tool must make visible. Ever delivers:

#+begin_src json
{"topic":"probe.done","offset":1,"timestamp":1785716928289,"key":null,"value":"{\"agent\":\"ever4-spectest\",\"status\":\"done\"}"}
#+end_src

A shell guard written as =case "$EVENT" in *'"status":"done"'*)= can never match, because the literal bytes are backslash-quoted. It looked correct for weeks because only its *reject* path had ever run: it declined an =exited= event for the wrong reason and therefore looked right. =ever sub= compounds this — verified live, it renders the payload *unescaped* for display:

#+begin_src
$ ever sub probe.done --from 0
[probe.done:1] {"agent":"ever4-spectest","status":"done"}
#+end_src

so eyeballing the topic actively hides the defect. *Any output this feature produces must not repeat that mistake.*

** Goals

- =ever hook test <id-or-name> --topic <topic> [--payload <data>]= — synthesise a matching event, run the hook's command exactly as the daemon would, and print a labelled transcript: matched pattern, the stdin bytes verbatim with a byte count, the =EVER_*= environment, exit status, and the command's own output.
- Structural guarantee, not a promise: the delivery path used by =hook test= cannot append to the log, cannot advance the tested hook's cursor, and cannot advance any other hook's cursor — enforced by the types it is handed, and re-checked observationally on every run.
- A separate, non-executing query — =ever hook match <topic>= — answering "which hooks would this topic wake?", which is a different question and must not execute anything.
- An exit-status vocabulary that distinguishes "the hook's command failed" from "the test could not be run" from "the test ran but did not conclude".
- A refusal surface (=EVER_SYNTHETIC=) that handlers can key on, specified as a compatibility contract from the day it ships, because handlers are shell scripts written by other people.

** Non-Goals

- *Validating the command's logic.* This shows what was delivered and what the command did with it. Whether that was right stays with the author.
- *A replacement for =hook logs=.* That is forensics after the fact; this is a preflight.
- *Fan-out.* No mode of this command executes more than one hook. See [[*Why =--all= is dropped]].
- *Fixing the escaping problem.* A companion change would remove the class outright; it is proposed in [[*Alternatives considered]] and deliberately kept out of this document's scope.
- *Publishing.* =hook test= never calls =TopicManager.publish=. If you want a real event, use =ever pub=.

*** "reports the exec failure with the resolved path, not a generic error"

Verified live: Ever never sees an exec failure. The daemon builds a shell string and runs =/bin/sh -c=, so =fork= succeeds, =execve("/bin/sh")= succeeds, and it is the *shell* that fails. A hook pointing at a deleted script produced, in its execution log:

#+begin_src
/bin/sh: line 1: /var/tmp/ever-spectest-probe/gone.sh: No such file or directory
#+end_src

and the store logged =Hook #3 (pid 3274710) exited with status 127=. So:

- The transcript can show the shell's diagnostic and exit 127. It *cannot* distinguish "exec failed" from "the command deliberately exited 127", and must not claim to.
- "The resolved path" is only present when the hook's command is an absolute path. A command found on =PATH= yields =sh: cmd: command not found= with no path — and *which* =PATH= is the store's, not the operator's. Reporting the store's =PATH= in the transcript is therefore worth more than reporting a resolved path, and this document specifies that instead.

** Facts established at base (all verified live unless marked)

1. *A hook child inherits the store's environment, not the client's.* A hook published to with =SPECTEST_CLIENT_MARKER=hello-from-client ever pub …= saw =SPECTEST_CLIENT_MARKER=<absent>=. The daemon passes =self.envp=, captured when the store started (=src/store/hooks.zig=). The child's =PATH= in the probe was the store's =PATH=, including a =direnv= entry from the shell that started it.
2. *=ever status= never touches the network.* It takes =--data-dir= (default =./data=) and reads the directory. Run from a directory with no =./data= it prints =error: cannot open data directory './data'= and exits 1 — regardless of =EVER_PORT=. The supervisor's observation holds. Every =hook= subcommand, by contrast, is a wire client. *Consequence:* "the store" in this document always means the store reached over the wire at =--address= / =--port=, never a data directory.
3. *=ever hook logs <id>= has no result-limiting flag*; =--limit 3= gives =error: unknown flag '--limit'=. The *wire* request already carries =max_bytes: u32 = 65536= (=protocol.HookLogsRequest=) — the capability exists and is simply not exposed. Unrelated to this feature, but it means "add a flag" here is a CLI-layer change, not a protocol change.
4. *Framework error shape.* =zig-cli-kit= writes a readable line to stderr, then =main.zig='s =else => return err= lets Zig print an error-return trace pointing into the dependency's source. Every failure in the =hook= family exits *1* — =rm= on a missing name, =logs= on a missing hook, a missing required argument, an unknown flag, an unknown subcommand. *The family has no exit-status vocabulary at all*, so this document defines one rather than claiming to inherit one.
5. *=.required = true= on a positional is currently advisory.* =ever hook logs= with no argument produced the handler's own =error: hook ID is required= (=src/main.zig:516=), not a framework error. A new subcommand must validate its own arguments.
6. *Hook names are not unique, and name resolution silently takes the first match.* Two hooks named =guard= were registered; =ever hook rm guard= removed =#1= without a word about =#5=. Directly relevant: a preflight that silently tests the wrong hook is worse than no preflight. See [[*Resolving =<id-or-name>=]].
7. *=ever pub= to a topic that does not exist fails* (=error: topic not found=, exit 1), and =pub= accepts arbitrary non-JSON bytes for a topic that does: =ever pub probe.done 'not json at all'= delivered ="value":"not json at all"=.
8. *The envelope's =offset= is a global log offset; an exact-topic hook's cursor is a topic-local skip count.* In the probe, five events on =probe.done= carried envelope offsets 1–5 while =hook list= showed cursor =5=; a second topic's first event took global offset 7. The two numbers are in different coordinate systems. See [[*Synthesising the event]].
9. *Hook execution logs live at =<data-dir>/hooks/<id>-<millis>.log=*, and =hook logs= selects the newest file whose name starts =<id>-= and ends =.log= (=src/net/server.zig=, =handleHookLogs=). Anything this feature writes into that directory would be picked up as a real execution.
10. *=ProcessTable= is mutex-protected* (=src/store/hooks.zig=), read by the connection thread for =hook ps= and written by the daemon thread.
11. *=reapChildren= is the sole =waitpid(-1, …, WNOHANG)= caller, it runs on more than one thread, and it discards the status of any pid not in the process table* (=src/store/hooks.zig:752-769=). Three callers, five call sites: =daemonLoop= (=:738=, every 500 ms), =killChildrenForHook= (=:710= and =:723= only — reached from =Server.handleUnregisterHook=, =src/net/server.zig:318-329=, i.e. *on a connection thread* whenever anyone runs =ever hook rm=), and =shutdownChildren= (=:813=, =:826=). [Superseded: 2026-08-03] An earlier draft of this fact named only the daemon loop, and the design that rested on it stated the wrong invariant; a later draft double-counted =:738=, which is =daemonLoop='s site and not =killChildrenForHook='s. *The consequence of the discard, which matters more than the fact:* any design that routes a child's exit status through the process table inherits a silent loss whenever the reaper observes a pid before it is registered — and the symptom is a confident wrong verdict, not a missing one. See [[*The second race, which is worse than the first — and what it does to the store]]. This is the central implementation hazard — see [[*The reaper race]].
12. *[read from source, not executed]* Cursor advance and one-shot removal live in =processHook=, one level *above* =executeHookCommand=, which touches neither. The structural separation this document needs already exists; it is not yet enforced by types.
13. *The =EVER_*= variables are not =envp= entries.* The daemon builds one shell string — =cd '<cwd>' && [custom env] EVER_TOPIC='…' … EVER_DATA='<envelope>' exec <command>= — and passes it as a single =argv= element to =/bin/sh -c= (=src/store/hooks.zig:909-944=), escaping each value through the hand-written =appendShellEscaped= (=:1153-1163=). =EVER_SYNTHETIC= will be implemented in that prefix, and the =EVER_DATA=/stdin identity passes through that quoter — pinned by [[*Test plan]] step 1. Custom =hook.env= pairs are additionally filtered by =isValidEnvKey= (=:1132-1140=) and *silently dropped* when the key is empty or non-identifier (=:914-926=); there is no CLI flag that sets them today, so every hook in the field has ="env":null=.
14. *A single =argv= element is capped at 131,072 bytes on this kernel* — measured by bisection: the largest accepted element was 131,065 bytes plus a 6-byte prefix, i.e. exactly 32 pages including the NUL. Values of 100,000 and 130,000 bytes deliver to a hook today (measured); above roughly 130,800 the shell string exceeds the cap. *[read from source]* =execve= failing leaves the child at =std.os.linux.exit(127)= (=:1078-1081=) with no diagnostic at all — a second, independent producer of the ambiguous 127 that [[*Re-verification]] discusses. Relevant to =EVER_VALUE=; see [[*Alternatives considered]].

* Proposal

** Where the test executes

*Server-side, in the store process, on the connection thread.* A new wire message pair =hook_test = 0x10= / =hook_test_ok = 0x90= (next free codes; =0x0F=/=0x8F= are the last in use).

The alternative — fork from the CLI — is rejected on evidence, not taste. It would deliver:

| Property             | Real delivery                        | Client-side fork                  |
|----------------------+--------------------------------------+-----------------------------------|
| environment          | store's =envp= at start (fact 1)      | operator's shell                  |
| =PATH=               | store's                              | operator's, usually richer        |
| cwd                  | hook's recorded =cwd=                 | reproducible                      |
| user / umask / rlimits | store's                            | operator's                        |
| fd 1,2               | regular file in =<data-dir>/hooks/=   | terminal, or whatever             |

The argument does not rest on any particular failure having gone green, and an earlier draft of this document made the mistake of resting it on one. *The general form:* a client-side fork can only ever produce *false greens about the environment*, and the environment is the one property of a delivery that cannot be reproduced outside the store process. Every other divergence in the table above is either reproducible with care or visible when it goes wrong; an environment difference is invisible by construction, because the transcript would faithfully report an environment nobody will ever deliver into.

Failure 1 is a good illustration provided it is told accurately, and the accurate telling is a *stronger* argument. The source (=ace-operations.org:29-32=) records *two simultaneous causes*: a stale session name after a =pi -r= revival, *and* an empty =$CHRONOA_DAEMON=. A client-side test would have caught the first — verified: with =CHRONOA_DAEMON= set, =chronoa send <no-such-session> …= exits 3 with =error: session '…' not found=, so the transcript would have been *red*, not green. It is the second cause that a client-side test cannot see, and the sequencing is the point: *once the session name was fixed, a client-side preflight would have gone green while production stayed broken*, because =$CHRONOA_DAEMON= is present in an operator's shell and absent in the store's. A preflight that goes green at the moment the remaining bug becomes the only bug is worse than no preflight.

[Superseded: 2026-08-03] The first draft of this section claimed a client-side test "would have printed a green transcript for the single failure that cost the most hours". That is false and falsifiable in one command; it collapsed two causes into one. The claim above replaces it.

The tool's value is entirely in being *the same path*, and the environment is where paths differ.

Executing on the *connection* thread rather than the daemon thread is also deliberate: a =hook test= against a 30-second command must not stall delivery for every other hook, which is what running it inline in =pollAndExecute= would do.

** Command surface

#+begin_src
ever hook test <ID-OR-NAME> --topic <TOPIC> [OPTIONS]

Arguments:
  <ID-OR-NAME>              Hook ID (e.g. 7) or hook name

Flags:
      --topic <TOPIC>       Topic to synthesise the event on (required unless the hook's
                            pattern is an exact topic, in which case it defaults to the pattern)
      --payload <DATA>      Event value, exactly as `ever pub <topic> <DATA>` takes it
                            (default: {})
      --payload-file <PATH> Read the value from a file; `-` reads stdin
      --key <KEY>           Event key (default: none, matching what `ever pub` can express)
      --offset <N>          Envelope offset (default: the offset the next real event would take)
      --timestamp <MS>      Envelope timestamp in ms (default: now; set it for a byte-stable
                            transcript a test can compare against)
      --timeout <DUR>       Harness deadline, e.g. 30s (default: 60s)
      --json                Emit the transcript as a single JSON object instead of prose
      --mark-envelope       Add "synthetic":true to the delivered envelope. Off by default;
                            turning it on changes the bytes and invalidates a byte-level guard test.
#+end_src

=--topic= is required rather than inferred because inferring it is impossible for the patterns that matter. =notify-orch.sh= — the field artefact this feature was written for — is registered on the prefix =ever4.= and its entire branch table switches on =$EVER_TOPIC=:

#+begin_src bash
case "$TOPIC" in
  *.done)      … ;;
  *.exit)      … ;;
  *.learnings) … ;;
esac
#+end_src

Without =--topic= not one row of that table can be exercised. This is also what makes failure 4 — =--on-exit= publishing to the same =.done= topic as real completions — catchable: run the hook once with =--topic ever4.X.done= and once with =--topic ever4.X.exit= and read which rows fire.

Validation: =--topic= must satisfy the hook's pattern under the store's own =matchTopic=. If it does not, exit 2 naming both, because testing a delivery that could never happen is a false green. The topic is *not* required to exist in the store — a preflight's purpose is to run before the first real event — but if it does not exist the transcript carries a warning, since =ever pub= to a missing topic fails (fact 7) and "the topic was never created" is itself a common cause of "the hook never fired".

** =--payload= semantics

*=--payload= is the value, not the envelope.* Its contract is defined by reference, and the reference is exact: =--payload D= must be accepted if and only if =ever pub <topic> D= would be accepted, and must produce the same =value= bytes.

That answers the "what if it is not valid JSON" question by construction: *nothing special happens.* =ever pub= accepts arbitrary bytes (fact 7), so =hook test= accepts them, wraps them in the envelope with the same JSON escaping, and delivers. A preflight that rejected payloads production accepts would be a tool that lies in the safe direction, which is still lying — and it would train operators to distrust it.

Two accommodations, both because the current CLI cannot express what the store can:

- =--key= exists because =ever pub= has no key argument but the HTTP publish path does (=src/net/http.zig=), so real events *can* carry keys and a handler reading =.key= or =$EVER_KEY= is otherwise untestable. Note that =EVER_KEY= is set to the *empty string* for keyless events, not left unset — verified live.
- =--payload-file -= exists because a payload containing quotes is exactly the payload that breaks under shell quoting, and requiring the operator to get that right in the tool that exists to catch quoting bugs would be perverse.

** The transcript

The transcript is the product. Its one job is to show the bytes rather than a view of the bytes.

#+begin_src
$ ever hook test 5 --topic ever4.spectest.done --payload '{"agent":"ever4-spectest","status":"done"}'

Hook             #5 (notify-orch)
Pattern          ever4.                       (prefix)
Topic            ever4.spectest.done          matches pattern: yes
Command          /home/ryota/.local/state/ace-ever4/notify-orch.sh
Working dir      /home/ryota/.local/state/ace-ever4
Executed by      store 127.0.0.1:17890, pid 3241, uid 1000
Store PATH       /nix/store/…/bin:/home/ryota/.local/bin:…

── stdin: 140 bytes, verbatim ──────────────────────────────────────────────
{"topic":"ever4.spectest.done","offset":7,"timestamp":1785719232750,"key":null,"value":"{\"agent\":\"ever4-spectest\",\"status\":\"done\"}"}
── end stdin ───────────────────────────────────────────────────────────────

── environment set by the store for this delivery ──────────────────────────
EVER_TOPIC=ever4.spectest.done
EVER_OFFSET=7
EVER_TIMESTAMP=1785719232750
EVER_KEY=
EVER_DATA=(identical to stdin, 140 bytes)
EVER_SYNTHETIC=1     ← set only by `hook test`; unset during real delivery
── end environment ─────────────────────────────────────────────────────────

── stdout + stderr, as the store captures them ─────────────────────────────
…
── end output ──────────────────────────────────────────────────────────────

Exit             0, after 41 ms   (signal: none, delivered: yes)
Store            events 7 → 7; every registered hook's cursor unchanged   (conclusive)
#+end_src

*The stdin block, the =EVER_*= values and every byte count above are a verbatim capture; the header and output lines are illustrative.* Those 140 bytes are what the store actually delivered for that topic and that value on an isolated probe on 2026-08-03, at the offset and timestamp the event actually received, recorded by a hook that printed its own stdin and its own =wc -c=. The first draft of this document carried an *invented* envelope labelled "137 bytes" which was in fact 145 — a reviewer measured it, in the document whose thesis is that the byte count is the point. Anything used as a worked example here must be measured, because an implementer will copy it into a golden test.

Rules, each of which is a defect this prevents:

1. *The stdin block is written verbatim.* No pretty-printing, no unescaping, no re-serialising, no truncation. =ever sub= renders =value= unescaped and that rendering is what hid the bug for weeks; this block exists precisely to be the thing =ever sub= is not.
2. *The byte count is printed with the block.* "Looks the same" is how the failure survived. A count lets a reader see that an embedded newline or a trailing byte is in the payload rather than in the display.
3. *=EVER_DATA= is not printed twice.* It is byte-identical to stdin by construction; printing it again invites a reader to diff two renderings and conclude something about the second one. The transcript asserts the identity and prints the length.
4. *The store's =PATH= is printed*, because it is the single most common reason a command that works in the operator's shell fails under the daemon, and because (per [[*Re-verification]]) it is the honest replacement for "the resolved path".
5. *Delimiters are unambiguous and carry lengths, and the prose form carries every field the JSON object carries*, so neither is the "real" one. That is a checkable property rather than a sentiment: =signal=, =delivered=, =reason= and =conclusive= must appear in the prose form — on the =Exit= and =Store= lines, as above — and not only under =--json=. A reviewer diffs the two field by field.

=--json= emits =={"hook":{…},"event":{…},"stdin_bytes_written":<int>,"stdin_bytes_intended":<int>,"stdin":"<escaped>","env":{…}, "exit_code":<int|null>,"signal":<int|null>,"duration_ms":<int>,"output":"<escaped>", "delivered":<bool>,"reason":"<string|null>","store":{"events_before":…,"events_after":…, "cursors_changed":<int>,"conclusive":<bool>}}== on one line. The two stdin counts are separate fields rather than one because they can differ and the difference is the finding — see [[*The fork-to-registration window]]. Coordinate the exact key style with the in-flight =air/v0.1/cli-json-list-output.org= draft rather than inventing a second convention.

** Refusability

*The synthetic marker lives in the environment, not in the envelope.*

- =EVER_SYNTHETIC=1= is set for, and only for, deliveries made by =hook test=.
- It is *absent* — not empty — during real delivery. The distinction matters here specifically: =EVER_KEY= is already set-but-empty for keyless events (verified live), so "set but empty" means something else in this environment and cannot be overloaded.
- The documented handler idiom is exactly one line, and it is the idiom handlers already use for =EVER_TOPIC=:

#+begin_src bash
[ -n "${EVER_SYNTHETIC:-}" ] && { echo "refusing synthetic event"; exit 0; }
#+end_src

- The value is =1=. It is never any other value. If a future need arises for variants, they get new variables; =EVER_SYNTHETIC= is a boolean-presence flag forever. This is stated now because it is a compatibility surface for shell scripts written by other people from the day it ships.

*Why not the envelope, which is what the draft asked for.* Adding ="synthetic":true= to the JSON changes the bytes on stdin between test and production. The tool's entire claim is "these are the bytes your guard will be compared against"; a tool that alters them to advertise itself has falsified its own transcript, and it does so in exactly the byte-level-guard class of bug that motivated the feature. A handler doing =case "$EVENT" in *…*)= would be compared against a different string in test than in production.

=--mark-envelope= is provided for the case where a handler genuinely cannot read its environment (an =ssh= or =sudo= hop that scrubs it, a handler that re-execs). It is off by default, and the transcript states plainly, when it is on, that the stdin block is no longer production-faithful.

*Refusability is a courtesy, not a safety mechanism.* A hook whose command deletes something will delete it. The transcript's header prints the command and cwd before any output, and the honest mitigation is the operator reading it, plus [[*Why =--all= is dropped]].

** Why =--all= is dropped

The draft's =--all= / =--pattern= answers "which hooks would this topic wake?" — a *different question*, needing no execution. Two decisions:

1. *=--all= is dropped entirely.* A flag that turns "run one command" into "run every matching command" is an incident with a keystroke. On the incident store that would have been 42 hooks, 24 of them pointing at deleted scripts. There is no mode of =hook test= that executes more than one hook.
2. *=--pattern= becomes its own non-executing verb: =ever hook match <topic>=.* Not a flag on =hook test=, because the word =test= implies execution and a flag that silently makes an executing command non-executing is precisely the ambiguity that produced the six failures.

#+begin_src
$ ever hook match ever4.spectest.status
ID   NAME          PATTERN   KIND     COMMAND
#7   notify-orch   ever4.    prefix   /home/ryota/.local/state/ace-ever4/notify-orch.sh

1 of 42 hooks would fire for 'ever4.spectest.status'.
#+end_src

It is a pure function of the hook table and =topic.matchTopic=: no execution, no publish, no cursor, no log file. Using the store's own matcher is not an implementation detail — =fetchPatternByOffset= calls =matchTopic= too (=src/store/topic.zig:338=), so the query and delivery agree by construction. If =hook match= resolved client-side it would have to duplicate the matcher, which is exactly the divergence this document warns about for =buildEventJsonFromStore=; prefer a small server-side verb, or expose the one matcher through the library.

*The contract needs stating precisely, and it is not the one the heading implies.* "Which hooks would this topic wake?" is only equivalent to "which hooks' patterns match?" while every registered hook is armed. =ever--hook-gc-and-lease.org= is scheduled *before* this item and introduces =armed= / =disabled= / =quarantined= plus =expires_at=; from the day it lands, a hook can match a topic and not wake for it. So: *=hook match= answers "whose pattern matches", it prints the hook's state in a column, and once states exist it marks the rows that match but would not fire.* Anything vaguer starts lying on the day item 2 ships — the same class of error this document catches in the OVERVIEW. It is also *strictly cheaper and lands sooner* than the execution half, and it is the piece the rest of the round-4 hook chain actually needs. See [[*What this makes checkable, and what it does not]].

The same listing should back a =--dry-run= on =hook add= ("this pattern would match these existing topics; N hooks already cover it"), which catches failure 2 at the earliest possible moment. Noted as a follow-up, not specified here.

** Exit status

The =hook= family currently exits 1 for everything (fact 4), so there is nothing to inherit. Four codes, and one rule that makes them memorable:

*0 and 1 are verdicts about the hook. 2 and 3 are verdicts about the harness.*

| Code | Meaning                          | Examples                                                                      |
|------+----------------------------------+-------------------------------------------------------------------------------|
|    0 | Delivered; command exited 0      |                                                                               |
|    1 | Delivered; command failed        | nonzero exit (including 127), or killed by a signal                           |
|    2 | *The test did not run*           | unknown/ambiguous hook, =--topic= not matching the pattern, store unreachable, no execution slot, fork/pipe/log failure, store-unchanged assertion violated |
|    3 | *The test ran but did not conclude* | command exceeded =--timeout= and was killed; no verdict available          |

The command's own exit code is *not* propagated into the CLI's exit status. It is reported in the transcript and in =--json=, but 127 is the most informative code in this system and colliding it with a shell's own 127 would make =ever hook test … ; echo $?= unreadable. A script that wants the raw code reads =--json=.

Exit 3 is separate from 1 because "the hook hung" and "the hook failed" call for different actions, and because a preflight that reports failure for a slow command trains people to ignore it.

** Structural non-mutation

"Must not touch the durable log" is enforced three ways, in decreasing strength.

*** By type

Extract the delivery core out of =HookDaemon.executeHookCommand= (which today already touches neither cursors nor the log — fact 12) into free functions whose signatures make mutation a compile error.

*The extraction must be in two halves, and only the first is shared with the daemon.* =executeHookCommand= is *fire-and-forget*: it forks, writes stdin, registers the child in =ProcessTable= and returns; the exit status is collected later by =reapChildren=, and =processHook= advances the cursor immediately after the *spawn* (fact 12, =src/store/hooks.zig:866-888=). A single =deliver= that returns an exit status therefore cannot be the daemon's path — handing it to =pollAndExecute= would serialise all hook delivery behind each hook's runtime, bounded only by =DEFAULT_HOOK_TIMEOUT_SECS = 300=, which is exactly the synchronous model =air/v0.1/hook-execution.org= was written to replace and exactly what this document rejects for the daemon thread elsewhere.

#+begin_src zig
const Spawned = struct {
    pid: i32,
    pgid: i32,

    /// The single deadline for this delivery, `started_ms + --timeout` for a

=deliver = spawn + awaitCompletion= exists only as the =hook test= handler's composition of the two. =processHook= calls =spawn= alone, and its behaviour is unchanged.

The guarantee lives on =spawn='s parameter list, which is where the publish and cursor paths would have had to enter:

- No =*TopicManager= parameter → =publish= is unreachable → the log cannot grow.
- No =*HookTable= parameter → =updateCursor= and =remove= are unreachable → no cursor can move and a =--once= hook cannot be auto-removed by a test.
- =hook= and =event= are values, so nothing the callee does is visible to the caller's table.
- =data_dir= is passed as a slice rather than reached through =self.hook_table.data_dir= (which is how =executeHookCommand= gets it today, =src/store/hooks.zig:949-955=), precisely so that no =*HookTable= is in scope. Note the log path is formatted into a fixed =[256]u8= with an =error.PathTooLong= failure mode, and =hook-tests/= is six bytes longer than =hooks/=; that margin needs a test, not an assumption — and the test must cover *both* callers, because after this split =spawn= is called from the daemon thread and from connection threads, and the buffer is the one piece of it that is length-sensitive.

*One deadline, not two.* =SpawnOpts= carries the harness deadline (used to bound the stdin write, [[*The fork-to-registration window]]) and =awaitCompletion= bounds the wait. These are *the same budget*, computed once as =started_ms + --timeout= and stored on =Spawned.deadline_ms=; both consume it. Stated because two independently-passed deadlines would give =--timeout 60s= up to 120 s of wall clock and make exit 3 ambiguous about which half was exceeded. =awaitCompletion= therefore takes no deadline parameter.

*Sizing, corrected.* An earlier draft called this "a refactor of ~40 lines with no behaviour change". =executeHookCommand= runs =src/store/hooks.zig:891-1129= — *239 lines*, essentially all of it the delivery core: envelope build, shell-string assembly through =appendShellEscaped=, log-file open, a ~60-line context header, =pipe2=, =fork=, =execve=, the stdin write and =ProcessTable= registration. [Superseded: 2026-08-03] The "~40 lines" figure understated it by roughly 5× and a scheduler would have sized this wrong. It is behaviour-preserving for the daemon *except* for the registration reordering required by [[*The fork-to-registration window]], which is called out there and is the one part of the refactor that changes what the daemon does.

This is the part of the proposal a reviewer should scrutinise hardest, because it is the part everything else rests on. It should land and be reviewed *separately* from the new subcommand.

The =hook test= handler additionally never constructs an =Event= that anything else can reach: it is a stack value passed to =spawn= and dropped.

*** By observation, on every run

The server samples, immediately before and immediately after the delivery:

- the log head offset and the total event count,
- the =(hook_id, cursor)= vector for *every* registered hook.

The result is printed as the transcript's last line. If anything changed, the command exits 2 and says which hook's cursor moved.

*Honest caveat, because this is a measurement that can lie.* The daemon runs concurrently; if a real event arrives mid-test, real cursors legitimately advance and a naive check reports a false alarm. So the check is *conditional on the head offset*: if the head moved, the line reads

#+begin_src
Store            3 events published by others during the test — cursor check inconclusive
#+end_src

and the exit status is unaffected. Under the acceptance test the store is quiescent and the check is exact. A check that cried wolf under load would be switched off within a week.

*** By test

See [[*Test plan]] — including a mutation test that removes the type-level guard and confirms the assertion fires.

*** The implementation this forbids

The obvious shortcut is "publish to a scratch topic and let the daemon deliver it". It must be rejected explicitly, because it looks like the small change and it is wrong in three ways at once: it appends to the durable log, it advances the tested hook's cursor, and it wakes *every other hook* whose pattern matches — on the incident store, a prefix hook like =ever4.= would have fired for a scratch topic under it. Reviewers should treat any patch containing a =publish= call in the =hook test= path as an automatic rejection.

* Design Details

** Synthesising the event

| Field       | Value                                                                       |
|-------------+-----------------------------------------------------------------------------|
| =topic=     | =--topic=, validated against the hook's pattern                              |
| =offset=    | =--offset=, else the offset the next real event would receive (global scale) |
| =timestamp= | current wall clock in ms, else =--timestamp= if determinism is needed        |
| =key=       | =--key=, else null                                                           |
| =value=     | =--payload=/=--payload-file= bytes verbatim, else ={}=                        |

The envelope is produced by the *same* =buildEventJsonFromStore= the daemon uses. It is currently private to =src/store/hooks.zig=; make it =pub= (or move it beside =deliver=) rather than writing a second builder, because two builders will diverge and the divergence will be invisible.

On =offset=: the envelope's =offset= is a *global* log offset, whereas an exact-topic hook's cursor is a topic-local skip count (fact 8). =hook list='s "Last Offset" column and the envelope's =offset= are therefore in different coordinate systems for exact-topic hooks. The default must be the global head, not the hook's cursor, and the transcript must not present the two side by side without labels — a transcript that teaches a false equivalence is worse than one that omits the number.

** The reaper race

*This is the hazard the draft's "with the store lock untouched" does not cover, and the one most likely to be missed in implementation.*

=HookDaemon.reapChildren= calls =waitpid(-1, &status, WNOHANG)= — *any* child of the store process — and discards the status of any pid it does not recognise (=src/store/hooks.zig:752-769=). It runs on the daemon loop every 500 ms, and it also runs on *connection* threads (fact 11). If the =hook test= handler forks a child and then calls =waitpid(child_pid, …)=, it races every one of those callers:

- a reaper wins → the handler's =waitpid= returns =ECHILD= and *the exit status is unrecoverable*;
- the handler wins → correct.

*The variable is the width of the fork-to-wait window — not the command's runtime, and not the reap period.* [Superseded: 2026-08-03] An earlier draft said "a typical hook command finishes in tens of milliseconds against a 500 ms reap period, so this passes in development and loses intermittently in the field". That is the wrong variable, and getting it wrong is what produced a regression test that could not fail. Measured on a standalone probe mirroring this structure (=~/.local/state/ace-ever4/reviews/probes/reaper-race-probe.c=, reproduced independently by this author):

| Fixture                                             | =ECHILD= per 200 runs, 3 trials |
|-----------------------------------------------------+---------------------------------|
| command runtime 1 / 10 / 50 / 200 ms, zero fork-to-wait gap | 0, 0, 0, 0 — at every runtime   |
| 0 ms gap                                            | 0, 0, 0                         |
| 5 ms gap                                            | 2, 2, 2                         |
| 20 ms gap                                           | 8, 8, 7                         |

With the waiter already queued on the parent's wait channel when the child exits, it wins regardless of how long the command ran. A preflight that intermittently reports "exit status unknown" is a preflight nobody trusts, and it fails in the direction of a false green — but it is the *window*, not the command, that decides how often.

*The resolution rests on an invariant, and it is not the obvious one.* [Superseded: 2026-08-03] An earlier draft stated it as "the daemon stays the sole owner of =waitpid=". *That is already false at base* — =reapChildren= runs on connection threads too, via =Server.handleUnregisterHook= (=src/net/server.zig:318-329=) → =HookDaemon.killChildrenForHook= (=src/store/hooks.zig:701-726=), which calls it at =:710= and =:723=. An implementer who believes the daemon is the sole owner will audit =daemonLoop= and will not notice that an =ever hook rm= issued during a =hook test= reaps the test's child from another thread.

*The true and load-bearing invariant:* =reapChildren= is the *sole* =waitpid(-1)= caller; it may run on any thread; and every status it collects is published through =ProcessTable.removeByPid= (=src/store/hooks.zig:566=). Nothing else in the store process may call =waitpid= in any form. Any new code path that wants a child's exit status must obtain it through the process table, not by waiting.

*This design satisfies that invariant by construction, and the ECHILD race above therefore cannot occur under it at all.* The =hook test= handler never calls =waitpid=; it waits on a completion slot. The race is described here because it is the obvious implementation and the one an implementer will reach for, not because the specified design mitigates it — there is no second waiter to lose. Everything that follows is about a *different* race, which routing through the table introduces.

*** The second race, which is worse than the first — and what it does to the store

=reapChildren='s =if (removeByPid(pid)) |entry|= has *no else branch*: an unrecognised pid's status is discarded (fact 11). If the reaper collects a pid before the spawning thread has registered it, two things follow, and the second is much worse than the first.

*The operator-visible half.* The completion is never signalled, so the connection thread waits out the entire =--timeout= and reports *exit 3, "the test ran but did not conclude"*, for a hook that exited successfully in a millisecond. A confident wrong verdict after a 60-second wait, where the ECHILD race at least produced an honest "unknown".

*The half nobody sees, which is the reason this invariant is a deliverable rather than a nicety.* =ProcessTable.removeByPid= is the *only* code anywhere that clears an entry — =slot.* = null= appears exactly once, at =src/store/hooks.zig:573=; =killAll= (=:606-616=) and =killByHookId= (=:618-630=) only signal. Verified by grep at base. So an entry that is added *after* its pid has been reaped names a pid that will never be waited again, and *nothing can ever remove it*:

1. One of =MAX_CONCURRENT_HOOKS= = 16 slots is held forever, and =hook ps= reports a running hook process that does not exist, forever.
2. Once past its deadline it is *permanently* past it, so =checkTimeouts= (=:773-802=) sets =any_killed= on every pass and executes its phase-2 =nanosleep(1 s)= *on the daemon thread* — every 500 ms poll cycle, indefinitely. Hook delivery degrades to roughly a one-in-three duty cycle and never recovers. Note this arrives *sooner* under this feature than it would for a daemon spawn: a leaked =hook test= entry carries =started_ms + --timeout=, 60 s by default, not =DEFAULT_HOOK_TIMEOUT_SECS='s 300 s.
3. Sixteen such leaks and =activeCount() >= MAX_CONCURRENT_HOOKS= holds forever: =executeHookCommand= returns =ConcurrentLimitReached= (=:894-895=), which =processHook= handles at =:868= by returning *without* advancing the cursor, so *all* hook execution stops until the store is restarted.
4. None of it is announced. A store in state 2 looks healthy from every CLI view and simply gets slow — which is precisely the shape of the incident that produced this batch, and precisely the reason its diagnosis took process-level forensics rather than any tool the store offers.

So the cost of getting the ordering wrong is not a bad preflight verdict. It is a daemon that quietly stops delivering, with no event, no log line and no CLI symptom, permanently, until someone restarts the store.

*** How reachable this is today, stated precisely

The *forker* is single-threaded today: =executeHookCommand= is reached only from =processHook= ← =pollAndExecute= ← =daemonLoop= (=src/store/hooks.zig:740=). The *reaper* is not (fact 11). So the window is *not* unreachable at base, and it is worth being exact about it, because the natural summary — "the only component that forks is also the only component that waits" — is false and this document already records why in fact 11.

What is true: an =ever hook rm= against a hook that has a tracked running child calls =killChildrenForHook=, which calls =reapChildren= on the *connection* thread up to thirty times over three seconds (=:707-716=, the 3 s / 100 ms loop), entirely concurrently with the daemon thread sitting between =fork= (=:1069=) and =process_table.add= (=:1122=). That is a genuine cross-thread window today. What keeps it from mattering is width, not impossibility: the daemon's exposed sub-window is the few microseconds between the child exiting and =add=, because a blocked stdin write is *ended* by the child's exit (=writeAllFd= breaks on =EPIPE=). Microseconds against a 100 ms reap cadence, requiring a coincident =hook rm=.

*That is exactly the wrong kind of safe.* The probability is low enough that nobody would ever diagnose it and high enough that it is not zero, and the failure is silent and permanent. This feature moves the fork onto a connection thread and hands the window to an operator-supplied payload, which turns a coincidence into a reproducible one — but the property has to be *stated* either way, because it is currently preserved by an accident of threading that nothing enforces and nothing tests.

Ever registers *after* the fork today, so the natural implementation is the broken one. Measured on the structural probe, with the window forced wider than the reap period:

#+begin_src
./probe slot-after  15 1 600 500   →  ok=0  timedout=15  DISCARDED=15   (×3, deterministic)
./probe slot-before 15 1 600 500   →  ok=15 timedout=0   DISCARDED=0    (×3, deterministic)
#+end_src

*Moving registration ahead of the stdin write ([[*The fork-to-registration window]] item 1) closes this in practice but not by construction, and the difference is measurable.* With registration immediately after =fork=, the residual window is straight-line code, but the spawning thread can still be preempted between =fork= returning and taking the =ProcessTable= mutex. Driving the reaper far above its real rate:

| Fixture (registration after fork, zero added gap) | Discarded            |
|---------------------------------------------------+----------------------|
| 1 ms reaper, 600 runs                             | 2                    |
| 1 ms reaper, 2,000 runs (quieter interval)        | 0                    |
| 0 ms reaper, 1,000 runs                           | 1                    |
| 1 ms reaper, 1 ms added gap, 200 runs             | 179, 172, 172        |

Three losses in roughly 3,600 runs at the tightest reaper this host will sustain — rare, load-dependent, and *not zero*. A one-millisecond gap takes it to 86%. So the reorder is a mitigation by timing, and every future edit that adds work between =fork= and registration silently buys some of it back. This is exactly the shape of defect the fleet conventions warn about: half-real under a light fixture, total under a heavier one.

*** The by-construction fix, and the invariant it preserves

*Invariant: the reaper must never observe a pid whose =ProcessTable= entry does not yet exist.*

Stated that way round, and not as "the reaper never loses a status", because the status is the lesser casualty. =removeByPid= is the only code that clears an entry, so a status collected before registration does not merely go missing — it makes the entry that arrives afterwards *immortal*, with the four consequences above ending in a store that stops delivering. "Never loses a status" invites the reading that a dropped status is an accuracy problem; it is a resource leak with a permanent, silent, store-wide failure at the end of it.

Three changes, each small, and together they hold by construction rather than by timing:

1. *=spawn= reserves the =ProcessTable= slot before =fork=* — taking the =MAX_CONCURRENT_HOOKS= check and the slot in one locked section — and fills in the pid under the same mutex =removeByPid= takes, immediately after =fork= returns. This also satisfies [[*The fork-to-registration window]], for a different reason: visibility and killability.
2. *=reapChildren= may no longer discard.* An unrecognised pid's status goes into a small bounded pending table; =spawn= checks it immediately after filling in the pid. Both interleavings are then covered — either =removeByPid= finds the entry, or the status is waiting in pending and the spawner collects it — and neither depends on who wins a mutex.

3. *=ProcessTable= gains a way to clear a reservation, and =spawn= owns it.* This follows directly from the finding above and is easy to miss: since =removeByPid= is today the *only* clearer, reserving a slot before the pid exists creates a *new* class of immortal entry — one whose pid is never filled in at all. Every path out of =spawn= that leaves a reservation without a live, reapable child must release it explicitly: =fork= failing, =pipe2= failing, the log-file open failing, =error.PathTooLong=, and the case where the status is collected from the pending table (where the entry must be cleared by the spawner, because no future =removeByPid= will match it). Without this, the fix for the leak introduces a second source of the same leak.

The pending table cannot overflow, and that is an argument rather than a hope: =waitpid(-1)= reaps only *direct* children of the store process, the store's only direct children are hook children, and with the concurrency check moved ahead of =fork= at most =MAX_CONCURRENT_HOOKS= of them can exist. A =MAX_CONCURRENT_HOOKS=-entry pending table is therefore sufficient by the same bound that sizes =ProcessTable=. If it ever does fill, the daemon logs loudly rather than dropping silently — the silent drop is the mechanism of every failure in this section.

*Change 2 is the fix; change 1 is an optimisation that narrows the window it covers.* Stated that way round deliberately: an implementer who does only change 1 passes every step in this plan except the ordering mutation, and reopens the hazard the first time anything is inserted between =fork= and registration — which is precisely how the current 30-second window came to exist.

With that settled, the mechanism: register the child in the existing mutex-protected =ProcessTable= (fact 10) with a completion slot.

#+begin_src zig
pub const ProcessEntry = struct {
    // … existing fields …
    synthetic: bool = false,
    /// Per-entry deadline. Daemon spawns get
    /// `start_time + DEFAULT_HOOK_TIMEOUT_SECS * 1000`, preserving today's
    /// behaviour exactly; `hook test` spawns get `start_time + --timeout`.
    deadline_ms: i64,
    /// Non-null only for `hook test` spawns. Refcounted; see below.
    completion: ?*Completion = null,
};

const Completion = struct {
    done: std.atomic.Value(bool),
    status: std.atomic.Value(u32),
    /// 2 at creation: one reference for the ProcessTable slot, one for the
    /// waiting connection thread. Whoever decrements it to 0 frees it.
    refs: std.atomic.Value(u8),
};
#+end_src

=reapChildren= already calls =removeByPid=; when the removed entry carries a =completion=, it stores the status, sets =done=, and releases the table's reference. The connection thread waits on =done=, bounded by the harness deadline, and releases its own reference when it stops waiting — for *any* reason.

*Ownership rule, stated because "both sides free carefully" is how this becomes a double free.* =Completion= is heap-allocated by the connection thread with =refs = 2=. There is exactly one release function, =release(c)= = =if (c.refs.fetchSub(1, .acq_rel) == 1) allocator.destroy(c)=. Neither side ever frees unconditionally, and neither side reads =*Completion= after its own release. This matters concretely because =ProcessEntry= is copied *by value* out of =removeByPid= (=src/store/hooks.zig:566-581=), so the reaper still holds the pointer after the slot is cleared — a design in which the connection thread "just frees it on timeout" is a use-after-free that will never fire in development and will fire in the field.

*The rule that makes "exactly twice" checkable is stated in terms of the table reference, not in terms of code paths,* because enumerating paths is how one gets missed:

- *The table's reference exists if and only if the slot reservation succeeded.* =reapChildren= releases it, *after =removeByPid= returns* — not while holding the =ProcessTable= mutex, which is a spin lock (=src/store/hooks.zig:545-547=) and must never contain an allocator call. =removeByPid= takes and drops the mutex internally and returns the entry by value, so a caller-side release is both correct and outside the lock.
- *The connection thread's reference always exists*, and it releases exactly once, on every exit from the wait: success, timeout, client disconnect, allocation failure, or any error return.
- *A failed reservation is a two-release case.* If =ProcessTable.add= returns =false= — which can happen despite the =activeCount()= check at =src/store/hooks.zig:894=, since the check and the =add= race, and whose own comment reads "Table full — should not happen since we checked above, but be safe" — no table reference was ever created, so the connection thread owns both and releases twice. The same holds if it never reached =add= at all. This is the path an enumeration of "early exits between =add= and the wait" misses, because =add= was reached and simply did not take.

A one-line statement of the whole rule: *=refs= starts at 2; the reservation succeeding is what transfers one of them to the table; whoever holds a reference releases it exactly once and then stops looking at the object.*

This falls out well for four other reasons:

1. *A hanging test child is killed, but not by =checkTimeouts= as it stands.* [Superseded: 2026-08-03] An earlier draft claimed "=checkTimeouts= already kills entries in the table, so a hanging test child is killed by the same code that kills a hanging real hook". It does not: =checkTimeouts= (=src/store/hooks.zig:773-802=) compares every entry's =start_time= against the single global =DEFAULT_HOOK_TIMEOUT_SECS = 300= (=:509=), and =ProcessEntry= carries no per-entry deadline. With =--timeout= defaulting to 60 s the harness would return exit 3 while the child ran on for another 240 s. Two changes make the claim true: =deadline_ms= on =ProcessEntry= (above), with =start_time + 300 s= as the fallback so *daemon* behaviour is unchanged; and =checkTimeouts= comparing against it. The connection thread additionally sends =SIGTERM= to the pgid itself the moment its deadline expires, so exit 3 is honest at the instant it is returned rather than up to 1.5 s later; =deadline_ms= is the *backstop* that still bounds the child if the client disconnects and no connection thread is left to signal. These are not redundant — one bounds the operator's wait, the other bounds the child's life. Note in passing that =checkTimeouts= phase 2 does a 1 s =nanosleep= *on the daemon thread* (=:794=), so any timing-out child — test or real — stalls delivery for a second; that is a pre-existing cost this feature makes easier to trigger, and it is why the connection thread does its own =SIGTERM=.
2. =shutdownChildren= already SIGTERMs the table, so stopping the store during a test cleans up.
3. =hook ps= shows the running test — a long preflight ought to be visible — and =synthetic= gives it a column so it is never mistaken for real traffic.
4. =MAX_CONCURRENT_HOOKS= (16) then applies to tests too. A test that cannot get a slot is exit 2, "the test could not be run", which is the honest answer rather than a queue.

Rejected alternatives: routing the test through the daemon thread (a 30 s command stalls all hook delivery for 30 s); blocking =SIGCHLD= around the fork (does not help — =reapChildren= does not need the signal); =pidfd_open= + =waitid(WNOWAIT)= (still racy against a =waitpid(-1)= that reaps, and it would break the sole-caller invariant this design depends on).

** The fork-to-registration window

*This is a defect in the daemon that this feature does not introduce, makes reachable on demand, and must therefore bound. It is stated here rather than fixed here.*

=executeHookCommand= writes the entire envelope to the child's stdin pipe *before* registering the child in =ProcessTable=:

#+begin_src
src/store/hooks.zig:1085   _ = std.os.linux.close(pipe_fds[0]);
src/store/hooks.zig:1089   writeAllFd(pipe_fds[1], json);      // blocking, unbounded
src/store/hooks.zig:1090   _ = std.os.linux.close(pipe_fds[1]);
   …
src/store/hooks.zig:1122   if (!self.process_table.add(entry)) { … }
#+end_src

=writeAllFd= (=:1144-1151=) is a blocking loop on a raw =write=. If the envelope exceeds the pipe buffer (64 KiB on Linux) and the handler does not read stdin, the *caller* blocks for the child's entire lifetime, during which the child is invisible to =hook ps=, to =checkTimeouts= and to =shutdownChildren=.

*Measured independently on an isolated probe, 2026-08-03.* Hook =#1= = a script that never reads stdin and sleeps 30 s; one event with a 90,000-byte value published at 01:05:44; an unrelated hook =#2= on a different topic given an event at 01:05:47. Store log:

#+begin_src
[2026-08-03 01:06:14] Hook #1: started pid 3710312, log: …/hooks/1-1785719144255.log
[2026-08-03 01:06:14] Hook #2: started pid 3714748, log: …/hooks/2-1785719174268.log
#+end_src

The "started pid" line is printed *after* the stdin write, and appears 30 s after the publish. =hook ps= during the window reported "No running hook processes". The unrelated hook =#2= fired 27 s late: *one hook stalled the entire daemon*, which is the scenario this document rejects for the daemon thread elsewhere. Note also the log filename timestamp (=…1785719144255=, taken before the fork) versus hook =#2='s (=…1785719174268=): 30,013 ms apart in a single stalled cycle.

*Why it is this document's problem.* =hook test= runs this code on a *connection* thread with an operator-supplied payload, and =--payload-file= exists precisely so that large and awkward payloads can be delivered. =ever hook test <id> --payload-file 100k.json= against a handler that does not =cat= wedges a connection thread with no deadline at all — =--timeout= is specified as bounding the *completion wait*, and the completion wait has not started yet. The feature turns an accident into a one-liner.

*What this design does about it,* and no more:

1. =spawn= reserves the =ProcessTable= slot *before the fork* and fills in the pid immediately after it, so the child is visible to =hook ps= and killable by =checkTimeouts= and =shutdownChildren= for the whole of its life. Registration therefore precedes the stdin write by construction rather than by ordering care. This is the one part of the =spawn= extraction that changes daemon behaviour — the child becomes visible earlier and its concurrency slot is taken earlier — and it should be reviewed as a behaviour change rather than waved through as part of a refactor. It is *also* required, for a completely different reason, by [[*The by-construction fix, and the invariant it preserves]]: two findings converge on the same one-line reorder, and the reorder alone is sufficient for neither.
2. On the *test* path, the stdin write is bounded by the harness deadline (non-blocking fd plus =poll=, carried on =SpawnOpts=). A write that does not complete within it is *exit 2*, "the test could not be run", naming the bytes written and the bytes intended. It is not exit 1: nothing has been learned about the hook.
3. The transcript reports bytes *written*, not bytes *intended*. This is not pedantry: =writeAllFd= returns =void= and breaks silently on =n <= 0=, so a short write today — a handler that exits early, closing the read end — truncates the envelope with no error anywhere. A transcript that printed the intended length would be asserting the document's central claim about bytes on the strength of a number it did not verify.
4. The daemon's own instance of the unbounded write is *not* fixed here. Bounding delivery to a real hook changes delivery semantics (what does the store do with an event a handler will not read?) and that decision belongs with =ever--hook-gc-and-lease.org='s backoff-and-quarantine work, or its own item. This document only stops =hook test= from being the easy way to trigger it.

** Output capture

The child's fd 1 and 2 are redirected to a regular file, exactly as in production — not to a pipe. This matters twice: libc's buffering mode and =isatty= must not differ from production, and a pipe with no concurrent drain deadlocks on output larger than the pipe buffer. (The stdin side has the same shape and is live today — see [[*The fork-to-registration window]].)

The file is =<data-dir>/hook-tests/<hook-id>-<millis>.log=, deliberately *not* under =<data-dir>/hooks/=:

- =hook logs= selects the newest =<id>-*.log= in =<data-dir>/hooks/= (fact 9). A test log placed there would be returned as if it were a real execution, quietly corrupting forensics.
- =ever--hook-exec-log-retention.org= is concurrently trying to bound =<data-dir>/hooks/= after it reached 105,272 files. A preflight run in a loop by CI must not feed that directory.

The file is read back into the response and *unlinked*. Nothing accumulates: the feature adds no new unbounded directory, which is the whole point of keeping it out of the other item's way. On harness failure the file is left in place and its path named in the error, so a crash still leaves evidence, and the daemon sweeps orphans in =hook-tests/= at startup.

** Resolving =<id-or-name>=

Reuse the existing list-then-match resolution, with *two* changes. Both exist because testing the wrong hook and reporting success is the failure mode this feature exists to eliminate, and reproducing it in the resolver would be self-defeating.

1. *Refuse an ambiguous name.* Names are not unique (fact 6) and =hook rm= silently takes the first match. =hook test= exits 2, listing every candidate with its id and pattern.
2. *Refuse an argument that is both a valid id and a name.* =handleHookRm= (=src/main.zig:556-563=) tries =parseInt= first and only falls back to a name lookup on failure, so a hook *named* =3= can never be addressed by name at all. Verified live: with a hook =#3= named =rec= and a hook =#4= named =3=, =ever hook rm 3= removed =#3= and left =#4= standing. =hook test= must exit 2 when a numeric argument also matches a name, and offer =--id N= / =--name S= to disambiguate. This is the same silent-wrong-hook defect as fact 6, in the same resolver, one line of specification away.

(=hook rm='s two behaviours are separate defects, out of scope here. Both are worth raising with =ever--hook-gc-and-lease.org=, which adds =gc= and =enable= onto the same resolver.)

** CLI declaration

Declared under the existing =hook= command in =src/main.zig='s =app= literal, in the same style as its siblings. Two framework facts constrain it (facts 4, 5): positional =.required= is advisory, so =<ID-OR-NAME>= is validated in the handler; and an unhandled error reaches =main='s =else => return err= and prints a Zig error-return trace into the dependency's source. Every =hook test= failure path must therefore terminate through the handler with a message and an explicit =std.process.exit(N)=, never by returning an error — otherwise a preflight failure prints a stack trace into =zig-cli-kit=, which is both useless and alarming.

** Wire protocol

| Code | Name           | Direction | Body                                                                    |
|------+----------------+-----------+-------------------------------------------------------------------------|
| 0x10 | =hook_test=    | Request   | ={"hook_id":N,"topic":"…","value":"…","key":null,"offset":null,"timestamp":null,"timeout_ms":60000,"mark_envelope":false}= |

Errors use the existing =error_response= (=0xFF=) frame. Note the request carries =hook_id= only — name resolution happens client-side against =list_hooks=, as =hook rm= already does, so the ambiguity refusal is in one place.

* What this makes checkable, and what it does not

=ever hook test= is scheduled third in =reviews/round-4/proposed-air/OVERVIEW.org= on a two-clause argument, quoted in full because an earlier draft of this section quoted only the first half and then claimed to have refuted the whole:

#+begin_quote
*3 early despite being a feature.* =ever hook test= is what makes every later hook change verifiable, and it is the tool half of the preflight rule in item 8. Four of six silent notification failures would have been caught by it.
#+end_quote

Three separate claims, and they do not stand or fall together.

1. *"Makes every later hook change verifiable" does not hold.* Counted item by item below: *1 of 15* acceptance criteria across the four sibling Ever items becomes checkable with this feature, and the one that does is checked by the non-executing =hook match= query rather than by executing anything.
2. *"The tool half of the preflight rule in item 8" is true but does not gate anything.* =ace--supervisor-plumbing-preflight.org= is a skill edit; all three of its acceptance criteria are about what the skill *text* says, so it can land in full whether or not this command exists. It reads better with the command and does not wait for it.
3. *"Four of six silent notification failures would have been caught" holds*, with the correction that it requires =--topic=, which the triage draft lacked. See [[*Against the six failures it claims to catch]].

*Which metric the conclusion is about matters, and the two metrics disagree.* On *sibling acceptance criteria* the query half does all the work — 1 of 15, and =hook match= is what checks it. On *field failures* the execution half does most of the work — =hook test= catches failures 1, 3 and 4; =hook match= catches failure 2. [Superseded: 2026-08-03] An earlier draft wrote "the part of this proposal that does the work is the non-executing =hook match= query, not the execution" without naming the metric, which the six-failures table in this same document contradicts. Stated properly: *the query half is what unblocks the batch; the execution half is what the feature is for.* That is an argument about sequencing, not about value, and it is why the recommendation below is to split them rather than to demote either.

* Alternatives considered

** Make the delivered envelope unambiguous instead — and do it anyway

Failure 3 exists because the payload is nested as an escaped JSON string. The narrow, permanent fix is *two lines in =executeHookCommand=*: export the raw payload alongside the envelope.

#+begin_src bash
EVER_DATA   # the full envelope, unchanged — value is an escaped string   (today)
EVER_VALUE  # the payload bytes, exactly as published, unescaped          (proposed)
#+end_src

Verified: no =EVER_VALUE= exists today; the daemon sets =EVER_TOPIC=, =EVER_OFFSET=, =EVER_TIMESTAMP=, =EVER_KEY=, =EVER_DATA= only. With it, the field script that motivated this document collapses from

#+begin_src bash
jq -r '.value | fromjson | .status // empty'
#+end_src

to =jq -r '.status' <<<"$EVER_VALUE"=, and — more to the point — the naive literal-byte guard =case "$EVER_VALUE" in *'"status":"done"'*)= *works*. It breaks nothing: it adds a variable, changes no existing bytes, and needs no protocol change.

*This is higher value per line than =hook test=,* and this document recommends landing it first. It does *not* subsume =hook test=: it addresses failure 3 only, leaving 1 (dead session name), 2 (too broad), and 4 (wrong topic) untouched. The two are complements, and the ordering argument is that the cheap permanent fix should not wait behind the expensive general one. Note the asymmetry in kind, not only in cost: =hook test= makes failure 3 *visible*, and only to someone who remembers to run a preflight; =EVER_VALUE= makes it *not happen*.

*It is not, however, a three-line patch, and the reason is the bound this document names so that its own document does not have to discover it.* The =EVER_*= variables are shell assignments prefixed to a single =/bin/sh -c= argv element, not =envp= entries (fact 13). =EVER_VALUE= would put the payload into that element a *second* time, roughly doubling it. A single argv element is capped at 131,072 bytes on this kernel — measured, fact 14 — and a 90,000-byte value delivers today, so the doubling puts an event of that size over the cap. The failure mode is the worst available: =execve= returning =E2BIG= leaves the child at =std.os.linux.exit(127)= with *no diagnostic anywhere*, which is byte-for-byte indistinguishable from the deleted-script case this document spends a section on. So =EVER_VALUE= must either declare a size threshold above which it is omitted (and say so, in-band, where a handler can see it), or large values must move off the argv entirely. That is a real, checkable constraint, it is not obvious, and it is exactly what gets discovered in production if the change ships as "three lines, obviously safe".

(=EVER_VALUE= belongs in its own document — it changes the hook delivery contract, which is a compatibility surface for shell scripts written by other people, and that is a different blast radius from adding a CLI verb. It is the same reason this document specifies =EVER_SYNTHETIC= as a contract from day one. It is named here because a reviewer should be able to see that the cheaper option was considered, why it was not treated as sufficient, and what it will cost.)

** =hook add --dry-run=

Catches failure 2 at the earliest possible moment, needs no execution machinery, and is cheap. But it cannot catch 1 or 3, which require running the command, and it does not help an *already registered* hook — which is every hook at the moment anyone becomes suspicious. It is strictly weaker than =hook match= + =hook test=, and it should be *implemented as* =hook match= run before registration rather than as a third code path.

** A =--dry-run= on =ever pub=

Rejected. It would have to answer "which hooks would this wake" (that is =hook match=) or actually deliver (that is =hook test=), and attaching either to the publish verb puts a non-publishing mode on the one command whose entire contract is that it publishes.

* Acceptance

Each criterion names the failure it comes from, and each is checkable by a reviewer without inheriting the author's context.

1. *The transcript shows the bytes, not a view of them.* For a hook guarding on =status: "done"= against a nested-JSON payload, =ever hook test= prints a stdin block containing =\"status\":\"done\"= — backslashes present — with a byte count, and the same run through =ever sub= prints it unescaped. Both outputs appear in the test's evidence, because the pair is the point. *(failure 3)*
2. *Nothing moves.* On a quiescent store, before and after a =hook test=: the event count is unchanged, =hooks.json= is byte-identical, and every hook's cursor is unchanged including the tested hook's and including a =--once= hook, which is still registered afterwards. The command's own last transcript line reports the same, and reports =inconclusive= rather than failing if another event arrives mid-test.
3. *The environment is the store's.* A hook tested with a marker variable set in the invoking shell does not see it; the transcript's environment block shows the store's =PATH=. A test run from a directory that is not the hook's cwd reports the hook's cwd and the command observes it. *(failure 1)*
4. *=--topic= is enforced and load-bearing.* A prefix-pattern hook cannot be tested without =--topic=; a =--topic= that does not satisfy the pattern exits 2 naming both; a hook whose command branches on =$EVER_TOPIC= takes a different branch for a =.done= topic than for a =.exit= topic. *(failure 4)*
5. *=--payload= is =ever pub='s argument.* Over a named sample set — ={}=; a nested-JSON object; =not json at all=; a payload containing ='=, =\=, =$=, a backtick and ="=; an empty string; a 100,000-byte value — =hook test --payload D= produces the same =value= bytes as =ever pub <topic> D=, and neither rejects any of them. ("For any =D=" was the earlier wording and is not checkable; the sample set is chosen so that each element is a quoting or sizing boundary rather than a repetition.)
6. *Refusal works and costs nothing.* A handler containing =[ -n "${EVER_SYNTHETIC:-}" ] && exit 0= exits 0 without side effects under =hook test= and runs normally under a real event. With =--mark-envelope= off — the default — the stdin bytes are byte-identical to those of a real event with the same topic, key, offset, timestamp and value.
7. *A deleted script is reported honestly.* Testing a hook whose script has been removed shows the shell's own diagnostic and exit 127 in the transcript, prints the store's =PATH=, and exits 1 (the hook failed) — not 2. The transcript does not claim to have detected an exec failure.
8. *Exit statuses are distinguishable.* A command exiting 3 gives CLI exit 1; an unknown hook id gives 2; an ambiguous hook *name* gives 2 and lists every candidate; a numeric argument that also matches a hook *name* gives 2 rather than silently picking the id; a command sleeping past =--timeout= gives 3, and the child's process group has been *signalled* by the connection thread before =hook test= returns, with the pgid gone within one daemon tick of that. [Superseded: 2026-08-03] An earlier wording promised the pgid was *gone* by the time the caller saw exit 3. Signalled is not gone: a handler running =trap '' TERM= survives =SIGTERM=, and the kill then arrives only through =checkTimeouts='s existing TERM → 1 s =nanosleep= → KILL escalation (=src/store/hooks.zig:786-801=) — roughly the 1.5 s the sentence claimed to have removed. What the connection thread's =SIGTERM= buys is a timely *verdict*, not a timely *death*, and the criterion now says only what it buys. Test-plan step 7 always worded this correctly; the criterion is brought into line with the step rather than the design being changed. A payload larger than the pipe buffer delivered to a handler that never reads stdin gives 2 within =--timeout=, not a hung connection.
9. *=ever hook match <topic>= lists every hook whose *pattern* matches that topic and nothing else*, prints each hook's state in a column, and runs no command, writes no file and moves no cursor. [Superseded: 2026-08-03] An earlier wording was "every hook that would fire". [[*Why =--all= is dropped]] retired exactly that phrasing — once =ever--hook-gc-and-lease.org= introduces =disabled= and =quarantined=, a hook can match and not fire — but the fix landed in the Proposal and not here, so the document asserted both contracts at once. Test-plan step 13 already agreed with the new one.
10. *No fan-out exists.* Checked against two artefacts rather than asserted universally: =ever hook test --help= lists no flag that takes a pattern or a set, and the =hook test= command declaration in =src/main.zig='s =app= literal has exactly one positional, no =takes_rest=, and no alias that accepts one.

* Test plan

Integration tests alongside =src/tests/integration.zig=, each against a store on an ephemeral port with its own temporary data directory. *Never against the default port or data directory* — the store on this workstation is production for it.

1. *Envelope fidelity, and the =EVER_DATA= identity.* Publish a real event and capture what a recording hook receives; run =hook test= with the same topic/key/value and capture again. Assert the two stdin byte strings are equal. This is the test that makes criterion 6 mean something, and it is the one that would have caught the envelope-marking mistake had it been made. The same recording hook has both =$EVER_DATA= and its own stdin in scope, so it must also assert they are byte-equal, with a payload containing ='=, =\=, =$=, a backtick and ="=. The document asserts that identity "by construction", but it is not free: =EVER_DATA= reaches the child through the hand-written =appendShellEscaped= quoter (fact 13), and the transcript prints only a length, which cannot detect a regression in a quoter. Verified to hold at base (138 bytes both sides, identical) — which makes this a pin, not a bug hunt, and pins are what stop it becoming one.
2. *Non-mutation.* Snapshot event count, =hooks.json= bytes and the full cursor vector; run =hook test= (including against a =--once= hook and with a second, unrelated prefix hook registered); assert all three are identical and that the second hook did not run.
3. *Mutation test of the type-level guard.* Re-introduce a mutable =*HookTable= parameter to =spawn= and add an =updateCursor= call; step 2 must FAIL. Restore. A guard that is not shown to fail when removed is not evidence. Run the same exercise for the publish path.
4. *Escaping visibility.* A payload containing =\"status\":\"done\"= must appear escaped in the transcript's stdin block and unescaped in =ever sub= output; assert both, in the same test, so the divergence is pinned rather than described.
5. *Environment isolation.* Start the store with a marker variable; run =hook test= from a process *without* it and one *with* a different value; assert the child observed the store's value both times.
6. *Reaper race — the fixture must vary the fork-to-wait window, not the command's runtime.* [Superseded: 2026-08-03] An earlier version of this step looped "a trivial command ≥200 times" and required a =waitpid(child_pid)=-from-the-connection-thread implementation to fail. Run exactly as written against exactly that implementation it passes *200/200, three times* — measured. It held the one variable that matters at zero. A step that asserts a mutation must fail and provably cannot detect it is executable prose that lies to the next implementer, which is the category this document weights highest. *Rewritten:* the fixture takes a test-only injected delay between =fork= and the wait, and asserts a *rate*, not merely "must fail". Against a pre-fix build that waits directly on the child: ≥15 lost statuses per 200 runs at a 20 ms injected gap (measured: 8, 8, 7 per 200 at 20 ms, 2, 2, 2 at 5 ms, 0, 0, 0 at 0 ms — so 20 ms is the smallest gap giving a comfortable margin over noise, and the step should use 50 ms and require ≥10). Against the specified build: *0 per 200 at every gap*, because the status is routed through the process table and the pending table, neither of which is timing-dependent. Also run under =zig build test -Doptimize=ReleaseFast=; a race may only manifest in a release build. *Bound the probe with a wall-clock cap* so a pre-fix run reports "still waiting after N s" rather than hanging and producing no evidence.
7. *Registration ordering — the mutation that actually discriminates, and the leak is the assertion.* Mutate =spawn= to register the child *after* the stdin write, as =executeHookCommand= does today, and give it a payload large enough that the write outlasts a reap period. Assert *the store-side symptom first*, because it is the one that persists and the one no CLI view announces: after the run, =hook ps= still lists a process whose pid does not exist, =ProcessTable.activeCount()= is one higher than the number of live children, and repeating the run =MAX_CONCURRENT_HOOKS= times wedges =activeCount= at the limit so that a subsequent *real* hook event is never delivered and its cursor never advances. Then assert the operator-side symptom: a hook that exits successfully in milliseconds is reported as *exit 3, "did not conclude"*, after the full =--timeout=. A test that pins only the second assertion passes the day someone makes the verdict honest while leaving the entry immortal. Measured on the structural probe, deterministically: 15/15 lost with registration after the fork, 0/15 with the slot reserved before it. Then assert the same fixture passes 15/15 against the specified build. Separately, with correct ordering but =reapChildren= mutated back to discarding unknown pids instead of using the pending table, assert the residual timing race is *observable* — measured at 179/200 losses with a 1 ms injected gap and a 1 ms reaper — so that the pending table is pinned as load-bearing rather than as belt-and-braces. Without this step nothing in the plan notices when someone inserts work between =fork= and registration.
8. *Timeout.* A hook sleeping past =--timeout= gives exit 3; the child's process group has been signalled before the command returns; the pgid is gone and =hook ps= is empty within one daemon tick of that. Assert separately that a handler running =trap '' TERM= still dies, via =checkTimeouts='s escalation, rather than surviving the test — that is the case acceptance criterion 8 stopped promising. *Prove it regresses:* against a version where the deadline is left to =checkTimeouts= and its global =DEFAULT_HOOK_TIMEOUT_SECS=, the pgid is still alive at exit 3 and this step must fail — which is what it asserted against the previous draft of this document, where it would have passed only by accident. Separately assert that a *daemon-spawned* hook still gets the 300 s default and not =--timeout='s 60 s, because the tempting fix for this step is to make the global smaller, which would start killing real hooks five times earlier than today.
9. *Large payload, unread stdin.* A payload above the 64 KiB pipe buffer delivered to a handler that never reads stdin: assert =hook test= returns within =--timeout= with exit 2 naming bytes written versus bytes intended, that the child appears in =hook ps= *during* the window (i.e. it was registered before the write, not after), and that the daemon delivered an unrelated hook's event while it was in progress. Against base ordering — write before register — all three assertions fail; that is the regression this step pins. Measured shape to reproduce: a 90,000-byte value and a =sleep 30= handler stalled the whole daemon for 30 s and left =hook ps= empty throughout.
10. *Slot exhaustion.* With =MAX_CONCURRENT_HOOKS= real hooks running, =hook test= exits 2 with "the test could not be run", not 1, and the run happens under the testing allocator so that the failed-reservation two-release path is exercised rather than merely specified.
11. *Reservations are released on every failure path.* Force each of =fork=, =pipe2= and the log-file open to fail in turn (fault injection on =SpawnOpts=, or a =data_dir= long enough to trigger =error.PathTooLong=), and after each assert that =ProcessTable.activeCount()= has returned to its pre-call value. Then force the pending-table path — the status arriving before the pid is filled in — and assert the same. This is the step that stops the fix for the immortal entry from introducing a second immortal entry; without it the reservation is a slot leak with no pid, which =removeByPid= can never clear because it matches on pid.
12. *No log-directory pollution.* Count entries in =<data-dir>/hooks/= before and after 50 =hook test= runs: unchanged. =<data-dir>/hook-tests/= is empty afterwards. =hook logs <id>= still returns the last *real* execution.
13. *Completion lifetime.* Under a loop of =hook test= runs that time out (exit 3), assert no leak and no double free under the testing allocator. The fixture must drive all three reference topologies, because an earlier version drove only the first and the other two are where the rule was incomplete: (a) normal completion and timeout; (b) =ever hook rm= run concurrently *against other hooks*, so =reapChildren= is driven from a connection thread as well as the daemon; (c) slot exhaustion, so =ProcessTable.add= actually returns =false= and the two-release path runs — without this, step 10's scenario is never seen by the allocator. Mutate the =release= refcount to an unconditional =destroy= on the connection-thread side; this step must fail. This is the step that pins [[*The reaper race]]'s ownership rule, and it is the one most likely to pass by luck if written loosely.
14. *Ambiguity.* Two hooks with the same name: =hook test <name>= exits 2 and names both ids. A hook *named* =3= alongside a hook =#3=: =hook test 3= exits 2 rather than silently choosing =#3=, and =--id 3= / =--name 3= each resolve unambiguously. Against base resolver behaviour the second case silently picks =#3=; that is the regression this pins.
15. *Match query.* Over a fixture of prefix, exact and (once item 9 lands) glob patterns, =hook match= returns exactly the set =topic.matchTopic= returns, asserted against the function directly rather than against a hand-written expectation.
16. *Removal during a test.* Run =ever hook rm= against the *same* hook a =hook test= is currently executing — the path that reaches =reapChildren= from a second thread via =killChildrenForHook= (fact 11). Assert the command returns *exit 2*, =reason="hook unregistered during test"=, rather than 1: the child was killed by store bookkeeping, not by anything the hook did, so no verdict about the hook is available. Assert also that the =Completion= is released exactly twice under the testing allocator, since this is the one path where the reaper's release is triggered by an unrelated client.
17. *Log path length.* A =data_dir= long enough to bring =<data-dir>/hook-tests/<id>-<millis>.log= within a few bytes of the =[256]u8= buffer: assert =error.PathTooLong= surfaces as exit 2 with the path named, not as a truncated write. Run it from *both* callers — the daemon's =hooks/= path and the test's six-bytes-longer =hook-tests/= path — since after the split =spawn= is called from two threads and this is its only length-sensitive buffer.

* Risks and open questions

- *The refactor is the risk, and it is ~239 lines rather than the ~40 an earlier draft claimed.* Extracting =spawn= touches the daemon's hot path. It must land and be reviewed *separately* from the new subcommand, so a bisect can tell the two apart — and one part of it, moving =ProcessTable= registration ahead of the stdin write ([[*The fork-to-registration window]]), is a genuine daemon behaviour change that should be reviewed as one rather than absorbed into "refactor".
- *This document specifies six changes inside =hooks.zig= that are not the new subcommand*: the =spawn=/=awaitCompletion= split, =ProcessEntry.deadline_ms= and the corresponding =checkTimeouts= comparison, the registration reorder, =reapChildren='s pending table, an explicit way to release a =ProcessTable= reservation, and =buildEventJsonFromStore= becoming =pub=. Each is small; together they are the majority of the risk, and none of them is visible from the CLI surface a reviewer would naturally read first.
- *The most expensive failure this feature can cause is silent.* Getting the registration ordering wrong leaks an unclearable =ProcessTable= entry, which ends in a daemon that stops delivering with no event, no log line and no CLI symptom (see [[*The second race, which is worse than the first — and what it does to the store]]). It is worth asking the =ever--hook-gc-and-lease.org= author whether the store should *announce* a =ProcessTable= entry whose pid no longer exists, since that is a one-line check on a table of sixteen and it converts this whole class from silent to noisy — for this feature and for any future one.
- *=hook test= runs the real command.* A hook that deploys, deletes or messages will do so. Mitigated by =EVER_SYNTHETIC=, the header printed before any output, and the absence of fan-out — but not eliminated, and the help text must say so in one line rather than burying it.
- *=--mark-envelope= is a trap by construction.* Anyone who turns it on has stopped testing the production byte stream. The transcript must say so on the run, not only in the docs.
- *Open: should =hook test= be able to target an unregistered hypothetical* (=--command … --pattern …=), so a hook can be exercised before =hook add=? It would catch failures earlier, but it means executing an arbitrary command supplied over the wire by anyone who can reach the store — a materially different security posture from executing a command an operator already registered. Deliberately excluded here; it needs its own document if wanted.
- *Recommended sequencing, stated as a recommendation because the decision is the user's.* Given the 1-of-15 count above, and given that =EVER_VALUE= removes the failure class this harness only reveals, the honest order is: *=EVER_VALUE= first* (own document, small, permanent, bounded by fact 14); *=ever hook match= second* (own document, small — it touches none of =hooks.zig='s process machinery, and it is the only part that unblocks a sibling item); *=hook test= after items 1 and 2*, because its whole cost sits in the daemon's process machinery, which items 1 and 2 are about to move. An earlier draft of this document said only "the sequencing decision is the supervisor's" and declined to make the call; on the evidence assembled here it should make it, and this is the call. Neither companion document is written by this work — both are named, not drafted.
