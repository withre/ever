#+title: Server-Side Hooks
#+state: complete
#+FILETAGS: :subscriber:orchestrator:

* Summary
Add a hook daemon that runs alongside the Ever store. Users register hooks persistently (=ever hook add <pattern> -- <cmd>=) and the daemon executes commands when matching events arrive. No client process to keep alive.

* Motivation
Client-side triggers (=ever on=) require the user to keep a process running. If it crashes, events are missed. If the machine reboots, the trigger is gone. Users want "register and forget" — define what should happen, and Ever handles execution.

The key insight from the debate: the original objection to server-side was about the *store process* running shell commands. But a separate daemon thread — tightly coupled to the store but not inside it — avoids that concern.

** Goals
- =ever hook add <pattern> -- <cmd>= to register a persistent hook
- =ever hook list= / =ever hook rm <id>= to manage hooks
- Hook daemon starts automatically with =ever store start=
- Hooks persist across restarts (stored in data directory)
- Each hook tracks its cursor (last processed offset)
- Commands run with the permissions of whoever started the store

** Non-Goals
- User-level permission isolation (all hooks run as the store's user)
- Distributed hook execution
- Complex scheduling (retry policies, cron-like timing)

* Research: How Other Systems Do This

| System           | Model                         | Registration    | Execution          | Persistence |
|------------------+-------------------------------+-----------------+--------------------+-------------|
| systemd .path    | Separate unit files           | Config files    | Child process      | Filesystem  |
| incron           | Daemon + incrontab            | Tab file        | fork/exec          | Filesystem  |
| PostgreSQL       | LISTEN/NOTIFY + triggers      | SQL DDL         | In-process         | Database    |
| K8s controllers  | Control loop in separate pod  | CRD / RBAC      | Reconciler process | etcd        |
| NATS JetStream   | Push consumer config          | API call        | Delivery to client | Server-side |
| SQLite hooks     | C callback registration       | API call        | In-process         | None        |
| Temporal         | Workflow triggers             | API call        | Worker process     | Server DB   |

** The incron model is the closest fit

incron is a daemon that watches filesystem events (via inotify) and runs commands. It has:
- A table file (like crontab) listing =<path> <event> <command>=
- A daemon (=incrond=) that reads the table and watches
- Commands run as fork/exec from the daemon
- The table persists on disk

Ever's hook daemon would be the same idea applied to event streams instead of filesystem paths.

** The systemd model shows the right separation

systemd .path units watch for file changes and activate a .service unit. The key architecture: the *watcher* (systemd) is separate from the *executor* (the service), but tightly coupled through unit file naming. For Ever:
- The *watcher* is the hook daemon (reads events from the shared log)
- The *executor* is fork/exec of the user's command
- The coupling is through the hook table (stored in the data directory)

** Architecture

│ ever store start             │
│                              │
│  ┌────────────────────────┐  │
│  │ Storage Engine (Log)   │  │
│  └────────┬───────────────┘  │
│           │ shared log       │

│  │ TCP Server             │  │
│  └────────────────────────┘  │
│                              │
│  ┌────────────────────────┐  │
│  │ Hook Daemon            │  │  ← new
│  │  reads shared log      │  │
│  │  fork/exec commands    │  │
│  │  tracks cursors        │  │
│  └────────────────────────┘  │
└──────────────────────────────┘
#+end_src

The hook daemon runs in the same process as the store (a separate thread), sharing the same =TopicManager=. This avoids TCP overhead — the daemon reads directly from the in-memory log.

** Execution Model

The hook daemon:
1. On startup: read =hooks.json=, start watching from each hook's cursor
2. Poll the shared log for new events (using =TopicManager.fetch= / =fetchPattern=) *[Superseded 2026-04-28 / re-checked 2026-08-03: prefix and wildcard hooks use =fetchPatternByOffset=, not =fetchPattern=. Only exact-topic hooks use =fetch=. See B1 in [[./hook-registration-cursor.org]].]*
3. For each new event matching a hook's pattern: fork/exec the command
4. On command completion: update cursor in =hooks.json= *[Superseded: the cursor advances on* spawn*, not on completion — see "Cursor Advancement Strategy" in [[./hook-execution.org]]. And it advances* only *on dispatch: a scan that matches nothing leaves it untouched, which is the defect in [[./hook-scan-cursor-and-lag.org]].]*
5. Sequential per hook (same as =ever on=)
6. On command failure: log to stderr, advance cursor (don't retry)

/[Superseded: 2026-08-03, revised after review — step 6 is superseded by =air/v0.1/hook-gc-and-lease.org=. *Do not implement from this summary; the rules there are conjunctions and their preconditions are the whole of their safety.* In outline: a hook that fails K times consecutively *in ways Ever can attribute to itself* enters =quarantined= and is retried on an exponential backoff with a 1 h ceiling instead of on every matching event, and it leaves =quarantined= by itself on the first success. *A non-zero exit is not one of those ways* — a hook command is a shell fragment whose status is a value its author chose, and for the filter idiom this repo encourages, a non-zero exit routinely means "this event was not for me" (measured: two common filter shapes produce six consecutive exit-1s while working correctly). So step 6's premise — that a non-zero exit is a *failure* — is itself what is superseded, not just the response to it. Deciding that a hook is *dead* is not something the store does on its own — it requires an operator running =ever hook gc --yes=. See R1/R2 in that document for the exact conditions. Step 4's "update cursor on command completion" is separately stale in the shipped code: the cursor advances when the child is *spawned* (=HookDaemon.processHook=), not when it is reaped.]/

** How =ever hook add= works

=ever hook add= is a client command (like =ever topic create=). It sends a new protocol message to the store:

#+begin_src
RegisterHook → { pattern, command, cwd }
UnregisterHook → { id }
ListHooks → {}
#+end_src

The store receives the registration, writes to =hooks.json=, and signals the hook daemon thread to reload.

** Why in-process daemon, not a separate process

A separate daemon would need its own connection to the store (TCP overhead), its own Io setup, and coordination for startup/shutdown. An in-process thread shares:
- The =TopicManager= directly (no TCP serialization for reads)
- The same =Io= instance
- The same lifecycle (starts/stops with the store)
- The same data directory

The cost: one more thread in the store process. But the store already spawns threads for connections, so this is no additional complexity.

** Comparison with =ever on= (client-side)

| Aspect          | =ever on=                    | =ever hook add=                 |
|-----------------+------------------------------+---------------------------------|
| Persistence     | Dies with process            | Survives restart                |
| Registration    | Command-line process         | API call, stored in data dir    |
| Execution env   | User's terminal/cwd/env      | Store's cwd + hook's cwd       |
| Management      | Kill the process             | =ever hook list/rm=             |
| Overhead        | TCP client polling           | Direct log access (in-process)  |
| Use case        | Ad-hoc, development          | Production, long-lived hooks    |

Both coexist — =ever on= for quick ad-hoc triggers, =ever hook add= for persistent ones.

** What to avoid

- *PostgreSQL trigger pitfall*: Triggers running in the database transaction. Ever's daemon runs AFTER events are committed to the log, never during. A slow hook can't block event publishing.
- *Jenkins config drift*: Hooks stored in XML that nobody audits. =ever hook list= makes all hooks visible and =ever hook rm= makes cleanup explicit.
- *Lambda parallel explosion*: Keep sequential execution per hook as default. Each hook has its own cursor and runs independently of other hooks. *[Superseded 2026-08-03: hooks are* not *independent.* =pollAndExecute= (=src/store/hooks.zig:830=) walks every hook sequentially on one daemon thread, and each prefix/wildcard scan holds the global =TopicManager= mutex — a spin lock — for its whole duration. One hook that is far behind therefore delays every *other* hook's dispatch and stalls *publishers*. Measured at =142d5e66=: publish round-trip 2 ms idle vs 21 ms with a saturated hook daemon, the penalty scaling with the single largest hook's scan. Per-hook cursors are independent; per-hook *execution* is not. See [[./hook-scan-cursor-and-lag.org]].*]*
