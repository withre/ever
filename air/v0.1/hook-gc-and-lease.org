#+title: Hook Reclamation — Failure Backoff, Expiry, and =hook gc=
#+state: draft
#+FILETAGS: :subscriber:orchestrator:cli:

* Summary

Nothing in Ever reclaims a hook registration. A hook survives the run that created it, the disappearance of its script, the wipe of its working directory, and every restart of the store. This document specifies four mechanisms that bound a hook's lifetime without ever losing one silently:

1. *Failure accounting and backoff.* A hook that fails repeatedly enters =quarantined= and is retried on an exponential schedule with a one-hour ceiling. It returns to =armed= by itself on the first success. It never escalates to anything worse.
2. *A dispatch guard for the provably-doomed case.* If a hook's working directory no longer exists, the daemon records the failure without forking, because the shell it would fork can only fail. The guard does *not* disable anything.
3. *Optional expiry.* =ever hook add --ttl <dur>= stores an absolute =expires_at=; at expiry the hook is disabled, never deleted. Off by default, consented at registration, renewable.
4. *=ever hook gc=* — an operator command that reports by default and acts only with =--yes=. *It is the only path by which a hook that an operator did not already bound with a TTL can be switched off.*

The division of labour is the point. The daemon's unattended powers are limited to actions that are bounded, self-healing, or consented at registration: it may slow a hook down (quarantine) and it may honour a lifetime the registrant asked for (TTL). It may *not* switch off a registration on its own inference. The two rules that decide a hook is dead — R1 (working directory absent) and R2 (literal absolute command path absent, plus an observed exit 127) — are evaluated by =gc= and applied only under =--yes=, with the evidence printed first.

Nothing here deletes a hook automatically, under any condition, ever, and nothing here disables one without either an operator's =--yes= or a TTL the registrant set.

This document *does not* fix the poll-cycle rescan cost that dominated the 2026-07-27 incident. That is =ever--hook-scan-cursor-and-lag= (round-4 item 1). See [[#scope-boundary][What this does not fix]].

* Motivation

** The failure mode, re-established from source at this base

Verified against =txpyxrnm= / =142d5e66= ("Migrate CLI to zig-cli-kit"), 2026-08-03. All line references are to that commit.

The hook daemon builds a single shell string per dispatch and hands it to =/bin/sh -c= (=src/store/hooks.zig=, =executeHookCommand=):

#+begin_src
cd '<hook.cwd>' && [NAME='v' ...] EVER_TOPIC='...' ... exec <hook.command>
#+end_src

Three properties follow directly, and all three matter for anything that tries to decide whether a hook is dead:

- *=hook.command= is a shell fragment, not an argv.* It is stored as one string and interpolated unquoted so that pipes and redirects work as the user intended (=hooks.zig=, comment above the =shell_cmd.appendSlice(hook.command)= call). There is no "resolved command path" to stat in the general case.
- *=hook.cwd= is a stored absolute path* (=main.zig= =handleHookAdd= reads =/proc/self/cwd=), and it is consumed by a =cd= that short-circuits the whole command with =&&=. If =cwd= is gone, the command *provably never executes*.
- *The exit status is never recorded anywhere durable.* =reapChildren= computes =(status >> 8) & 0xFF= and, if non-zero, writes one line to the store's stderr. It is not written to the hook record and not written to the per-execution log file under =data/hooks/=. Recovering "how often has this hook failed" today means grepping the store's stderr log, which is exactly what the incident had to do.

Nothing in =pollAndExecute= consults liveness of any kind. Every hook in the table is polled every 500 ms for as long as the store runs.

*** Exit-status semantics, measured

Measured 2026-08-03 on an isolated store (own =--data-dir= under =/var/tmp=, port 7931, torn down afterwards), one hook per case, one published event:

| Case                                            | Observed exit | Logged by daemon?            |
|-------------------------------------------------+---------------+------------------------------|
| =cwd= absent, command fine (=/bin/echo hello=)  | 1             | yes                          |
| command is an absolute path that does not exist | 127           | yes                          |
| command exists but is not executable            | 126           | yes                          |
| command resolved from =PATH= (=echo hello=)     | 0             | no (only non-zero is logged) |
| script exits 3                                  | 3             | yes                          |
| script kills itself with =SIGKILL=              | *(nothing)*   | *no*                         |

The last row is a defect that anything counting failures must handle. =reapChildren= extracts =(status >> 8) & 0xFF=, which is 0 for a signal death. *A hook killed by a signal — including by the daemon's own 300-second timeout — is today indistinguishable from a hook that exited 0.* Any naive =consecutive_failures= counter built on the existing extraction would silently treat every timeout kill as a success.

The first row matters too: the =cwd=-missing class does *not* produce 127. It produces whatever the host's =/bin/sh= returns for a failed =cd= — measured 1 here (=/bin/sh= is bash 5.3 on this host); the value is shell-dependent and *the design must not key on it*. This is the entire =/tmp=-wipe class from the incident, and a GC keyed on exit 127 misses all of it.

*** The record format is more fragile than it looks

=HookTable.load= parses =hooks.json= with =ignore_unknown_fields = true=, tries the current format, then falls back to a legacy format, then =catch return=. Measured on the isolated store:

- *Unknown fields are silently discarded on the next write.* Injecting =state=, =consecutive_failures= and =expires_at= into all 7 rows, restarting, and publishing one event: all 7 hooks loaded, and the first =saveLocked= (triggered by the first cursor update, i.e. within one poll cycle) rewrote the file with those fields gone. This is the downgrade path, and it is lossy and immediate.
- *One malformed row destroys the entire registry, silently.* Deleting the =cursor= key from a single row took the table from *7 hooks to 0 hooks loaded*, with **no error, no warning and no log line** — only =Hook daemon started (0 hooks loaded)=. The next =ever hook add= then rewrote =hooks.json= with one row and =next_id= reset to *1*, permanently destroying the other six registrations and reusing their IDs.

That second finding is the reason this document treats the record migration as a first-class hazard rather than a detail. Adding a field without a Zig default to =HookJson= would do exactly this to every existing store on first start of the new binary.

** Goals

- A repeatedly-failing hook stops costing a dispatch per matching event, without being switched off.
- A hook that provably cannot run is *identified* automatically, with the evidence recorded, and stopped by an operator in one command.
- A registration can be given an explicit lifetime at creation, and renewed.
- An operator can see what is reclaimable, and why, before anything happens.
- The disabled/quarantined state and all counters survive a restart.
- A store written by the previous binary loads with no change in hook count or behaviour.
- *No unattended mechanism can silence a registration the store's operator did not bound.*

** Non-Goals

- *Reaping on lag, age, or topic silence.* Beyond the incident's own reasoning (a low-traffic topic is indistinguishable from an abandoned one), there is a structural reason: =Hook.cursor= is *polymorphic in the pattern shape* — a topic-local skip count for exact topics, a global log offset for prefix/wildcard patterns (=hooks.zig= doc comment on =Hook.cursor=; =TopicManager.tipForPatternLocked=). There is no single "lag" number comparable across hooks. Of the 16 hooks on the live store, 9 carry topic-local counts and 7 carry global offsets. Lag may be *reported*; it must never be a reclamation input.
- *Automatic deletion of anything, ever.* Reclamation means =disabled=. Deletion is =ever hook rm= or =ever hook gc --purge <id>… --yes=, both operator-initiated and both targeted at named ids.
- *Automatic disable on inference.* Superseding this document's first revision: the daemon does not disable a hook because it decided the hook is dead. Its only unattended disable is TTL expiry, which the registrant asked for. See [[#why-gc-only][Why the disable rules are not daemon rules]].
- *Repointing a hook's command* (=ever hook update=). See [[#repoint-coupling][Coupling]].
- *Recovering events missed while a hook was broken.* See [[#repoint-coupling][Coupling]]; this is today's behaviour and this document does not change it.
- *Per-hook execution timeouts.* The daemon uses a fixed 300 s (=DEFAULT_HOOK_TIMEOUT_SECS=). Making it per-hook is out of scope. The *interaction* with failure counting is in scope and is resolved in [[#daemon-signals][Signals the daemon sent itself]], not left open.

* Proposal

** <<record-fields>>Record format

Eight fields are added to =Hook=, =HookJson=, =HookJsonLegacy= *and =protocol.HookInfo=*. *Every one carries a Zig default*, so a row written by the previous binary parses unchanged and a response from an older store decodes unchanged.

| Field                  | Type          | Default   | Meaning                                                                        |
|------------------------+---------------+-----------+--------------------------------------------------------------------------------|
| =state=                | =[]const u8=  | ="armed"= | =armed= / =quarantined= / =disabled=                                           |
| =consecutive_failures= | =u32=         | =0=       | Reset to 0 on any success                                                      |
| =last_exit_status=     | =?i32=        | =null=    | =0..255= = exit code; *negative = −signal* (=-9= = SIGKILL)                    |
| =last_error=           | =?[]const u8= | =null=    | Short reason for the last failed attempt; =null= if the last attempt succeeded |
| =next_attempt_at=      | =?i64=        | =null=    | Epoch ms; while =now < next_attempt_at= the hook is skipped                    |
| =expires_at=           | =?i64=        | =null=    | Epoch ms; =null= = no expiry                                                   |
| =disabled_at=          | =?i64=        | =null=    | Epoch ms when the hook entered =disabled=                                      |
| =disabled_reason=      | =?[]const u8= | =null=    | One of the reason strings in [[#reason-strings][Reason strings]]               |

A ninth counter, =timeouts: u32 = 0=, is added alongside them for the diagnostic tally in [[#daemon-signals][Signals the daemon sent itself]]. It is never an input to any rule.

=state= is a *string*, not a Zig enum, so that a record written by a later binary carrying a state this one does not know still parses. An unrecognised =state= value is treated as =armed= and logged once at load, naming the hook id and the value. Rationale: a hook wrongly armed is noisy; a hook wrongly disabled is a silent outage, and round-4's recurring failure class is silent outages.

=expires_at= is stored *absolute*, never as a remaining duration, so a restart cannot extend a lifetime.

A =version: u32 = 1= field is added to =HookFileJson= and written as =2=. The current binary does not branch on it; it exists so a future reader can tell a downgraded file from an original one. This is the only defence available — see [[#downgrade][Downgrade]].

*** Load path hardening (required, not optional)

Given the measured "one bad row loses everything, silently" behaviour, the migration cannot land without this:

- If =hooks.json= exists, is non-empty, and *both* parse attempts fail, the store must:
  1. log an error naming the file, its size, and the parse error;
  2. rename it to =hooks.json.unparseable-<epoch_ms>=;
  3. start with an empty table. It must *not* silently start empty and then overwrite the file.
- If =hooks.json= parses but yields zero hooks while the file is larger than a threshold that could not hold zero hooks (say 64 bytes), that is the same condition and takes the same path.

*Truncation is not corruption, and must not be treated as it.* =load= allocates a fixed 1 MB buffer and reads until it is full or a read returns ≤ 0, with no check that the whole file was consumed. A =hooks.json= larger than 1 MB is therefore delivered to the parser truncated mid-JSON, both parse attempts fail, and the rule above would rename a *perfectly valid registry* to =hooks.json.unparseable-<ms>= and start empty — turning a recoverable condition into the exact catastrophe the rule exists to prevent. So: =load= must =fstat= the file first and compare against the bytes read; if the file is larger than the buffer, log an error naming both sizes, *leave the file alone*, and refuse to start the hook daemon rather than starting it empty. The current ceiling is not remote — 16 hooks is ~3.8 kB, and nine new fields put the limit near 2,500 hooks.

Without this, any future field addition that misses a default silently destroys every registration on every store, and the operator's first sign is that nothing fires.

** States

Three states. The observable difference is one sentence: *a =quarantined= hook fires again on its own; a =disabled= hook never does until an operator says so.*

| State         | Polled?                            | Leaves by itself?           | How it is entered                                                         |
|---------------+------------------------------------+-----------------------------+---------------------------------------------------------------------------|
| =armed=       | every tick                         | —                           | default; any success; =hook enable=                                       |
| =quarantined= | only when =now >= next_attempt_at= | yes — one success → =armed= | =consecutive_failures= reaches K                                          |
| =disabled=    | *never*                            | *no*                        | TTL expiry; =hook disable=; =hook gc --yes=. *Never on daemon inference.* |

Two invariants, both of which a reviewer can check by reading the transition table alone:

- There is *no automatic transition from =quarantined= to =disabled=*, at any threshold. Hook #186 above is why.
- The only unattended transition into =disabled= is TTL expiry, and a TTL exists only because the registrant passed =--ttl=. Every other route into =disabled= passes through an operator command.

*** Skip ordering matters

The quarantine check must happen in =processHook= *before* the =fetch= / =fetchPatternByOffset= call, and disabled hooks must be skipped in =pollAndExecute= before =processHook= is entered. This is not a micro-optimisation: for a prefix/wildcard hook whose pattern matches nothing, that fetch is a walk of the whole log (=TopicManager.fetchPatternByOffset=, =topic.zig=). Skipping it turns a quarantined hook's cost from 2 scans/second into 1 scan/hour at the backoff ceiling, and a disabled hook's cost into zero.

The =cwd= guard is the exception and it is deliberately *not* in that group: it needs an event to guard, so it sits after the fetch. See [[#tick-ordering][Ordering inside the daemon tick]].

** Failure accounting and backoff

*** What counts as a failure

An attempt fails if any of:

- the child exited non-zero → =last_exit_status = code=, =last_error = "exit"=;
- the child was terminated by a signal *the daemon did not send* → =last_exit_status = -signal=, =last_error = "signal"=;
- the =cwd= guard refused to spawn → =last_exit_status= unchanged, =last_error = "cwd-missing"=;
- =fork=, =execve= setup or log-file creation failed → =last_error = "spawn-failed"=.

Hitting =MAX_CONCURRENT_HOOKS= is *not* a failure. It is backpressure, the cursor already does not advance, and counting it would quarantine healthy hooks during a burst.

*** <<counting>>How "consecutive" is counted, given that one hook can have 16 children in flight

This has to be pinned, because =processHook= loops over a batch of up to 100 fetched events and calls =executeHookCommand= for each, stopping only at the *global* =MAX_CONCURRENT_HOOKS = 16=. A single hook draining a backlog can therefore have 16 children running at once, and =reapChildren= collects them with =waitpid(-1, …, WNOHANG)= in whatever order the kernel offers.

- *Accounting happens at reap*, never at spawn. The outcome is not known until then.
- *=consecutive_failures= increments by at most 1 per hook per poll cycle*, however many of that hook's children were reaped in that cycle. The daemon records, per hook, the tick sequence number at which it last incremented, and skips the increment if it equals the current tick.
- *A success in a cycle wins over failures in the same cycle.* If any child of a hook reaped in a cycle exited 0, the counter resets to 0 and the state returns to =armed=, regardless of sibling failures. A hook that succeeded at all is not broken.
- *The quarantine gate is not a burst brake.* It is evaluated at the top of =processHook=, before the batch loop, so a hook failing on every event still spawns its whole in-flight batch before the K-th failure is observed. Quarantine takes effect from the *next* poll cycle. This is a deliberate limit: throttling mid-batch would require the daemon to block on reaps, which is what [[./hook-execution.org]] removed.

Two consequences worth stating because they are otherwise surprising:

1. Reaching K takes at least K poll cycles — 2.5 s at K = 5. Any acceptance criterion that drives a hook to quarantine must pace its events at least one poll interval (500 ms) apart; publishing five events at once produces one failure, not five.
2. The counter therefore doubles as a *clock*. Because failures 5 and up are separated by the backoff delay, =consecutive_failures >= 10= implies the hook has been failing continuously for at least 30+60+120+240+480 s = 15.5 minutes. [[#gc-rules][=gc='s reclamation rules]] use that instead of carrying a separate timestamp field.

This is the one place the change touches shared mutable state from two threads: the counters are mutated on the daemon thread at reap and read on a server thread by =hook list= / =gc=. They live in =HookTable=, whose mutex already covers =updateCursor= / =snapshot=, and the implementation must use it. Per the fleet rule, the resulting tests run under =-Doptimize=ReleaseFast= as well as debug.

*** <<signal-accounting>>Signal deaths must be decoded

=reapChildren= currently does =(status >> 8) & 0xFF=, which is 0 for a signal death. It must decode the full wait status: =WIFEXITED= → exit code; =WIFSIGNALED= → =-WTERMSIG=. Without this, a hook killed by a signal is recorded as a success.

*** <<daemon-signals>>Signals the daemon sent itself do not count as failures

The daemon kills its own children in three places — =checkTimeouts= at the hard-coded =DEFAULT_HOOK_TIMEOUT_SECS = 300=, =shutdownChildren= on store shutdown, and =killChildrenForHook=. If a decoded =SIGTERM=/=SIGKILL= counted as a failure, then:

- *any hook that legitimately runs longer than five minutes would quarantine for up to an hour*, on a timeout nobody opted into (the =--timeout= flag specified in [[./hook-execution.org]] never shipped; see the marker there). On the live store, =#11= and =#12= invoke =chronoa= and =#227= runs a crosstalk notify — all commands that can legitimately block on another agent. A notification path going quiet for an hour is exactly the silent-outage class round 4 exists to eliminate;
- a clean store shutdown would quarantine *every* hook that happened to be running.

So: *=ProcessEntry= gains =signalled_by_daemon: bool=, set when the daemon signals that entry.* At reap, a child that died from a signal with that flag set records =last_error = "timeout"= (or ="shutdown"=), does *not* increment =consecutive_failures=, and does not reset it either. The count is surfaced separately — =hook list= shows a =TIMEOUTS= tally — so the behaviour is visible rather than merely suppressed.

This is the correct answer only because the timeout is not per-hook. *If a per-hook =--timeout= is added later, a timeout on a hook that declared one should count*, because then the operator consented to the bound. That is a hand-off requirement, not a future nicety.

*** The curve, pinned

- =K = 5=. The fifth consecutive failure moves the hook to =quarantined=.
- =delay(n) = min(30s × 2^(n − K), 1h)= for =n = consecutive_failures=, giving 30 s, 1 m, 2 m, 4 m, 8 m, 16 m, 32 m, 1 h, 1 h, … from n = 5 onwards.
- Ceiling = 1 h, and it is a fixed point. A permanently broken hook costs 24 dispatch attempts per day forever — and, for a prefix hook, 24 full-log scans per day instead of 172,800. That is cheap enough that there is no case for escalating further, and escalating further is what would have killed hook #186.
- One success sets =consecutive_failures = 0=, =next_attempt_at = null=, =last_error = null=, and =state = armed=.
- =timeouts= (see [[#daemon-signals][above]]) is a separate counter and is never reset by a success; it is diagnostic only.

*** The cursor during quarantine

While a hook is quarantined and not yet due, its cursor does not advance, because no fetch and no dispatch happen. Matching events accumulate in the log and are delivered when the hook next attempts — oldest first. This is strictly better than today, where a dispatch that exits 127 still advances the cursor past the event.

When the attempt *does* come due, the batch is fetched and dispatched normally, and the cursor advances at spawn as it does today. So a permanently broken hook still consumes up to 100 events per hourly attempt and drops them. Changing that — retrying the same event rather than advancing past it — needs the attempted-versus-delivered cursor split that belongs to the repoint half, and this document deliberately does not introduce it. See [[#repoint-coupling][Coupling]].

The interaction to be aware of: a long-quarantined prefix hook resumes with a large backlog, drained 100 events per poll cycle and at most =MAX_CONCURRENT_HOOKS= (16) concurrently. That is a real burst, and it is the same burst =hook enable= faces — see [[#reversibility][Reversibility]].

** The =cwd= dispatch guard (the daemon's only static check)

After the batch is fetched and immediately before each fork, =stat(hook.cwd)=. If it returns =ENOENT=:

- do not fork;
- record the attempt as a failure with =last_error = "cwd-missing"=, subject to the once-per-cycle rule in [[#counting][How "consecutive" is counted]];
- advance the cursor exactly as a spawn would, because this sits exactly where the spawn would have been and has an event and an offset in hand;
- count toward quarantine like any other failure. *The guard never disables anything.*

This is sound: the dispatch string is =cd '<cwd>' && … exec <cmd>=, so a failed =cd= short-circuits before the command and the fork can only produce a shell that fails. Skipping it saves a fork/exec and, more importantly, gives the failure a *typed* reason in the record, which is what =gc= later reads as evidence.

Only =ENOENT= triggers the guard — =EACCES=, =EIO=, =ESTALE=, =ELOOP=, =ENOTDIR= and =ENAMETOOLONG= all mean "unknown", and the daemon forks anyway and lets the real outcome decide. An NFS mount that is down returns =ESTALE= or =EIO=, not =ENOENT=.

There is no corresponding guard for the command path. The command is a shell fragment (see [[#rejected-static][Rejected: stat the command path before spawning]]) and the only way to know whether it runs is to run it.

** <<why-gc-only>>Why the disable rules are not daemon rules

/[Superseded: 2026-08-03 — the first revision of this document made R1 and R2 *daemon* rules that moved a hook to =disabled= once =consecutive_failures= reached K. The round-4 spec review argued they should be =gc= candidate rules only. That argument is adopted, and this section records why, because "the reviewer said so" is not a reason a later implementer can evaluate.]/

The question is narrow: the daemon already caps a permanently-broken hook at 24 dispatch attempts per day via the backoff ceiling. Automatic disable takes that to zero. *What does the 24-to-0 step buy, and is it worth letting the daemon switch off a registration on its own inference?*

On this store, it buys almost nothing, and the document's own numbers say so:

- The census of 2026-08-03 contains *zero* hooks that R1 or R2 would fire on. The incident's 24 dead hooks were reclaimed by hand and have not recurred.
- The incident's actual cost driver — =#17=, =#19=, =#157=, =#158=, all at cursor 0 with patterns that never match — is out of reach of both rules under the daemon reading, because a hook that never fires never fails. So the automatic rules do not address the pathology that motivated the item; [[#scope-boundary][round-4 item 1]] does.
- 24 attempts/day is roughly one log file per hour per dead hook. Set against a 105,272-file, 476 MB =data/hooks/= at the time of the incident, that is not the term that matters.

Against that, the cost is concrete and was demonstrated by the review:

- *R2 is an inference, not a proof.* Its static half extracts a token heuristically from a shell fragment and its dynamic half reads an exit code from the past. Five of the seven absolute-path hooks on the live store belong to other fleets that redeploy their own scripts, and an =rm= + =cp= redeploy that overlaps one matching event produces =last_exit_status == 127= and =stat == ENOENT= *simultaneously and legitimately*. Under a daemon rule that is a silenced hook belonging to someone else; under a =gc= rule it is a line in a report that is gone by the time anyone reads it.
- *R1 is a proof, but only about a moment.* =stat(cwd) == ENOENT= proves the command did not run *this time*. It says nothing about whether the directory is coming back — and the workflow this document exists to serve is rig rebuilds, which round-3 calls routine and which are literally =rm -rf && mkdir=. A daemon rule needs a wall-clock guard to be safe; a =gc= rule gets one for free, because a human ran it.
- The blast radius is asymmetric. A dead hook left armed costs 24 forks a day. A working hook wrongly disabled is a silent outage on a neighbouring fleet, discovered when something does not happen.

So the division is: *the daemon may slow a hook down (quarantine, self-healing, reversible, bounded) and may honour a lifetime the registrant declared (TTL). Deciding that a hook is dead is an operator's judgement, and =gc --yes= is where it is exercised* — with the evidence printed immediately before.

What this gives up, stated plainly so it is not discovered later: *a store with no operator never reclaims anything it was not given a TTL for.* That is a real regression against the first revision, and the answer is that =--ttl= is the mechanism for unattended reclamation and it should be the default discipline for orchestration rigs. The registrant knows how long its run will last; the daemon never does. (Making =--ttl= a documented default in the ACE-stack skill is out of scope here and is noted for whoever owns that file.)

** R3 — expiry, the daemon's one unattended disable

If =expires_at != null= and =now >= expires_at=, set =state = disabled=, =disabled_reason = "expired"=, at poll time, before any fetch. Log *once*, at the transition — not once per tick. (The incident's 15 MB log is what one un-deduplicated per-tick log line looks like.)

This one is unattended because the registrant asked for it. Everything else the daemon can do to a hook is reversible without an operator.

No other automatic disable exists. In particular, no rule involving lag, cursor distance, age, =created_at=, topic emptiness, or failure *ratio* — see [[#rejected-ratio][Rejected: a failure ratio]].

** Expiry, and why this is a TTL and not a lease

The triage draft calls this "leasing the registration to the run that made it", and proposes =--ttl= / =--lease= as synonyms. They are not the same thing and the difference is load-bearing.

A *lease* is held against a liveness signal: the holder renews, and expiry means the holder is gone. A *TTL* is a wall clock. Ever has no way to observe whether the run that registered a hook is still alive — there is no owner field, no session handle, no heartbeat. Shipping a wall clock under the name "lease" invites exactly the failure the incident's own non-goal warns about: a long-running rig whose hooks vanish mid-run, silently, on a timer nobody remembers setting. Hook =#170= (=ace-stack.support.tick=) has been registered since at least April.

So: implement a TTL, call it a TTL, and make renewal explicit.

- =ever hook add --ttl <dur>= — parsed with the existing =timers.parseDuration= (=src/store/timers.zig=, accepts =s= / =m= / =h= / =d=, rejects =0= and bare integers). *=parseDuration= returns =u64= seconds and =expires_at= is epoch milliseconds*, so the store is =expires_at = getMilliTimestamp() + parseDuration(s) * 1000=. Getting this wrong makes =--ttl 1h= expire in 3.6 seconds, and the symptom looks like a broken acceptance criterion rather than a unit bug.
- =ever hook renew <id|name> [--ttl <dur>]= — sets =expires_at = now + dur=, or extends by the original TTL if =--ttl= is omitted. Refuses on a hook with no =expires_at= (a TTL is not something you can acquire by renewing).
- *No default TTL, ever.* Omitting =--ttl= means =expires_at = null=, which is today's behaviour.
- =--lease= is *not* provided as an alias. If a real lease is wanted later it needs an owner identity and a heartbeat, and it should not inherit this name.

** =ever hook gc=

*** Shape

#+begin_src bash
ever hook gc                              # report only; reclaims nothing; exit 0
ever hook gc --yes                        # disables R1/R2 candidates; never deletes
ever hook gc --include-quarantined --yes   # additionally disables hooks flagged under W1
ever hook gc --purge <id> [<id>…] --yes    # removes named, already-disabled hooks
#+end_src

=--dry-run= is accepted as an explicit synonym for the default, so scripts can state their intent. Running without =--yes= is always a dry run; there is no configuration that changes that.

*** <<gc-rules>>The reclamation rules

These are =gc='s rules. The daemon does not evaluate them; see [[#why-gc-only][Why the disable rules are not daemon rules]].

**** R1 — working directory absent

A hook is a *reclaimable* candidate under R1 when all of:

1. =state != "disabled"=; *and*
2. =stat(hook.cwd)= returns =ENOENT= — evaluated *now*, by =gc=, not read from the record. Any other =stat= error (=EACCES=, =EIO=, =ESTALE=, =ELOOP=, =ENOTDIR=, =ENAMETOOLONG=) disqualifies; *and*
3. either =consecutive_failures >= 10= with =last_error == "cwd-missing"=, *or* the hook has never dispatched at all (=last_exit_status == null= and =consecutive_failures == 0=).

Condition 3 is where the wall clock comes from, and it is why no timestamp field is needed. By the backoff curve, going from 5 failures to 10 costs 30+60+120+240+480 s, so *=consecutive_failures >= 10= means the =cwd= has been missing on every attempt for at least 15.5 minutes* — comfortably longer than an =rm -rf && mkdir= rig rebuild, and far shorter than the months hook =#20= spent broken. The once-per-poll-cycle increment rule in [[#counting][How "consecutive" is counted]] is what makes that inference valid; without it a burst could reach 10 in one tick.

The "never dispatched" branch exists because it is the only way to reclaim the incident's real cost driver. Hooks =#17=, =#19=, =#157= and =#158= sat at cursor 0 on patterns that never matched, so they never failed and never would. =gc= can still prove their =cwd= is gone, and an operator looking at the report can act. The daemon could not, and that is the substantive thing the daemon reading of R1 never bought.

**** R2 — command is a literal absolute path that is absent, and the last dispatch exited 127

Both halves are required, and the static half is deliberately narrow. A token qualifies only if:

- it is the first whitespace-delimited token of =hook.command=; *and*
- it begins with =/=; *and*
- it contains none of =$=, backtick, =*=, =?=, =[=, =~=, =\=, =:=, single or double quote.

A hook is a *reclaimable* candidate under R2 when its token qualifies, =stat(token) == ENOENT= evaluated now, =last_exit_status == 127=, and =consecutive_failures >= 10=. A qualifying token that is absent on a hook that has *never* dispatched goes to the *flagged* section instead, not the reclaimable one: without an observed 127 the conjunction is incomplete, and the whole value of R2 is that it is a conjunction.

Why both halves:

- *The static half alone is unsound.* Of the 16 hooks on the live store on 2026-08-03, *9 have a first token that is not a path*: =sh= (×5), =echo= (×2), =chronoa= (×2). A rule that stats the first token and disables on failure would switch off 56% of a working store, including hooks belonging to four other fleets. It is also blind to an autofs path, which can return =ENOENT= to =stat= and still resolve when the shell execs it.
- *The exit-127 half alone is unsound.* 127 is also what a script returns when it deliberately exits 127, or when a command *inside* the script is not found. Requiring the path to be absent as well makes the conjunction provable.
- *Neither half is stable across a redeploy.* Five of the seven absolute-path hooks on the live store belong to fleets that rewrite their own scripts. An =rm= + =cp= redeploy of =/home/ryota/.local/state/acefix/log-event.sh= that overlaps a matching event produces a genuine 127 *and* a genuine =ENOENT= at the same instant. That is why the =consecutive_failures >= 10= floor is required here too, and why the action needs an operator: a redeploy cannot keep failing for 15 minutes without someone noticing for other reasons.

**** W1 — flagged, never reclaimed by =--yes= alone

=state == "quarantined"= and =consecutive_failures >= 20=, or an R2 token match on a hook that has never dispatched. Reported, never acted on without =--include-quarantined=.

*** Output, in two sections

#+begin_example
RECLAIMABLE (2)
  #31  air.old.        /tmp/ever-orch/notify.sh    cwd-missing       cwd ENOENT: /tmp/ever-orch
       last exit 1, 12 consecutive failures, last attempt 2026-08-01T09:14:02Z
  #44  build.done      /tmp/rig/deploy.sh          command-missing   stat ENOENT: /tmp/rig/deploy.sh, last exit 127
       last exit 127, 5 consecutive failures, last attempt 2026-08-02T22:03:11Z

FLAGGED FOR REVIEW (1) — not reclaimed by --yes
  #186 chronoafix.     /home/ryota/.local/state/acefix-chronoafix/notify-orch.sh   quarantined
       139 consecutive failures, last exit 1, command and cwd both present
       (requires --include-quarantined; a hook in this section may be healthy)

2 reclaimable, 1 flagged, 0 reclaimed (dry run; pass --yes to act)
#+end_example

Rules:

- The *reclaimable* section contains only R1 and R2 matches. Every line carries the rule name and the evidence that proves it — the path that returned =ENOENT=, the recorded =last_exit_status=, and the failure count that supplies the 15-minute floor. Expired hooks are not listed: the daemon has already disabled them and there is nothing for =gc= to decide.
- The *flagged* section contains W1 and nothing else. It is informational. =--yes= alone does not touch it.
- A hook that is =armed= with =consecutive_failures == 0= appears in neither section, except under R1's "never dispatched" branch — which requires =gc= to have just proved its =cwd= gone. A working hook whose =cwd= exists is not a candidate under any rule.
- Lag is *not* printed by =gc= at all, to remove the temptation to act on it. It belongs in =hook list=, which is =ever--hook-scan-cursor-and-lag='s surface.
- All paths are printed *exactly as stored*. No =~= abbreviation, no =$HOME= substitution: the evidence line has to be something a reviewer can paste into =stat=, and R2's own qualification test disqualifies any token containing =~=.

*** <<purge>>=--purge= takes explicit ids, and only ids

/[Superseded: 2026-08-03 — the first revision spelled this =gc --purge --state disabled --yes=, a state filter with no target, which on this store would delete *every* disabled hook across six fleets in one command. The state filter is withdrawn.]/

=ever hook gc --purge <id> [<id>…] --yes= removes the named hooks. It refuses — non-zero exit, nothing changed, not even partially — if *any* named hook:

- is not =disabled=; or
- has been =disabled= for less than one hour by =disabled_at= (printed, so the operator can see how long is left); or
- does not exist.

There is no bulk form, no =--all=, and no state selector. Removal is irreversible and irreversible operations get typed-out ids.

In dry-run mode =--purge <id>…= prints one line per named hook — id, name, pattern, command as stored, =disabled_reason=, =disabled_at= and its age — followed by =N would be removed, 0 removed (dry run; pass --yes to act)=. A hook that fails one of the preconditions is printed with the reason it would be refused, and the dry run exits non-zero so a script notices.

*** The one-step invariant

*No single command takes a hook from =armed= to removed.* Removal requires the hook to be =disabled= already, and to have been =disabled= for an hour. =ever hook rm <id>= keeps its current behaviour: it is explicit, single-target, and already exists — this document does not add a precondition to it.

*** Why =--purge= exists at all

Because [[#downgrade][downgrade re-arms everything]]. Disabling is not durable against a rollback of the store binary; removal is. An operator who has decided a hook is dead and expects to roll back needs a reclamation that survives.

** Reversibility <<reversibility>>

*** =ever hook enable <id|name>=

Sets =state = armed=, =consecutive_failures = 0=, =next_attempt_at = null=, =last_error = null=, =disabled_at = null=, =disabled_reason = null=.

=expires_at= is handled by cases, *not* cleared unconditionally:

| Was disabled by           | =expires_at= after =enable=                                                        |
|---------------------------+------------------------------------------------------------------------------------|
| =expired=                 | cleared, unless =--ttl= given — re-arming into an instant re-expiry is a trap      |
| anything else, TTL future | *preserved unchanged* — the registrant's bound survives an unrelated disable       |
| anything else, TTL past   | *refuse*: print the stored =expires_at= and require =--ttl <dur>= or =--clear-ttl= |

/[Superseded: 2026-08-03 — the first revision cleared =expires_at= on every =enable=. That is right for the expiry case and wrong everywhere else: a rig that registered =--ttl 8h= (exactly the discipline this document argues for) would have its bound silently removed by an operator disabling and re-enabling the hook for an unrelated reason, turning a bounded registration into the immortal debris the document exists to prevent — via the document's own recovery command.]/

=ever hook disable <id|name>= is the inverse, with =disabled_reason = "operator"=. It does not touch =expires_at=.

*** What "with its cursor" actually means

The cursor is *not touched* by disable, by expiry, by quarantine, or by enable. Concretely, for an event published while the hook was disabled:

- The event is still in the log — Ever never deletes it on a hook's account.
- On =enable=, the hook resumes from its stored cursor, so *that event is delivered*, along with every other matching event since. Delivery is bounded at 100 events per poll cycle and 16 concurrent children.
- This can be a large burst. =ever hook enable= therefore *prints a bound on the backlog before acting*, and accepts =--from tail= to skip it and resume at the head instead. For an exact-topic hook the number is exact: =non_marker_count − cursor=. For a prefix/wildcard hook it is =nextOffset() − cursor=, which counts *unscanned log entries across all topics*, not matching events — on this store the log holds ~116,700 events across dozens of topics while a given prefix hook matches a small fraction. It must therefore be printed as an upper bound (=up to N events pending=), and the wording must not imply the hook will fire N times. Computing the exact figure would mean the full-log scan this whole document is trying to avoid.
- Default is to replay, because the stated non-goal is that nothing is lost silently. =--from tail= is the explicit opt-out, and it reuses the vocabulary =hook add= already has.

One consequence worth stating plainly rather than discovering: re-enabling a long-disabled prefix/wildcard hook restores its contribution to the full-log rescan until it catches up. On a store without round-4 item 1's fix, that is the incident's pathology re-armed on purpose. =enable= should say so in its output when the pending count is large.

Verified 2026-08-03 at =142d5e66=, *after* the zig-cli-kit migration (=src/main.zig=, the =hook= command's =subcommands= array). The triage draft's closing line was written before that migration; it still holds, and the details are:

This document adds =gc=, =enable=, =disable=, =renew=, and =--ttl= on =add=. =hook list= gains a =STATE= column and a =TIMEOUTS= tally; for =quarantined= the state column shows the time until the next attempt, for =disabled= it shows the reason. That column is the primary observable distinguishing the two states.

Wire protocol: four new request/response pairs. The last opcodes in use are =hook_logs = 0x0F= and =hook_logs_ok = 0x8F= (=src/protocol/message.zig=), so the new pairs are *=0x10–0x13= / =0x90–0x93=*, in the order =hook_gc=, =hook_enable=, =hook_disable=, =hook_renew=. The new-client half is *not* free: =protocol.HookInfo= (=message.zig:144=) must gain the same eight fields with the same defaults, or a new client talking to an older store fails to decode a response that legitimately omits them. See [[#record-fields][Record format]].

** <<reason-strings>>Reason strings

Fixed vocabulary, so that scripts and reviewers can match on them.

=disabled_reason=: =expired= (daemon), =operator= (=hook disable=), =gc-cwd-missing=, =gc-command-missing=, =gc-quarantined= (all =gc --yes=). The =gc-= prefix is not decoration — it is how a reader tells at a glance that a human consented, which after the [[#why-gc-only][daemon/operator split]] is the distinction that matters.

=last_error=: =exit=, =signal=, =cwd-missing=, =spawn-failed=, =timeout=, =shutdown=. The last two do not increment =consecutive_failures= (see [[#daemon-signals][Signals the daemon sent itself]]).

** <<downgrade>>Downgrade

Measured, not assumed. An older binary reading a file written by the new one:

1. parses successfully (=ignore_unknown_fields = true=);
2. ignores =state=, =expires_at=, =consecutive_failures= and the rest;
3. polls *every* hook, including the disabled ones, because it has no concept of state;
4. rewrites =hooks.json= without those fields on the first cursor update — measured to happen within one poll cycle of the first matching event.

Every disabled hook re-arms, every TTL is erased, and the failure history is gone. There is no way to prevent this from the new binary's side, because the old binary does not check a version field. What this document can do, and does:

- write =version: 2= so a *future* reader can detect the round trip;
- make =ever hook gc= (report mode) the documented pre-downgrade step, since its output is the only record of what was disabled and why;
- provide =--purge=, because removal is the only reclamation a downgrade cannot undo.

This must be stated in the release notes for the change. A downgrade is one-way and lossy.

* Design Details

** <<rejected-static>>Rejected: stat the command path before spawning

The triage draft proposes "on dispatch, stat the resolved command first: unrunnable means record the failure and disable rather than spawn-and-fail". Rejected as the *sole* criterion, for the reasons in [[#gc-rules][R2]]: =hook.command= is a shell fragment, 9 of 16 live hooks have a non-path first token, and =stat= disagrees with =execve= for autofs and for anything reached through =PATH=. The static check survives as one half of a conjunction evaluated by =gc=, never on its own and never in the daemon.

The =cwd= check *is* done before spawning, because =cwd= is a stored absolute path with exactly one consumer and no ambiguity — but it only records a failure, it does not disable.

** Rejected: reaping on lag

Covered under Non-Goals; the structural reason (polymorphic cursor) is worth repeating here because it is not obvious from the draft: comparing =Hook.cursor= to the log head is only meaningful for prefix/wildcard hooks. For an exact-topic hook the cursor is a per-topic skip count and the comparison is a category error. Any implementation tempted to add "lag" to the GC input set should be sent back to =hooks.zig='s =Hook.cursor= doc comment.

** <<rejected-ratio>>Rejected: a failure *ratio*

Hook #186 failed 139 times consecutively and then succeeded on a run of comparable length without intervention. A ratio computed over any window containing both is meaningless, and a ratio computed over the failure run alone is 100%. Consecutive count, reset on success, is the only accounting that distinguishes "broken" from "flaky" — and the reset is what makes it self-healing.

** <<tick-ordering>>Ordering inside the daemon tick

/[Superseded: 2026-08-03 — the first revision listed the =cwd= check as step 4 of five and asserted "steps 1–4 must all precede the fetch" and "step 4 is per-tick, not per-event". Those are mutually inconsistent: before the fetch there is no event and no offset, so "advance the cursor exactly as a spawn would" had no defined value, and the only per-tick advance available for a prefix hook is =nextOffset()=, which would consume the entire backlog on the first tick after a =cwd= vanished. Resolved below in favour of *per-event, after the fetch*.]/

=daemonLoop= gains no new phase. Inside =pollAndExecute=, per hook, in order:

1. =state == "disabled"= → skip. *No fetch.*
2. =expires_at= reached → transition to =disabled=, log once, skip. *No fetch.*
3. =next_attempt_at= in the future → skip. *No fetch.*
4. *Fetch* the batch (up to 100 events).
5. For each event in the batch, immediately before the fork: =stat(cwd)=. On =ENOENT=, record the failure (once per cycle, per [[#counting][the counting rule]]), advance the cursor as a spawn would, and move to the next event. Otherwise fork as today.

Steps 1–3 precede the fetch, and that is what criterion 14 and the "move the quarantine check after the fetch" mutation check both test. *Step 5 is per-event and necessarily follows the fetch*, because it stands exactly where the fork stands and needs the same event and offset the fork would have had.

The consequence, stated because it bounds the damage: a hook whose =cwd= disappears loses *at most one batch of events per poll cycle* and *contributes at most one failure per cycle*, so it reaches K in K cycles, exactly like any other failing hook. It does not accumulate failures without matching events, and it does not consume a backlog it never fetched. Both of those were true under the withdrawn per-tick reading.

** Persistence pressure

=HookTable.saveLocked= rewrites the whole file on every mutation, and =updateCursor= already calls it per delivered event. Failure accounting adds writes on the failure path. This is not a new problem and this document does not solve it, but the implementation must not add a save per *tick* — only per state transition and per delivered event, as today.

** <<scope-boundary>>What this does not fix

The incident's CPU burn came from =fetchPatternByOffset= walking the whole log for hooks whose pattern never matches. This document reduces that cost only as a side effect: a disabled hook is not polled, and a quarantined one is polled hourly instead of twice a second. But:

- a hook that *never fires* can never accumulate failures, so *no daemon mechanism here will ever quarantine or disable it*. It is reclaimable only by TTL, or by an operator running =gc=. The incident's most expensive hooks by scan lag (=#17=, =#19=, =#157=, =#158=, all at cursor 0) were in exactly that category — and R1's "never dispatched" branch is specifically there so that =gc= can still prove their =cwd= is gone and offer them to an operator. That branch is the one place this document reaches the incident's actual cost driver, and it reaches it only through a human.
- the reduction depends on someone having run =gc --yes=, or on a TTL having been set at registration. There is no unattended path from "dead" to "not polled".

The general fix is =ever--hook-scan-cursor-and-lag= (round-4 item 1: advance the cursor on scan). The two are complementary and neither substitutes for the other. Do not justify this document with the 2,004,113-events-per-cycle figure; that number belongs to item 1.

* <<repoint-coupling>>Coupling with =ever--hook-repoint-and-resilience=

The triage draft says to land this with round-3's =ever--hook-repoint-and-resilience.org= — "or the repoint path has nothing to repoint from". *That document is not scheduled in this batch and will not be implemented alongside this one.* This design therefore stands alone. What that costs, precisely:

** Already landed from that draft

Its third goal — a =--from tail= default so "follow new events only" is a declaration rather than offset arithmetic — *shipped*. At this base, =ever hook add= with neither =--from= nor =--from-beginning= sends =start_cursor = null= and the server resolves the tip under the publish lock (=main.zig= =handleHookAdd=; =air/v0.1/hook-registration-cursor.org=, History 2026-04-21 and 2026-04-28). Only the first two goals remain open.

** What is degraded without the repoint half

1. *A disabled hook can only come back at its original command.* There is no =hook update=, so a hook whose script moved must be removed and re-added, which loses the cursor (a new registration starts at the tip). =enable= restores the registration, not a corrected one.
2. *Events arriving while a hook is broken are still lost.* The =cwd= guard advances the cursor without spawning, matching what a spawn that exits 127 does today. The alternative — freezing the cursor — is the time bomb round-3 names explicitly: the moment the script returns, the hook replays the whole backlog. Round-3's answer is a separate "attempted" cursor, and that is the repoint half's design to make. *Reversible in this document means the registration comes back, not the missed events.* Quarantine is a partial exception: while a quarantined hook is not yet due it fetches nothing and its cursor stands still, so events in that window are deferred rather than dropped — but the attempt that ends the window still advances the cursor over its batch whether or not the dispatch worked.
3. *No "skip and warn" on a missing command.* This document's answer is a =gc= report plus an operator's =--yes=, which is slower than skip-and-warn and needs a human. A store that wants the hook to keep itself alive across a script's disappearance needs round-3.

** What a later repoint implementation must inherit from this design

Three requirements, stated so that whoever implements repoint does not have to reverse-engineer them:

1. A successful =hook update= must set =state = armed=, =consecutive_failures = 0=, =next_attempt_at = null=, =last_error = null=, =disabled_reason = null=. Otherwise a repointed hook stays quarantined or disabled and the repoint appears to do nothing.
2. If repoint introduces a separate "attempted" cursor, failure accounting must key on *delivery* outcomes only. Counting both an attempt and its delivery would double the effective K.
3. =state= is a string with unknown values tolerated (treated as =armed=, logged once). Repoint may add its own state without a coordinated release.
4. If repoint adds a per-hook =--timeout=, a kill originating in =checkTimeouts= must start counting as a failure *for hooks that declared one*, because the bound was then consented to. Hooks with no declared timeout keep the exclusion in [[#daemon-signals][Signals the daemon sent itself]].

** =once= hooks

=hook.once= predates all of this and interacts badly with every new state, so the interaction is specified rather than left to be discovered. In shipped code, =processHook= calls =hook_table.remove(hook.id)= immediately after the *spawn*, before any outcome is known. So a =once= hook that fails is deleted anyway, and can be neither quarantined, nor disabled, nor recovered.

That is the one place where this document's headline — "nothing is deleted automatically, ever" — is already false in shipped code, and it is false in a way this document does not fix. The rules:

- A =once= hook *can* carry a TTL, and expiry disables it before it ever fires. That is the only reclamation that reaches it.
- The =cwd= guard applies: if =cwd= is =ENOENT=, no fork happens — and because the removal is coupled to the spawn, *the hook is not removed either*. It records a failure and stays registered, so a =once= hook is the one case where the guard also prevents a silent self-deletion.
- A =once= hook cannot reach K by dispatching, because it is gone after the first dispatch. It can reach K through the =cwd= guard.
- =gc= treats a =once= hook exactly like any other: R1 can reclaim it, R2 effectively cannot (it never survives a dispatch to record a 127).
- Making removal-on-success rather than removal-on-spawn is a behaviour change this document does not make. It belongs with the attempted-versus-delivered cursor split. Flagged here so it is not silently inherited as acceptable.

* Acceptance

Each criterion is checkable from this document alone, against a store built from the change, with no access to the author. "Isolated store" means a store started with its own =--data-dir= and a port other than 7890.

*Pacing convention, which several criteria depend on.* Because =consecutive_failures= increments at most once per hook per poll cycle ([[#counting][How "consecutive" is counted]]), any criterion that says "drive the hook to N failures" means *N matching events published at least one poll interval (500 ms) apart*. Publishing N events at once produces *one* failure, not N — the hook spawns the whole batch before the first reap. Where a criterion below says "5 paced events" this is what it means, and a criterion that publishes them together is testing something else.

** Migration and durability

1. *No-op on an existing store.* Take a =hooks.json= written by the pre-change binary containing at least three hooks with different =cursor= values. Start the new binary against it. =ever hook list= reports the same number of hooks, the same ids, names, patterns, commands and cursors, and every hook shows state =armed=.
2. *Round trip.* After (1), publish one event matching one hook so a save occurs. Re-read =hooks.json=: every row now carries =state="armed"=, =consecutive_failures=0=, =last_exit_status=null=, =expires_at=null=, and the file carries =version: 2=. No pre-existing field changed except =cursor=.
3. *Disabled survives restart.* Disable a hook (=ever hook disable <id>=), stop the store, start it again. =hook list= shows it =disabled= with the same =disabled_reason=, and publishing a matching event produces no new file under =data/hooks/= and no new process in =hook ps=.
4. *Quarantine survives restart.* Drive a hook to =quarantined= (below), stop and start the store, and confirm =consecutive_failures= and =next_attempt_at= are unchanged in =hook list= and in =hooks.json=.
5. *Unparseable file is not destroyed.* Corrupt =hooks.json= (delete one required key from one row). Start the store. It logs an error naming the file, renames it to =hooks.json.unparseable-<ms>=, and starts empty. Registering a new hook does *not* overwrite the renamed file. *This criterion regresses today: at =142d5e66= the same input silently takes 7 hooks to 0, logs nothing, and the next registration rewrites the file with =next_id= reset to 1.*
6. *Unknown state is loud and safe.* Hand-edit one row to =state: "future-state"=. On start the store logs a warning naming that hook id and the value, and the hook behaves as =armed=.
   - *6a — Oversize is not corruption.* Generate a valid =hooks.json= larger than 1 MB (roughly 2,600 hooks at nine new fields, or pad one =command= string). Start the store. It logs an error naming the file size and the buffer size, does *not* rename the file, and does not start the hook daemon with a partial table. Distinguishing this from criterion 5 is the point: the two inputs are both "parse failed" and must take different paths.
   - *6b — =HookInfo= tolerates omission.* Build a client from the change and point it at a store built before it (or hand-craft a =list_hooks_ok= body omitting all nine new fields). =ever hook list= renders every hook with state =armed= and zeroed counters rather than failing to decode.

** Backoff and quarantine

7. *K is 5.* A hook whose command exits 1 every time (command and =cwd= both present), driven by 5 *paced* events, is =armed= after 4 and =quarantined= on the 5th. =hook list= shows =quarantined= and a next-attempt time about 30 s out.
   - *7a — A batch is one failure, not many.* Publish 5 matching events *simultaneously* to the same always-failing hook. All 5 spawn (5 new files under =data/hooks/=), and =consecutive_failures= afterwards is *1*, not 5. The hook is still =armed=. This is the criterion that pins the counting rule; without it an implementer is free to choose either semantics.
   - *7b — A success in the batch wins.* Point a hook at a command that exits 0 on even offsets and 1 on odd ones, and publish 4 events together. After the batch is reaped, =consecutive_failures= is 0 and the state is =armed=.
8. *The curve.* From =quarantined=, successive failures produce next-attempt gaps of approximately 30 s, 1 m, 2 m, 4 m, 8 m, 16 m, 32 m, 1 h, and then 1 h indefinitely. Checkable from =next_attempt_at= in =hooks.json= without waiting out the whole curve.
9. *Quarantine never becomes disable.* Leave a hook failing for at least 200 consecutive dispatches. It is still =quarantined=. No amount of failure moves it to =disabled= on its own.
10. *Self-healing.* Repair the failing command so it exits 0. Without any operator command, the hook fires at its next scheduled attempt, and afterwards =hook list= shows =armed= with =consecutive_failures= 0.
11. *Observable difference.* With one hook =quarantined= and one =disabled=, both with working commands, publish matching events and wait past the quarantined hook's next-attempt time. The quarantined hook fires; the disabled hook does not. This is the whole distinction.
12. *Signal deaths count.* A hook whose command kills itself with =SIGKILL=, driven by 5 paced events, reaches =quarantined=, and =last_exit_status= is =-9=. *This regresses today: at =142d5e66= such a dispatch produces no log line at all, because =(status >> 8) & 0xFF= is 0 for a signal death.*
   - *12a — The daemon's own kills do not.* A hook whose command sleeps 310 s is killed by =checkTimeouts= at 300 s. After 5 such dispatches it is still =armed=, =consecutive_failures= is 0, =last_error= is ="timeout"=, and =hook list= shows a =TIMEOUTS= tally of 5. *Without this exclusion the same fixture quarantines, which would take any hook that legitimately runs over five minutes off the air for an hour on a timeout nobody opted into.*
   - *12b — Shutdown does not quarantine the store.* Start three long-running hooks, stop the store while they run, start it again. All three are =armed= with =consecutive_failures= 0.
13. *Backpressure is not failure.* Saturate =MAX_CONCURRENT_HOOKS= with long-running hooks and let another hook's events be deferred. That hook's =consecutive_failures= stays 0.
14. *A quarantined hook does not scan.* On a store with a large log and *no other hooks registered*, quarantine one prefix hook at a 1 h next-attempt and compare the store's read-syscall rate against its idle baseline with no hooks at all. The two must not differ. (=/proc/$PID/io= =syscr= is process-wide and the store also reads for TCP/HTTP work, so the criterion is "no increase over an idle baseline", not "zero".) Measurable without =strace=, as in the incident's notes:

#+begin_src bash
a=$(awk '/^syscr/{print $2}' /proc/$PID/io); sleep 3
b=$(awk '/^syscr/{print $2}' /proc/$PID/io); echo $(( (b-a)/3 ))
#+end_src

** The =cwd= guard, and the limits of automatic action

15. *The guard does not fork, and does not disable.* Register a hook from a directory, delete the directory, publish 5 paced matching events. No child process is spawned for any of the 5 (nothing new appears under =data/hooks/=), =last_error= is ="cwd-missing"=, =consecutive_failures= is 5, and the hook is *=quarantined=, not =disabled=*. *This is the criterion that pins the daemon/operator split: an implementation that disables here has re-introduced the withdrawn design.*
   - *15a — The guard is per-event, not per-tick.* With the same hook, publish nothing at all for 10 poll cycles after deleting the directory. =consecutive_failures= stays at its previous value — a hook with no matching events accumulates no failures, however long its =cwd= has been gone.
   - *15b — The guard bounds cursor loss.* With the same hook, note the cursor, publish 3 paced events, and confirm the cursor advanced by exactly 3 event-positions — not to the log head.
16. *No unattended disable of any kind, on any evidence.* Take the strongest possible case: a hook whose command is an absolute path to a deleted script, whose =cwd= is also deleted, driven by 200 paced events. It ends =quarantined= at the 1 h ceiling. *No store-side mechanism moves it to =disabled=.* Only =gc --yes= does. Run the whole of the rest of this section against a store on which =gc= has never been invoked and nothing is ever disabled except by TTL.
17. *No static-only disable.* Register hooks with commands =echo hi=, =sh -c 'exit 0'= and =true= (any command resolved through =PATH= and present on any POSIX host — do not use a fixture that needs the ACE stack installed). None is ever disabled, none is quarantined while it exits 0, and none appears in =gc='s reclaimable section. *A rule that stats the first token would flag 9 of the 16 hooks on the reference census below.*
18. *Only ENOENT.* A hook whose command path exists but is not executable exits 126; it is =quarantined=, and =gc= does not list it as reclaimable. A hook whose =cwd= is unreadable due to permissions on a parent directory (=EACCES= from =stat=) is forked normally — the guard does not trigger — and =gc= does not list it.
19. *Expiry disables, does not delete.* =ever hook add --ttl 30s <pattern> -- <cmd>=; after 30 s the hook is =disabled= with reason =expired=, still present in =hook list=, and the store logged the expiry *exactly once* (not once per 500 ms tick).
   - *19a — =--ttl= is in the right unit.* =ever hook add --ttl 1h= produces an =expires_at= about 3,600,000 ms in the future, not 3,600. Stated as its own criterion because =timers.parseDuration= returns *seconds* and =expires_at= is *epoch milliseconds*, and the 1000× error presents as "the TTL criterion is flaky" rather than as a unit bug.
20. *No default TTL.* A hook added without =--ttl= has =expires_at: null= in =hooks.json= and is never expired.
21. *Renew.* =ever hook renew <id> --ttl 1h= on a hook with a TTL moves =expires_at= forward by about an hour. =ever hook renew <id>= on a hook with no =expires_at= fails with a non-zero exit and changes nothing.
22. *Lag is never an input.* A hook whose cursor is millions of events behind the head, whose command and =cwd= both exist and which has never failed, is =armed=, is not listed as reclaimable by =gc=, and is not flagged.

** =hook gc=

23. *Dry run is the default and is inert.* On any store, run =ever hook gc= twice. Both invocations print byte-identical output, exit 0, and leave =hooks.json='s mtime and contents unchanged.
24. *Evidence is printed, and it is pasteable.* Every line in the RECLAIMABLE section names the rule (=cwd-missing= / =command-missing=) and the concrete evidence — the path that returned =ENOENT=, the recorded =last_exit_status=, the failure count. Every path is printed *exactly as stored*, with no =~= abbreviation, so a reviewer can paste it straight into =stat= and get the same answer.
25. *The 15-minute floor.* A hook whose =cwd= was deleted 4 paced events ago (=consecutive_failures= 4, still =armed=) is *not* reclaimable. Drive it to 10 and it is. *A hook whose directory is deleted and recreated before the 10th failure ends =armed= and never appears in the reclaimable section* — this is the =rm -rf && mkdir= rig-rebuild case, and it is the criterion that distinguishes this design from one that acts on a single observation.
   - *25a — R2 needs the observed 127, not just the missing path.* Register a hook whose command is an absolute path to a script and delete the script *before any event matches*. =gc= lists it under FLAGGED FOR REVIEW, never RECLAIMABLE, because =last_exit_status= is null. Now drive it to 10 paced failures: it moves to RECLAIMABLE. Separately, a hook whose script *exists* and exits 127 deliberately, at 10 failures, appears in neither section.
   - *25b — Never-dispatched =cwd= reclamation.* Register a hook on a pattern nothing will ever match, delete its directory, and let it sit. It never fails and never quarantines (criterion 15a). =gc= nevertheless lists it as reclaimable under R1's never-dispatched branch, and =gc --yes= disables it. *This is the only mechanism in the document that reaches the incident's =#17/#19/#157/#158= class.*
26. *Quarantined is flagged, not reclaimed.* With a hook at 139 consecutive failures whose command and =cwd= both exist: =gc= lists it under FLAGGED FOR REVIEW; =gc --yes= does not touch it; =gc --include-quarantined --yes= disables it.
   - *26a — Working hooks are never candidates.* On the reference census below — 16 hooks, none with a missing =cwd=, none with a missing absolute command path, none with a TTL — =ever hook gc= reports *zero* entries in the RECLAIMABLE section.
27. *=--purge= needs typed-out ids.* =ever hook gc --purge --yes= with no ids refuses and changes nothing; there is no =--all= and no state selector. =--purge <id> --yes= naming an =armed= or =quarantined= hook refuses *the whole invocation* and changes nothing, even if other named ids would qualify.
   - *27a — =--purge= needs the hook to have been disabled for an hour.* =--purge <id> --yes= on a hook disabled 5 minutes ago refuses, prints =disabled_at= and the remaining wait, and exits non-zero. The same command an hour later succeeds.
   - *27b — =--purge= dry-runs.* =ever hook gc --purge <id>= without =--yes= prints the hook's id, name, pattern, command as stored, =disabled_reason=, =disabled_at= and its age, says =1 would be removed, 0 removed=, and leaves =hooks.json= byte-identical.
28. *=--yes= only disables.* After =ever hook gc --yes= on a store with reclaimable candidates, the hook count in =hook list= is unchanged; only states changed. The =disabled_reason= values begin with =gc-=, distinguishing them from =expired= and =operator=.

** Reversibility

29. *Enable restores the registration and the cursor.* Disable an *exact-topic* hook. Publish 3 matching events. Run =ever hook enable <id>=. It prints =3 events pending= before acting, and the hook then fires for all 3, oldest first, producing 3 new files under =data/hooks/=. The hook must be exact-topic: for a prefix/wildcard hook the printed figure is =nextOffset() − cursor=, an upper bound over *all* topics, and it equals 3 only on an otherwise idle store.
   - *29a — The prefix bound is labelled as a bound.* Repeat with a prefix hook on a store carrying unrelated traffic. The output says =up to N events pending= and N exceeds the number the hook actually fires for. A criterion asserting equality here would be wrong.
30. *=--from tail= opts out.* Repeat (29) with =ever hook enable <id> --from tail=. The pending count is still printed, no historical event fires, and the next event published *after* the command does fire.
31. *Enable clears the failure counters.* After (29), =hook list= shows the hook =armed= with =consecutive_failures= 0, no =next_attempt_at= and no =disabled_reason=.
   - *31a — Enable preserves a live TTL.* Register with =--ttl 8h=, =ever hook disable <id>=, then =ever hook enable <id>=. =expires_at= is *unchanged* — still about 8 h out, not null. *An implementation that clears it has converted a bounded registration into a permanent one via the recovery command, which is the debris class this document exists to prevent.*
   - *31b — Enable refuses a stale TTL.* Register with =--ttl 30s=, =hook disable= it before expiry, wait past the 30 s, then =hook enable=. The command *refuses*, prints the stored =expires_at=, and requires =--ttl <dur>= or =--clear-ttl=. Neither of those two forms refuses.
32. *Enable after expiry clears the TTL.* Let a =--ttl 30s= hook expire on its own, then =hook enable= it: it is =armed= with =expires_at: null=, and it does not immediately re-expire. Contrast with 31a — the two cases must behave differently, and that difference is the whole of M6.

* Test plan

Test discipline required by the fleet: prove each regression test fails against the pre-change source before it passes, and mutate each guard independently.

** Unit (=src/store/hooks.zig=)

1. =HookJson= defaults: parse a fixture with no new fields → all defaults as specified.
2. =HookFileJson= with =version= absent → loads; with =version: 2= → loads.
3. Backoff arithmetic: table-driven over =n = 5..15=, asserting the exact millisecond delays and the 1 h clamp.
4. Wait-status decoding: =WIFEXITED= codes 0/1/126/127 and =WIFSIGNALED= 9/15 map to =last_exit_status= 0/1/126/127/−9/−15. *Must fail against the current =(status >> 8) & 0xFF=.*
5. R2 token qualification: a table of command strings — =/abs/path.sh=, =./rel.sh=, =echo hi=, =$HOME/x.sh=, =~/x.sh=, =sh -c '…'=, =/abs/path.sh | tee /tmp/x=, =/abs/with space/x.sh= — asserting which qualify. Only the first and the pipe form qualify.
6. State transitions: armed→quarantined at K, quarantined→armed on success, quarantined stays quarantined at 500 failures, disabled never leaves without an explicit call.
7. TTL unit arithmetic: =--ttl 1h= → =expires_at − now ≈ 3_600_000=, not 3_600.
8. Counting: a simulated reap sequence for one hook of (fail, fail, fail) within one tick increments by 1; (fail, success, fail) within one tick leaves the counter at 0; the same three failures across three ticks increment by 3.
9. =gc= candidate classification: a table of synthetic records — =(state, consecutive_failures, last_error, last_exit_status, cwd exists, token qualifies, token exists)= → =reclaimable(R1) / reclaimable(R2) / flagged / none=. This is where the 10-failure floor and the never-dispatched branches are pinned.

** Integration (=src/tests/integration.zig=)

10. Criteria 1–6b (migration), driven against a temp data dir. 6a needs a generated oversize file.
11. Criteria 15–18 (the guard and its limits), each with its own hook so a mutation that breaks one rule fails a disjoint test.
12. Criteria 19–21 (TTL), using short durations.
13. Criteria 24–28 (=gc=), including the 15-minute floor (25) driven by an accelerated backoff constant if the test build allows one — otherwise by writing =consecutive_failures= directly into a fixture =hooks.json= before start, which is legitimate here because the criterion is about =gc='s classification, not about how the counter got there.
14. Criteria 29–32 (enable / =--from tail= / TTL preservation).
15. Criterion 23 (=gc= idempotence): capture stdout twice and the file mtime.
16. Criteria 12a/12b (daemon-sent signals), which need a test-only override of =DEFAULT_HOOK_TIMEOUT_SECS= or they take five minutes each.

** Concurrency

Failure counters are written on the daemon thread at reap and read on server threads by =hook list= and =gc=. Per the fleet rule, the counting tests (unit 8, criteria 7a/7b/13) must also run under =zig build test -Doptimize=ReleaseFast=; a torn read of =consecutive_failures= is exactly the class of defect that only shows up there.

** Mutation checks

Each of these must fail a *different* test set. A mutation that fails nothing is a finding:

- remove the =ENOENT=-only restriction on the =cwd= guard (accept any =stat= error) → criterion 18;
- remove the =last_exit_status == 127= half of R2 → criterion 25a;
- remove the token-qualification restriction in R2 → criterion 17;
- drop the =consecutive_failures >= 10= floor from =gc='s R1 → criterion 25;
- let the daemon disable on the =cwd= guard → criteria 15 and 16;
- allow quarantine to escalate to disabled → criteria 9 and 26;
- remove the once-per-cycle cap on the failure counter → criterion 7a (and, indirectly, 25, whose 15-minute inference depends on it);
- count a daemon-sent signal as a failure → criteria 12a and 12b;
- reset =consecutive_failures= on any completion rather than on success → criterion 10;
- move the quarantine check after the fetch → criterion 14;
- move the =cwd= guard before the fetch → criteria 15a and 15b;
- clear =expires_at= on every =enable= → criterion 31a;
- accept =--purge= without ids, or without the one-hour floor → criteria 27 and 27a;
- drop a default from one new field → criterion 1;
- treat a short read as a parse failure → criterion 6a.

** Bounded probes

Any test that waits for a hook to fire must bound its own wait and fail on timeout rather than hang. Any test that reads =hooks.json= while the store is running must retry until it parses — the file is written by =open(TRUNC)= then =rename=, and a read racing the write can legitimately see an empty file, which parses as "no hooks" and is indistinguishable from the failure under test.

* Open questions

1. *K = 5, the 1 h ceiling, and =gc='s 10-failure floor* are pinned so the document is implementable, and the floor now carries weight it did not before — it is the wall clock that protects a rig rebuild (criterion 25). The evidence constrains K only loosely; it constrains the *shape* firmly, because hook #186 says the ceiling behaviour (retry forever, never escalate) is what matters. Of the three, the floor is the one worth a second opinion, and it is one constant.
2. *=gc --include-quarantined= threshold* is set at 20 consecutive failures. It is a display threshold only — nothing acts on it without two explicit flags — so it is cheap to change.
3. *The one-hour minimum time-in-=disabled= before =--purge=* is asserted, not derived. It exists so that an accidental =gc --yes= followed by an immediate =--purge= cannot destroy a registration inside one operator session. Any value from ten minutes to a day would serve the same purpose.

The reviewer's case was that automatic disable buys the step from 24 dispatch attempts per day to zero, that the current census contains no hook either rule would fire on, and that the incident's real cost driver is out of reach of both — set against being the only mechanism that can silence a live registration on a store carrying six other fleets. Re-derived here and agreed: see [[#why-gc-only][Why the disable rules are not daemon rules]]. What survives daemon-side is the =cwd= dispatch guard, which does not fork and does not disable, because it still saves a doomed fork and gives the failure the typed reason =gc= later reads as evidence. The concession is not free and the document says so: a store with no operator now reclaims nothing it was not given a TTL for, which makes =--ttl= the load-bearing mechanism rather than a convenience.

  *Blockers.* B1: R2 stated no failure threshold, and the literal reading disabled on a single observation — which an =rm= + =cp= redeploy of another fleet's script can produce legitimately. Now a =consecutive_failures >= 10= floor, an operator step, and criterion 25 (delete-and-restore ends =armed=). B2: R1 was specified per-event in one place and per-tick in another, with a cursor advance that had no defined value before the fetch and would have consumed a whole backlog. Resolved as per-event, after the fetch, immediately before the fork; the contradicting "no rule here will ever disable a hook that never fires" claim is restated rather than deleted, and R1's never-dispatched branch in =gc= is what now reaches that class.

  *Majors.* M2: the 15-minute floor comes free from the backoff curve, so no timestamp field was needed. M3: failure counting is pinned at reap, capped at one increment per hook per poll cycle, with success winning within a cycle — which also makes M2's inference valid and forced the pacing convention now stated at the head of Acceptance. M4: R2 has no tick-ordering entry because it is not a daemon rule. M5: daemon-sent signals (the fixed 300 s timeout, shutdown) no longer count as failures, closing a former open question that would otherwise have taken any hook running over five minutes off the air for an hour. M6: =enable= no longer clears =expires_at= unconditionally. M7: both supersession markers restated — see the History of =./server-hooks.org= and =./hook-execution.org=. M8: =--purge= takes typed-out ids and a one-hour floor; the untargeted =--state disabled= form is withdrawn.
