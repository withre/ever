#+title: Hook Reclamation — Failure Backoff, Expiry, and =hook gc=
#+state: draft
#+FILETAGS: :subscriber:orchestrator:cli:

* Summary

Nothing in Ever reclaims a hook registration. A hook survives the run that created it, the disappearance of its script, the wipe of its working directory, and every restart of the store. This document specifies four mechanisms that bound a hook's lifetime without ever losing one silently:

1. *Failure accounting and backoff.* A hook that fails repeatedly *in ways Ever can attribute to itself* enters =quarantined= and is retried on an exponential schedule with a one-hour ceiling. It returns to =armed= by itself on the first success. It never escalates to anything worse. A hook that merely exits non-zero is *not* failing as far as Ever is concerned — that is a value its author chose, and on this store it usually means "this event was not for me" ([[#what-counts][why]]).
2. *A dispatch guard for the provably-doomed case.* If a hook's working directory no longer exists, the daemon records the failure without forking, because the shell it would fork can only fail. The guard does *not* disable anything.
3. *Optional expiry.* =ever hook add --ttl <dur>= stores an absolute =expires_at=; at expiry the hook is disabled, never deleted. Off by default, consented at registration, renewable.
4. *=ever hook gc=* — an operator command that reports by default and acts only with =--yes=. *It is the only path by which a hook that an operator did not already bound with a TTL can be switched off.*

The division of labour is the point. The daemon's unattended powers are limited to actions that are bounded, self-healing, or consented at registration: it may slow a hook down (quarantine) and it may honour a lifetime the registrant asked for (TTL). It may *not* switch off a registration on its own inference. The two rules that decide a hook is dead — R1 (working directory absent) and R2 (literal absolute command path absent, plus an observed exit 127) — are evaluated by =gc= and applied only under =--yes=, with the evidence printed first.

A fifth thing this document has to fix before it can ship any of the above: it turns one name-addressed verb into four, and hook names are neither unique nor unambiguously resolvable today. See [[#names][Name addressing]].

Nothing here deletes a hook automatically, under any condition, ever, and nothing here disables one without either an operator's =--yes= or a TTL the registrant set.

This document *does not* fix the poll-cycle rescan cost that dominated the 2026-07-27 incident. That is =ever--hook-scan-cursor-and-lag= (round-4 item 1). See [[#scope-boundary][What this does not fix]].

* Motivation

** The failure mode, re-established from source at this base

Verified against =txpyxrnm= / =142d5e66= ("Migrate CLI to zig-cli-kit"), 2026-08-03. All line references are to that commit.

The hook daemon builds a single shell string per dispatch and hands it to =/bin/sh -c= (=src/store/hooks.zig=, =executeHookCommand=):

#+begin_src
cd '<hook.cwd>' && [NAME='v' ...] EVER_TOPIC='...' ... exec <hook.command>
#+end_src

Three properties follow directly, and all three matter for anything that tries to decide whether a hook is dead:

- *=hook.command= is a shell fragment, not an argv.* It is stored as one string and interpolated unquoted so that pipes and redirects work as the user intended (=hooks.zig=, comment above the =shell_cmd.appendSlice(hook.command)= call). There is no "resolved command path" to stat in the general case.
- *=hook.cwd= is a stored absolute path* (=main.zig= =handleHookAdd= reads =/proc/self/cwd=), and it is consumed by a =cd= that short-circuits the whole command with =&&=. If =cwd= is gone, the command *provably never executes*.
- *The exit status is never recorded anywhere durable.* =reapChildren= computes =(status >> 8) & 0xFF= and, if non-zero, writes one line to the store's stderr. It is not written to the hook record and not written to the per-execution log file under =data/hooks/=. Recovering "how often has this hook failed" today means grepping the store's stderr log, which is exactly what the incident had to do.

Nothing in =pollAndExecute= consults liveness of any kind. Every hook in the table is polled every 500 ms for as long as the store runs.

*** Exit-status semantics, measured

Measured 2026-08-03 on an isolated store (own =--data-dir= under =/var/tmp=, port 7931, torn down afterwards), one hook per case, one published event:

| Case                                            | Observed exit | Logged by daemon?            |
|-------------------------------------------------+---------------+------------------------------|
| =cwd= absent, command fine (=/bin/echo hello=)  | 1             | yes                          |
| command is an absolute path that does not exist | 127           | yes                          |
| command exists but is not executable            | 126           | yes                          |
| command resolved from =PATH= (=echo hello=)     | 0             | no (only non-zero is logged) |
| script exits 3                                  | 3             | yes                          |
| script kills itself with =SIGKILL=              | *(nothing)*   | *no*                         |

The last row is a defect that anything counting failures must handle. =reapChildren= extracts =(status >> 8) & 0xFF=, which is 0 for a signal death. *A hook killed by a signal — including by the daemon's own 300-second timeout — is today indistinguishable from a hook that exited 0.* Any naive =consecutive_failures= counter built on the existing extraction would silently treat every timeout kill as a success.

The first row matters too: the =cwd=-missing class does *not* produce 127. It produces whatever the host's =/bin/sh= returns for a failed =cd= — measured 1 here (=/bin/sh= is bash 5.3 on this host); the value is shell-dependent and *the design must not key on it*. This is the entire =/tmp=-wipe class from the incident, and a GC keyed on exit 127 misses all of it.

*** The record format is more fragile than it looks

=HookTable.load= parses =hooks.json= with =ignore_unknown_fields = true=, tries the current format, then falls back to a legacy format, then =catch return=. Measured on the isolated store:

- *Unknown fields are silently discarded on the next write.* Injecting =state=, =consecutive_failures= and =expires_at= into all 7 rows, restarting, and publishing one event: all 7 hooks loaded, and the first =saveLocked= (triggered by the first cursor update, i.e. within one poll cycle) rewrote the file with those fields gone. This is the downgrade path, and it is lossy and immediate.
- *One malformed row destroys the entire registry, silently.* Deleting the =cursor= key from a single row took the table from *7 hooks to 0 hooks loaded*, with **no error, no warning and no log line** — only =Hook daemon started (0 hooks loaded)=. The next =ever hook add= then rewrote =hooks.json= with one row and =next_id= reset to *1*, permanently destroying the other six registrations and reusing their IDs.

That second finding is the reason this document treats the record migration as a first-class hazard rather than a detail. Adding a field without a Zig default to =HookJson= would do exactly this to every existing store on first start of the new binary.

** Goals

- A repeatedly-failing hook stops costing a dispatch per matching event, without being switched off.
- A hook that provably cannot run is *identified* automatically, with the evidence recorded, and stopped by an operator in one command.
- A registration can be given an explicit lifetime at creation, and renewed.
- An operator can see what is reclaimable, and why, before anything happens.
- The disabled/quarantined state and all counters survive a restart.
- A store written by the previous binary loads with no change in hook count or behaviour.
- *No unattended mechanism can silence a registration the store's operator did not bound.*

** Non-Goals

- *Reaping on lag, age, or topic silence.* Beyond the incident's own reasoning (a low-traffic topic is indistinguishable from an abandoned one), there is a structural reason: =Hook.cursor= is *polymorphic in the pattern shape* — a topic-local skip count for exact topics, a global log offset for prefix/wildcard patterns (=hooks.zig= doc comment on =Hook.cursor=; =TopicManager.tipForPatternLocked=). There is no single "lag" number comparable across hooks. Of the 16 hooks on the live store, 9 carry topic-local counts and 7 carry global offsets. Lag may be *reported*; it must never be a reclamation input.
- *Automatic deletion of anything, ever.* Reclamation means =disabled=. Deletion is =ever hook rm= or =ever hook gc --purge <id>… --yes=, both operator-initiated and both targeted at named ids.
- *Automatic disable on inference.* Superseding this document's first revision: the daemon does not disable a hook because it decided the hook is dead. Its only unattended disable is TTL expiry, which the registrant asked for. See [[#why-gc-only][Why the disable rules are not daemon rules]].
- *Repointing a hook's command* (=ever hook update=). See [[#repoint-coupling][Coupling]].
- *Recovering events missed while a hook was broken.* See [[#repoint-coupling][Coupling]]; this is today's behaviour and this document does not change it.
- *Per-hook execution timeouts.* The daemon uses a fixed 300 s (=DEFAULT_HOOK_TIMEOUT_SECS=). Making it per-hook is out of scope. The *interaction* with failure counting is in scope and is resolved in [[#daemon-signals][Signals the daemon sent itself]], not left open.

* Proposal

** <<record-fields>>Record format

Thirteen fields are added to =Hook=, =HookJson=, =HookJsonLegacy= *and =protocol.HookInfo=*. *Every one carries a Zig default*, so a row written by the previous binary parses unchanged and a response from an older store decodes unchanged.

They fall into four groups, and the grouping is the argument for the count — each group answers a question a different reader asks.

*The four tables below are authoritative for both the set and the count.* Where any prose in this document or another disagrees with them, they are right and the prose is stale. That is not a formality: the central measured hazard here is that *one* field reaching =HookJson= without a default takes every registration in the store to zero, silently, and an implementer reconciling a prose count against a longer table has to guess which is wrong.

*State and lifetime:*

| Field             | Type          | Default   | Meaning                                                          |
|-------------------+---------------+-----------+------------------------------------------------------------------|
| =state=           | =[]const u8=  | ="armed"= | =armed= / =quarantined= / =disabled=                             |
| =expires_at=      | =?i64=        | =null=    | Epoch ms; =null= = no expiry                                     |
| =disabled_at=     | =?i64=        | =null=    | Epoch ms when the hook entered =disabled=; gates =--purge=       |
| =disabled_reason= | =?[]const u8= | =null=    | One of the reason strings in [[#reason-strings][Reason strings]] |

*Quarantine accounting — the only fields that are inputs to K:*

| Field                  | Type   | Default | Meaning                                                                              |
|------------------------+--------+---------+---------------------------------------------------------------------------------------|
| =consecutive_failures= | =u32=  | =0=     | *Attributable* failures only ([[#attributable][what counts]]). Reset to 0 on any success |
| =streak_started_at=    | =?i64= | =null=  | Epoch ms of the failure that took the counter 0 → 1; supplies every wall-clock floor  |
| =next_attempt_at=      | =?i64= | =null=  | Epoch ms; while =now < next_attempt_at= the hook is skipped                           |

*R1's evidence, deliberately separate from the above ([[#cwd-observation][why]]):*

| Field               | Type   | Default | Meaning                                                              |
|---------------------+--------+---------+-----------------------------------------------------------------------|
| =cwd_missing_since= | =?i64= | =null=  | Epoch ms of the first guard hit in the current run; cleared when =stat(cwd)= succeeds |

*Diagnostic — displayed, never an input to any rule:*

| Field              | Type          | Default | Meaning                                                                        |
|--------------------+---------------+---------+---------------------------------------------------------------------------------|
| =last_exit_status= | =?i32=        | =null=  | =0..255= = exit code; *negative = −signal* (=-9= = SIGKILL)                     |
| =last_error=       | =?[]const u8= | =null=  | Short reason for the last failed attempt; =null= if the last attempt succeeded  |
| =last_success_at=  | =?i64=        | =null=  | Epoch ms of the last exit-0 dispatch. *The fact an operator needs most*         |
| =nonzero_exits=    | =u32=         | =0=     | Total non-zero exits, never reset. The only remaining trace of the signal removed from K |
| =timeouts=         | =u32=         | =0=     | Kills the daemon itself sent ([[#daemon-signals][why]])                          |

=last_success_at= earns its place on one argument: an operator looking at a flagged hook has to decide whether to disable it, and "never succeeded since it was registered in April" and "succeeded ninety minutes ago" are opposite verdicts that render identically without it. On a store carrying other fleets' hooks that is the difference between a decision and a coin flip.

=state= is a *string*, not a Zig enum, so that a record written by a later binary carrying a state this one does not know still parses. An unrecognised =state= value is treated as =armed= and logged once at load, naming the hook id and the value. Rationale: a hook wrongly armed is noisy; a hook wrongly disabled is a silent outage, and round-4's recurring failure class is silent outages.

=expires_at= is stored *absolute*, never as a remaining duration, so a restart cannot extend a lifetime.

A =version: u32 = 1= field is added to =HookFileJson= and written as =2=. The current binary does not branch on it; it exists so a future reader can tell a downgraded file from an original one. This is the only defence available — see [[#downgrade][Downgrade]].

*** <<load-hardening>>Load path hardening (required, not optional)

Given the measured "one bad row loses everything, silently" behaviour, the migration cannot land without this:

- If =hooks.json= exists, is non-empty, and *both* parse attempts fail, the store must:
  1. log an error naming the file, its size, and the parse error;
  2. rename it to =hooks.json.unparseable-<epoch_ms>=;
  3. start with an empty table. It must *not* silently start empty and then overwrite the file.
- If =hooks.json= parses but yields zero hooks while the file is larger than a threshold that could not hold zero hooks (say 64 bytes), that is the same condition and takes the same path.

*Truncation is not corruption, and must not be treated as it.* =load= allocates a fixed 1 MB buffer and reads until it is full or a read returns ≤ 0, with no check that the whole file was consumed. A =hooks.json= larger than 1 MB is therefore delivered to the parser truncated mid-JSON, both parse attempts fail, and the rule above would rename a *perfectly valid registry* to =hooks.json.unparseable-<ms>= and start empty — turning a recoverable condition into the exact catastrophe the rule exists to prevent. So: =load= must =fstat= the file first and compare against the bytes read; if the file is larger than the buffer, log an error naming both sizes, *leave the file alone*, and refuse to start the hook daemon rather than starting it empty. The current ceiling is not remote — 16 hooks is ~3.8 kB, and thirteen new fields put the limit near 1,900 hooks.

Without this, any future field addition that misses a default silently destroys every registration on every store, and the operator's first sign is that nothing fires.

** States

Three states. The observable difference is one sentence: *a =quarantined= hook fires again on its own; a =disabled= hook never does until an operator says so.*

| State         | Polled?                            | Leaves by itself?           | How it is entered                                                         |
|---------------+------------------------------------+-----------------------------+---------------------------------------------------------------------------|
| =armed=       | every tick                         | —                           | default; any success; =hook enable=                                       |
| =quarantined= | only when =now >= next_attempt_at= | yes — one success → =armed= | =consecutive_failures= reaches K                                          |
| =disabled=    | *never*                            | *no*                        | TTL expiry; =hook disable=; =hook gc --yes=. *Never on daemon inference.* |

Two invariants, both of which a reviewer can check by reading the transition table alone:

- *No automatic transition from =quarantined= to =disabled= on failure evidence of any kind, at any threshold.* Hook #186 is why.
- The only unattended transition into =disabled= is TTL expiry, and a TTL exists only because the registrant passed =--ttl=. Every other route into =disabled= passes through an operator command.

*Expiry does apply to a quarantined hook*, and that is intended: a TTL is a statement about the registration's lifetime, not about its health, and a hook that is both expired and failing is not a case where the expiry should be ignored. The first invariant is about *failure evidence*, and that qualifier is load-bearing.

*** Skip ordering matters

The quarantine check must happen in =processHook= *before* the =fetch= / =fetchPatternByOffset= call, and disabled hooks must be skipped in =pollAndExecute= before =processHook= is entered. This is not a micro-optimisation: for a prefix/wildcard hook whose pattern matches nothing, that fetch is a walk of the whole log (=TopicManager.fetchPatternByOffset=, =topic.zig=). Skipping it turns a quarantined hook's cost from 2 scans/second into 1 scan/hour at the backoff ceiling, and a disabled hook's cost into zero.

The =cwd= guard is the exception and it is deliberately *not* in that group: it needs an event to guard, so it sits after the fetch. See [[#tick-ordering][Ordering inside the daemon tick]].

** Failure accounting and backoff

*** <<what-counts>>Why a non-zero exit is not evidence of anything

This is the single most important constraint on the whole design, and the first two revisions of this document got it wrong.

A hook command is a *shell fragment* whose exit status is whatever its last executed command returned. Ever never told the author that this value meant "healthy". For the dominant idiom on this store — a prefix hook that receives everything under a namespace and routes a subset — *declining an event is the normal path*, and whether declining produces a zero or non-zero status is an accident of how the script happens to end.

Measured 2026-08-03 on an isolated store (own =--data-dir=, port 7951, torn down). Three scripts, all correct, all delivering the one event they existed for, none with a trailing =exit 0=; six declined =.status= events then one =.done=:

| Script shape                                                          | Declines produce | Verdict |
|-----------------------------------------------------------------------+------------------+---------|
| A — =case "$EVER_TOPIC" in *.done) … esac=, event does not match      | *exit 0*         | safe, by accident: an unmatched =case= returns 0 |
| B — guard is the script's last statement: =… \vert{} grep -q X && act= | *exit 1* × 6     | *6 consecutive "failures" from a healthy hook* |
| C — =case= matches, and the branch's last command is the predicate    | *exit 1* × 6     | same |

All three then delivered the =.done= correctly. Under a K of 5 counting generic non-zero exits, B and C quarantine on the fifth *declined* event, and the =.done= — the event the hook exists for — waits out the backoff, up to an hour at the ceiling.

This is not hypothetical for this store. Five of the sixteen live hooks are prefix hooks and four of those five are fleet notification paths, including =#227=, the supervisor's own wake-up channel. Both =#186= and =#227= are shape A *and* carry an unconditional =exit 0= — doubly safe — but *nothing in Ever requires, documents or checks either property*, and =hook new='s scaffold adds neither. Shape B is the shortest way to write a filter and the one a person reaches for first.

*And the table above is not the whole population, because not every hook command is a script.* Half the live store's commands are bare tools invoked directly: =#11= and =#12= are =chronoa send op --prefix …=, =#4= is =echo … \vert{} tee -a /tmp/…=, =#6= is =echo … >> /tmp/…=. For those there is no script shape to inspect at all — the exit status is *the tool's*, and it means whatever that tool decided it means. A =tee= or a redirect into a =/tmp= path returns non-zero the moment the directory goes. So a reader must not conclude "my hook ends in a =case=, therefore this does not apply to me": for a third of these hooks there is no =case= to end in.

So: *Ever cannot distinguish "the command failed" from "the command declined", and must not pretend to.* This is the same category error the document already rejects one level down — exit 127 means both "not found" and "the script chose 127", which is exactly why [[#gc-rules][R2]] is a conjunction and not a single test. The first two revisions applied that reasoning to 127 and then failed to apply it to 1. The remedy adopted here is shape-independent for exactly this reason: a generic non-zero never counts, whatever produced it.

/[Superseded: 2026-08-03 — revisions 1 and 2 of this document listed "the child exited non-zero" as the first thing that counts as a failure, which would have quarantined a healthy shape-B filter hook on its fifth declined event. Withdrawn; a generic non-zero exit is now recorded and displayed but is *not* an input to K.]/

There is a rhyme worth recording, because it is the same mistake in a neighbouring system and it was paid for once already. Hook =#186='s own header documents six revisions of filter logic, and revision 6 reads: "'nonzero exit == crash' is FALSE for chronoa: portable-pty flattens signal deaths to exit code 1, so every session the supervisor kills reported a crash." That is a script learning not to read another system's exit code as a health signal. This document is the same lesson one layer out.

*** <<attributable>>What does count: failures the daemon can attribute to itself

=consecutive_failures= counts *only* outcomes that Ever caused or can prove, never outcomes it merely observed:

| Cause                                                        | Counts toward K? | =last_error= |
|---------------------------------------------------------------+------------------+--------------|
| =cwd= guard refused to spawn (=stat(cwd) == ENOENT=)          | *yes*            | =cwd-missing= |
| =fork= / =execve= setup / log-file creation failed            | *yes*            | =spawn-failed= |
| child died from a signal the daemon did not send              | *yes*            | =signal=     |
| exit 127 *and* the [[#gc-rules][R2 token test]] qualifies *and* that token is absent | *yes* | =command-missing= |
| exit 127 with no qualifying token, or a qualifying token that exists | *no*       | =exit=       |
| any other non-zero exit                                       | *no*             | =exit=       |
| child killed by a signal the daemon *did* send                | *no*             | =timeout= / =shutdown= |
| =MAX_CONCURRENT_HOOKS= reached                                | *no*             | unchanged    |

The 127 row is deliberately narrow: it is the incident's own hook. =#20= ran =/tmp/ever-orch/gate-watch.sh=, a qualifying absolute token, absent, exiting 127 on 88,804 dispatches. That hook still quarantines under this rule. A script that merely *chooses* to exit 127 does not.

What is given up: a hook that is genuinely broken and signals it with =exit 1= is never quarantined, and keeps costing one dispatch per matching event. That is exactly today's behaviour, and Ever has no basis for calling it broken. It is not invisible — =nonzero_exits=, =last_exit_status= and =last_success_at= are in the record, =hook list= shows them, and =gc= flags a hook that has never succeeded. The operator decides, which is where every judgement in this document now lives.

*** <<counting>>How "consecutive" is counted, given that one hook can have 16 children in flight

This has to be pinned, because =processHook= loops over a batch of up to 100 fetched events and calls =executeHookCommand= for each, stopping only at the *global* =MAX_CONCURRENT_HOOKS = 16=. A single hook draining a backlog can therefore have 16 children running at once, and =reapChildren= collects them with =waitpid(-1, …, WNOHANG)= in whatever order the kernel offers.

- *Accounting happens at reap*, never at spawn. The outcome is not known until then.
- *=consecutive_failures= increments by at most 1 per hook per poll cycle*, however many of that hook's children were reaped in that cycle. The daemon records, per hook, the tick sequence number at which it last incremented, and skips the increment if it equals the current tick.
- *A success in a cycle wins over failures in the same cycle.* If any child of a hook reaped in a cycle exited 0, the counter resets to 0 and the state returns to =armed=, regardless of sibling failures. A hook that succeeded at all is not broken.
- *The quarantine gate is not a burst brake.* It is evaluated at the top of =processHook=, before the batch loop, so a hook failing on every event still spawns its whole in-flight batch before the K-th failure is observed. Quarantine takes effect from the *next* poll cycle. This is a deliberate limit: throttling mid-batch would require the daemon to block on reaps, which is what [[./hook-execution.org]] removed.

Two consequences worth stating because they are otherwise surprising:

1. Reaching K takes at least K poll cycles — 2.5 s at K = 5. Any acceptance criterion that drives a hook to quarantine must pace its events at least one poll interval (500 ms) apart; publishing five events at once produces one failure, not five.
2. Wall-clock floors are read from =streak_started_at=, which is set when the counter goes from 0 to 1 and cleared when it returns to 0.

   /[Superseded: 2026-08-03 — revision 2 derived the wall clock from the backoff curve instead, arguing that =consecutive_failures >= 10= implies 15.5 minutes because failures 5 and up are separated by the delay. It is arithmetically true and it was a mistake to rely on it: it silently depends on the once-per-cycle cap, so a mutation that removes the cap also removes a safety property in a different section, with no test relating the two. An explicit timestamp costs one field and cannot be undermined from a distance.]/

This is the one place the change touches shared mutable state from two threads: the counters are mutated on the daemon thread at reap and read on a server thread by =hook list= / =gc=. They live in =HookTable=, whose mutex already covers =updateCursor= / =snapshot=, and the implementation must use it. Per the fleet rule, the resulting tests run under =-Doptimize=ReleaseFast= as well as debug.

*** <<signal-accounting>>Signal deaths must be decoded

=reapChildren= currently does =(status >> 8) & 0xFF=, which is 0 for a signal death. It must decode the full wait status: =WIFEXITED= → exit code; =WIFSIGNALED= → =-WTERMSIG=. Without this, a hook killed by a signal is recorded as a success.

*** <<daemon-signals>>Signals the daemon sent itself do not count as failures

The daemon kills its own children in three places — =checkTimeouts= at the hard-coded =DEFAULT_HOOK_TIMEOUT_SECS = 300=, =shutdownChildren= on store shutdown, and =killChildrenForHook=. If a decoded =SIGTERM=/=SIGKILL= counted as a failure, then:

- *any hook that legitimately runs longer than five minutes would quarantine for up to an hour*, on a timeout nobody opted into (the =--timeout= flag specified in [[./hook-execution.org]] never shipped; see the marker there). On the live store, =#11= and =#12= invoke =chronoa= and =#227= runs a crosstalk notify — all commands that can legitimately block on another agent. A notification path going quiet for an hour is exactly the silent-outage class round 4 exists to eliminate;
- a clean store shutdown would quarantine *every* hook that happened to be running.

So: *=ProcessEntry= gains =signalled_by_daemon: bool=, set when the daemon signals that entry.* At reap, a child that died from a signal with that flag set records =last_error = "timeout"= (or ="shutdown"=), does *not* increment =consecutive_failures=, and does not reset it either. The count is surfaced separately — =hook list= shows a =TIMEOUTS= tally — so the behaviour is visible rather than merely suppressed.

This is the correct answer only because the timeout is not per-hook. *If a per-hook =--timeout= is added later, a timeout on a hook that declared one should count*, because then the operator consented to the bound. That is a hand-off requirement, not a future nicety.

*** The curve, pinned

- =K = 5=, *and the streak must span ≥ 60 s of wall clock* (=now − streak_started_at >= 60_000=). Both conditions, not either. A hook that fires once an hour therefore needs five hours to quarantine, which is correct: K exists to separate transient from persistent, and five dispatches inside one second are one trial, not five.
- =delay(n) = min(30s × 2^(n − K), 1h)= for =n = consecutive_failures=, giving 30 s, 1 m, 2 m, 4 m, 8 m, 16 m, 32 m, 1 h, 1 h, … from n = 5 onwards.
- Ceiling = 1 h, and it is a fixed point. A permanently broken hook costs 24 dispatch attempts per day forever — and, for a prefix hook, 24 full-log scans per day instead of 172,800. That is cheap enough that there is no case for escalating further, and escalating further is what would have killed hook #186.
- One success sets =consecutive_failures = 0=, =next_attempt_at = null=, =last_error = null=, and =state = armed=.
- =timeouts= (see [[#daemon-signals][above]]) is a separate counter and is never reset by a success; it is diagnostic only.

*** The cursor during quarantine

While a hook is quarantined and not yet due, its cursor does not advance, because no fetch and no dispatch happen. Matching events accumulate in the log and are delivered when the hook next attempts — oldest first. This is strictly better than today, where a dispatch that exits 127 still advances the cursor past the event.

When the attempt *does* come due, the batch is fetched and dispatched normally, and the cursor advances at spawn as it does today. So a permanently broken hook still consumes up to 100 events per hourly attempt and drops them. Changing that — retrying the same event rather than advancing past it — needs the attempted-versus-delivered cursor split that belongs to the repoint half, and this document deliberately does not introduce it. See [[#repoint-coupling][Coupling]].

The interaction to be aware of: a long-quarantined prefix hook resumes with a large backlog, drained 100 events per poll cycle and at most =MAX_CONCURRENT_HOOKS= (16) concurrently. That is a real burst, and it is the same burst =hook enable= faces — see [[#reversibility][Reversibility]].

** The =cwd= dispatch guard (the daemon's only static check)

After the batch is fetched and immediately before each fork, =stat(hook.cwd)=. If it returns =ENOENT=:

- do not fork;
- record the attempt as a failure with =last_error = "cwd-missing"=, subject to the once-per-cycle rule in [[#counting][How "consecutive" is counted]];
- advance the cursor exactly as a spawn would, because this sits exactly where the spawn would have been and has an event and an offset in hand;
- count toward quarantine like any other failure. *The guard never disables anything.*

This is sound: the dispatch string is =cd '<cwd>' && … exec <cmd>=, so a failed =cd= short-circuits before the command and the fork can only produce a shell that fails. Skipping it saves a fork/exec and, more importantly, gives the failure a *typed* reason in the record, which is what =gc= later reads as evidence.

Only =ENOENT= triggers the guard — =EACCES=, =EIO=, =ESTALE=, =ELOOP=, =ENOTDIR= and =ENAMETOOLONG= all mean "unknown", and the daemon forks anyway and lets the real outcome decide. An NFS mount that is down returns =ESTALE= or =EIO=, not =ENOENT=.

There is no corresponding guard for the command path. The command is a shell fragment (see [[#rejected-static][Rejected: stat the command path before spawning]]) and the only way to know whether it runs is to run it.

*** <<cwd-observation>>The guard's own observation state

=cwd_missing_since: ?i64= is set to the current time when the guard fires and the field is =null=, and cleared to =null= on any dispatch where =stat(cwd)= succeeds. It is *not* derived from =consecutive_failures= and shares nothing with it.

That separation is the point, and it exists because tying R1's threshold to the quarantine counter is unsound in a specific way: a quarantined hook is by definition already past K, so any rule phrased as "disable when =consecutive_failures= reaches K" is *pre-satisfied* for exactly the population that is skipped on all but one tick per hour. The rule then reduces to a single =stat= sample, taken at an instant nobody chose, against hooks somebody is most likely in the middle of repairing — moving a directory, rebuilding a rig, re-cloning a worktree. Hook =#186= spent three days in that condition with its =cwd= at =~/Coding/github.com/withre/chronoa=, a live worktree; one badly-timed sample during a =jj workspace= operation would have been enough.

With a dedicated field, [[#gc-rules][R1]] requires *two ENOENT observations by two different observers separated by at least fifteen minutes* — one recorded by the daemon at dispatch, one taken by =gc= at the moment the operator asks. A directory that is absent for one second and present at the next dispatch clears the field and the evidence with it.

** <<why-gc-only>>Why the disable rules are not daemon rules

/[Superseded: 2026-08-03 — the first revision of this document made R1 and R2 *daemon* rules that moved a hook to =disabled= once =consecutive_failures= reached K. The round-4 spec review argued they should be =gc= candidate rules only. That argument is adopted, and this section records why, because "the reviewer said so" is not a reason a later implementer can evaluate.]/

The question is narrow: the daemon already caps a permanently-broken hook at 24 dispatch attempts per day via the backoff ceiling. Automatic disable takes that to zero. *What does the 24-to-0 step buy, and is it worth letting the daemon switch off a registration on its own inference?*

On this store, it buys almost nothing, and the document's own numbers say so:

- The census of 2026-08-03 contains *zero* hooks that R1 or R2 would fire on. The incident's 24 dead hooks were reclaimed by hand and have not recurred.
- The incident's actual cost driver — =#17=, =#19=, =#157=, =#158=, all at cursor 0 with patterns that never match — is out of reach of both rules under the daemon reading, because a hook that never fires never fails. So the automatic rules do not address the pathology that motivated the item; [[#scope-boundary][round-4 item 1]] does.
- 24 attempts/day is roughly one log file per hour per dead hook. Set against a 105,272-file, 476 MB =data/hooks/= at the time of the incident, that is not the term that matters.

Against that, the cost is concrete and was demonstrated by the review:

- *R2 is an inference, not a proof.* Its static half extracts a token heuristically from a shell fragment and its dynamic half reads an exit code from the past. Five of the seven absolute-path hooks on the live store belong to other fleets that redeploy their own scripts, and an =rm= + =cp= redeploy that overlaps one matching event produces =last_exit_status == 127= and =stat == ENOENT= *simultaneously and legitimately*. Under a daemon rule that is a silenced hook belonging to someone else; under a =gc= rule it is a line in a report that is gone by the time anyone reads it.
- *R1 is a proof, but only about a moment.* =stat(cwd) == ENOENT= proves the command did not run *this time*. It says nothing about whether the directory is coming back — and the workflow this document exists to serve is rig rebuilds, which round-3 calls routine and which are literally =rm -rf && mkdir=. A daemon rule needs a wall-clock guard to be safe; a =gc= rule gets one for free, because a human ran it.
- The blast radius is asymmetric. A dead hook left armed costs 24 forks a day. A working hook wrongly disabled is a silent outage on a neighbouring fleet, discovered when something does not happen.

So the division is: *the daemon may slow a hook down (quarantine, self-healing, reversible, bounded) and may honour a lifetime the registrant declared (TTL). Deciding that a hook is dead is an operator's judgement, and =gc --yes= is where it is exercised* — with the evidence printed immediately before.

What this gives up, stated plainly so it is not discovered later, and in two parts because the second is easy to miss.

*First: a store with no operator never reclaims anything it was not given a TTL for.* That is a real regression against the first revision, and the answer is that =--ttl= is the mechanism for unattended reclamation and it should be the default discipline for orchestration rigs. The registrant knows how long its run will last; the daemon never does. (Making =--ttl= a documented default in the ACE-stack skill is out of scope here and is noted for whoever owns that file.)

*Second, and this is a cost the concession itself created: moving disable to =gc= made delivery loss on a broken hook unbounded in time.* Under the first revision, a hook whose =cwd= vanished disabled at K and stopped consuming events after roughly five. Now the daemon never disables, so the =cwd= guard advances the cursor past *every* matching event for as long as nobody runs =gc=. Quarantine caps the rate — one batch of up to 100 per hourly attempt at the ceiling, so on the order of 2,400 events a day per broken hook rather than all of them — but the total is bounded only by how long the hook goes unnoticed. The trade is: a large reduction in the risk of disabling someone else's working hook, paid for in events dropped by a hook nobody is watching. It is the right trade, because a wrongly-disabled notification path is a silent outage on another fleet while a broken hook's dropped events were already going nowhere — but it is a trade, not a pre-existing condition, and whoever revisits M1 should revisit it knowing which way it cut.

That cost also *interacts* with =ever--hook-scan-cursor-and-lag= (round-4 item 1), which is being specified in parallel and advances hook cursors on scan rather than only on delivery. A hook that is quarantined and behind will therefore reach and consume its backlog sooner than it does today. Naming the interaction, not resolving it: the two documents change the same cursor from different directions, and whichever lands second owns reconciling them. Nothing here should be built assuming the other has not landed.

** R3 — expiry, the daemon's one unattended disable

If =expires_at != null= and =now >= expires_at=, set =state = disabled=, =disabled_reason = "expired"=, at poll time, before any fetch. Log *once*, at the transition — not once per tick. (The incident's 15 MB log is what one un-deduplicated per-tick log line looks like.)

This one is unattended because the registrant asked for it. Everything else the daemon can do to a hook is reversible without an operator.

No other automatic disable exists. In particular, no rule involving lag, cursor distance, age, =created_at=, topic emptiness, or failure *ratio* — see [[#rejected-ratio][Rejected: a failure ratio]].

** Expiry, and why this is a TTL and not a lease

The triage draft calls this "leasing the registration to the run that made it", and proposes =--ttl= / =--lease= as synonyms. They are not the same thing and the difference is load-bearing.

A *lease* is held against a liveness signal: the holder renews, and expiry means the holder is gone. A *TTL* is a wall clock. Ever has no way to observe whether the run that registered a hook is still alive — there is no owner field, no session handle, no heartbeat. Shipping a wall clock under the name "lease" invites exactly the failure the incident's own non-goal warns about: a long-running rig whose hooks vanish mid-run, silently, on a timer nobody remembers setting. Hook =#170= (=ace-stack.support.tick=) has been registered since at least April.

So: implement a TTL, call it a TTL, and make renewal explicit.

- =ever hook add --ttl <dur>= — parsed with the existing =timers.parseDuration= (=src/store/timers.zig=, accepts =s= / =m= / =h= / =d=, rejects =0= and bare integers). *=parseDuration= returns =u64= seconds and =expires_at= is epoch milliseconds*, so the store is =expires_at = getMilliTimestamp() + parseDuration(s) * 1000=. Getting this wrong makes =--ttl 1h= expire in 3.6 seconds, and the symptom looks like a broken acceptance criterion rather than a unit bug.
- =ever hook renew <id|name> [--ttl <dur>]= — sets =expires_at = now + dur=, or extends by the original TTL if =--ttl= is omitted. Refuses on a hook with no =expires_at= (a TTL is not something you can acquire by renewing). The name form refuses ambiguity per [[#names][Name addressing]].
- *No default TTL, ever.* Omitting =--ttl= means =expires_at = null=, which is today's behaviour.
- =--lease= is *not* provided as an alias. If a real lease is wanted later it needs an owner identity and a heartbeat, and it should not inherit this name.

*** <<gc-rules>>The reclamation rules

These are =gc='s rules. The daemon does not evaluate them; see [[#why-gc-only][Why the disable rules are not daemon rules]].

**** R1 — working directory absent

A hook is a *reclaimable* candidate under R1 when all of:

1. =state != "disabled"=; *and*
2. =stat(hook.cwd)= returns =ENOENT= — evaluated *now*, *in the store process* (see [[#where-stat][Where the =stat= calls happen]]), not read from the record. Any other =stat= error (=EACCES=, =EIO=, =ESTALE=, =ELOOP=, =ENOTDIR=, =ENAMETOOLONG=) disqualifies; *and*
3. =cwd_missing_since != null= and =now − cwd_missing_since >= 15 min=.

Condition 3 is a *daemon* observation and condition 2 is a *=gc=* observation, so R1 requires two independent ENOENT readings fifteen minutes apart, by two observers, one of which the operator chose the moment of. See [[#cwd-observation][The guard's own observation state]] for why that must not be expressed as a =consecutive_failures= threshold.

A hook that has *never dispatched* has no daemon observation at all and therefore fails condition 3 permanently. It goes to the *flagged* section instead — see below.

/[Superseded: 2026-08-03 — revision 2 made a never-dispatched hook with a missing =cwd= *reclaimable*, and Open question 3 of revision 1 claimed this was "specified" when no rule or criterion covered it. Both withdrawn. The argument for it — "=stat(cwd) == ENOENT= is provable without a dispatch" — confused provability of the *predicate* with safety of the *action*: it is one sample, taken at an arbitrary instant, applied to the population the store knows the least about. A hook registered thirty seconds ago from a directory a rig is about to create is indistinguishable from one abandoned in April. That inverts this document's own conservatism principle, applying the weakest evidence to the least-known population.]/

**** R2 — command is a literal absolute path that is absent, and the last dispatch exited 127

Both halves are required, and the static half is deliberately narrow. A token qualifies only if:

- it is the first whitespace-delimited token of =hook.command=; *and*
- it begins with =/=; *and*
- it contains none of =$=, backtick, =*=, =?=, =[=, =~=, =\=, =:=, single or double quote.

A hook is a *reclaimable* candidate under R2 when its token qualifies, =stat(token) == ENOENT= evaluated now *in the store process* ([[#where-stat][why that matters]]), =last_exit_status == 127=, =consecutive_failures >= K=, and =now − streak_started_at >= 15 min=. A qualifying token that is absent on a hook that has *never* dispatched goes to the *flagged* section instead: without an observed 127 the conjunction is incomplete, and the whole value of R2 is that it is a conjunction.

Note that under [[#attributable][what counts]], a qualifying-token 127 is one of the four attributable causes, so =consecutive_failures= for such a hook *is* a streak of command-missing observations rather than a mixture. That is deliberate: it is what makes the same counter usable here and not usable for R1, where the guard's evidence needed its own field.

Why both halves:

- *The static half alone is unsound.* Of the 16 hooks on the live store on 2026-08-03, *9 have a first token that is not a path*: =sh= (×5), =echo= (×2), =chronoa= (×2). A rule that stats the first token and disables on failure would switch off 56% of a working store, including hooks belonging to four other fleets. It is also blind to the gap between the check and the use — see the note below.
- *The exit-127 half alone is unsound.* 127 is also what a script returns when it deliberately exits 127, or when a command *inside* the script is not found. Requiring the path to be absent as well makes the conjunction provable.
- *Neither half is stable across a redeploy.* Five of the seven absolute-path hooks on the live store belong to fleets that rewrite their own scripts. An =rm= + =cp= redeploy of =/home/ryota/.local/state/acefix/log-event.sh= that overlaps a matching event produces a genuine 127 *and* a genuine =ENOENT= at the same instant. That is why the wall-clock floor is required here too, and why the action needs an operator: a redeploy cannot keep failing for 15 minutes without someone noticing for other reasons.

*A note on =stat= versus =execve=, replacing a claim that was asserted without evidence.* /[Superseded: 2026-08-03 — revisions 1 and 2 said a static check is "blind to an autofs path, which can return =ENOENT= to =stat= and still resolve when the shell execs it". *That was asserted, not measured; there is no autofs on this host and root is ZFS, so it could not have been.* Withdrawn in favour of the weaker claim below, which needs no filesystem-specific behaviour and which the code establishes on its own.]/ =stat= and =execve= are two syscalls at two instants with an arbitrary gap between them, and nothing makes the pair atomic. Any path whose existence varies in time — a rig mid-rebuild, a script being replaced by =rm= then =cp=, a filesystem being mounted — can therefore disagree between the check and the use, in either direction. That is enough to disqualify a static check as a *sole* criterion without appealing to any particular filesystem, and the redeploy race above is a concrete, reproducible instance of it. The same reasoning applies to =cwd= and to the command path alike; revisions 1 and 2 applied it only to the command path, which was inconsistent.

**** <<where-stat>>Where the =stat= calls happen

*Every =stat= in R1 and R2 is evaluated in the store process, and =ever hook gc= is a thin client that renders what the server computed.* The =hook_gc= request body carries no path data for exactly this reason.

This has to be said out loud because =ever= is a network client: =--address/-a= and =--port/-p= exist with =EVER_HOST= / =EVER_PORT=, and this fleet's own conventions require workers to address a store explicitly. An implementer who puts the =stat= next to =gc='s output formatting — which is where it naturally wants to live — makes =ever hook gc --yes -a other-host= evaluate the evidence against the *operator's* filesystem. Every absolute path belonging to hooks on that host then reads =ENOENT=, and the report is a list of healthy hooks.

The fifth commit found the principle for names: *the check must happen where the mutation happens.* It applies unchanged to evidence — *the =stat= must happen where the hook would have run* — and revisions 3 and 4 applied it to the resolver and not to the paths.

The conjunctions do defend against getting this wrong, which is why it is a correctness statement rather than a hole: R2 also requires =last_exit_status == 127=, =consecutive_failures >= K= and a 15-minute streak; R1 also requires =cwd_missing_since != null=, which is a daemon observation. A healthy hook on a remote store therefore survives a wrongly-located =stat=. That is the two-observer design defending against an error nobody anticipated — but it is not a reason to leave the location unstated, and W1c has no second observer at all.

**** W1 — flagged, never reclaimed by =--yes= alone

Reported, never acted on without =--include-flagged=:

- *W1a* — =state == "quarantined"= with =consecutive_failures >= 20=; or
- *W1b* — an R2 token match on a hook that has never dispatched; or
- *W1c* — =stat(cwd) == ENOENT= on a hook that has never dispatched (the =#17/#19/#157/#158= class), *and* =now − created_at >= 24 h=.

/[Superseded: 2026-08-03 — the flag was =--include-quarantined= through revision 4, which named only W1a while acting on all three, so an operator sweeping quarantined hooks would also have disabled never-dispatched ones without the flag saying so. Renamed to =--include-flagged=, which is what it does.]/

The 24-hour floor on W1c is new, and it is there because W1c is the one branch in the whole document with *no second observer*: a never-dispatched hook has no daemon observation by construction, so =gc='s single =stat= is all the evidence there will ever be. The document withdrew exactly that evidence standard from RECLAIMABLE two paragraphs above — "one sample, taken at an arbitrary instant, applied to the population the store knows the least about" — and it should not survive here just because a flag guards it. =created_at= is the only store-side evidence a never-dispatched hook has, so it is what the floor is built from, and 24 hours is enough to separate "registered thirty seconds ago from a directory a rig is about to create" from "abandoned in April". W1b needs no such floor: a qualifying-token match on a hook that never dispatched still has the token test behind it, and the token is immutable.

All three remain *visible* without any flag, which is all Open question 3 ever needed, and an operator who agrees reclaims one with =ever hook disable <id>= — targeted, single, already in this document, and requiring them to type the id.

This keeps a property worth naming: *every automatic action in this document is backed by an outcome the store actually observed.* Nothing acts on a hook the store has never run.

       registered 2026-04-11 (114d ago), never succeeded, cwd ENOENT: /tmp/ever-orch
       (no observed failure; reclaim with `ever hook disable 17` or --include-flagged)

2 reclaimable, 2 flagged, 0 reclaimed (dry run; pass --yes to act)
#+end_example

Every flagged line carries =last_success_at= (or "never succeeded" plus the registration age), because that is the fact the operator's decision turns on and nothing else in the line supplies it.

Rules:

- The *reclaimable* section contains only R1 and R2 matches. Every line carries the rule name and the evidence that proves it — the path that returned =ENOENT=, the recorded =last_exit_status=, and the failure count that supplies the 15-minute floor. Expired hooks are not listed: the daemon has already disabled them and there is nothing for =gc= to decide.
- The *flagged* section contains W1 and nothing else. It is informational. =--yes= alone does not touch it.
- A hook that is =armed= with =consecutive_failures == 0= appears in neither section, except under R1's "never dispatched" branch — which requires =gc= to have just proved its =cwd= gone. A working hook whose =cwd= exists is not a candidate under any rule.
- Lag is *not* printed by =gc= at all, to remove the temptation to act on it. It belongs in =hook list=, which is =ever--hook-scan-cursor-and-lag='s surface.
- All paths are printed *exactly as stored*. No =~= abbreviation, no =$HOME= substitution: the evidence line has to be something a reviewer can paste into =stat=, and R2's own qualification test disqualifies any token containing =~=.

*** <<purge>>=--purge= takes explicit ids, and only ids

/[Superseded: 2026-08-03 — the first revision spelled this =gc --purge --state disabled --yes=, a state filter with no target, which on this store would delete *every* disabled hook across six fleets in one command. The state filter is withdrawn.]/

=ever hook gc --purge <id> [<id>…] --yes= removes the named hooks. It refuses — non-zero exit, nothing changed, not even partially — if *any* named hook:

- is not =disabled=; or
- has been =disabled= for less than one hour by =disabled_at= (printed, so the operator can see how long is left); or
- does not exist.

There is no bulk form, no =--all=, and no state selector. Removal is irreversible and irreversible operations get typed-out ids.

In dry-run mode =--purge <id>…= prints one line per named hook — id, name, pattern, command as stored, =disabled_reason=, =disabled_at= and its age — followed by =N would be removed, 0 removed (dry run; pass --yes to act)=. A hook that fails one of the preconditions is printed with the reason it would be refused, and the dry run exits non-zero so a script notices.

*** The one-step invariant

*No command introduced by this document takes a hook from =armed= to removed.* Removal via =gc --purge= requires the hook to be =disabled= already, and to have been =disabled= for an hour.

/[Superseded: 2026-08-03 — revisions 1 and 2 stated this as "no single command takes a hook from =armed= to removed" and justified it with "=ever hook rm <id>= keeps its current behaviour: it is explicit, single-target, and already exists". Both halves are wrong. =hook rm= accepts *id or name*, and in the name form it is neither explicit nor single-target — it is first-match over an array whose order is an artefact of past deletions (see [[#names][Name addressing]]) — and it takes an =armed= hook to removed in one step with no confirmation. So the invariant was already false in shipped code, and it was the argument that made =--purge= acceptable.]/

=ever hook rm= predates this document and remains the documented single-target escape hatch. It is *not* covered by the invariant, and this document narrows it in exactly one way: the name form must refuse ambiguity like every other name-addressed verb. Rewriting =hook rm='s client-side resolve-then-act to go through the server is *not* required here — it is a pre-existing narrow window on a verb this document does not add — but it is named in [[#names][Name addressing]] so that nobody reads it as the pattern to follow.

*** Why =--purge= exists at all

Because [[#downgrade][downgrade re-arms everything]]. Disabling is not durable against a rollback of the store binary; removal is. An operator who has decided a hook is dead and expects to roll back needs a reclamation that survives.

** <<names>>Name addressing, and why four new verbs cannot inherit the current resolver

This document adds =enable=, =disable= and =renew= as =<id|name>= verbs, and revision 2's criterion 27 spoke of hooks "named on the same command line" for =--purge=. That takes the number of name-addressed verbs from one to four, on a resolver that cannot detect ambiguity. Fixing it is therefore a prerequisite of this change rather than a follow-up.

*** What is true today, at =142d5e66=

Verified by reading the source and reproduced on an isolated store (own =--data-dir=, port 7951, torn down):

- =HookTable.addWithCursor= performs *no uniqueness check* on =name=. Registering two hooks called =guard= succeeds silently, no warning.
- =HookTable.removeByName= and =HookTable.findIdByName= both =return= on the *first* array match — and *neither has a single call site anywhere in the tree, including tests*. They are dead code that looks like the right primitive. =handleHookRm= in the CLI does its own first-match scan with a =break=.
- *The wire protocol has no name-addressed operation at all.* =UnregisterHookRequest= carries =id: u64= and nothing else. So the CLI's name form is implemented entirely client-side: =listHooks()= on one connection, scan the result, *reconnect* ("since we consumed the connection for listHooks"), then =removeHook(id)=. That is resolve-then-act with the table mutable in between — the daemon auto-removes =once= hooks on its own schedule, and ids are reusable after the =next_id= reset that [[#load-hardening][criterion 5]] measures. Narrow, but it is a window, and it is the pattern a new verb would copy.
- =removeByName= uses =swapRemove=, which moves the *last* element into the freed slot. Measured: after =hook rm guard= removed =#4=, =hook list= came back =#6, #5= — the array reordered. *Which of two same-named hooks a verb hits is not the oldest, not the lowest id, and not predictable from anything an operator can see.* The live store shows the same churn: its array order is =[3, 4, 10, 6, 7, 8, 9, 11, 12, 220, 193, 170, 221, 186, 226, 227]=.
- Measured end to end: =ever hook rm guard= printed =Hook 'guard' (#4) removed.=, left the other =guard= live, and *the same command run again removed a different hook*.
- *The repo already decided this question the other way for timers.* =TimerTable.add= does =if (std.mem.eql(u8, t.name, name)) return error.AlreadyExists;=. Timer names are a unique key. Hook names look like one, are used like one, and are not one.
- *9 of the 16 live hooks have =name: null=*, and every resolver skips them. The name form cannot address 56% of the production store at all — including all nine PATH-resolved hooks.

*** What this document requires

Four changes, the first three of which are prerequisites:

1. *=hook add= rejects a duplicate =--name= with =error.AlreadyExists=*, exactly as =TimerTable.add= already does, with the same error and the same shape. Two lines, with the precedent in the same repo. Over the wire this is =ErrorCode.conflict= (409), which already exists.
2. *Every name resolver returns =error.Ambiguous= when more than one hook matches* — also =ErrorCode.conflict=, with every candidate id in the message. The CLI prints them and exits non-zero without acting. This is needed *in addition to* (1), because (1) cannot retroactively de-duplicate a store that has been accumulating hooks since April.
3. *Resolution happens server-side, in the same critical section as the mutation.* The request body for each new verb carries ={ id: ?u64, name: ?[]const u8 }=. *Exactly one must be set; both-set and neither-set are =ErrorCode.bad_request= (400), which =server.zig= already uses for malformed bodies in sixteen places.* The server resolves the name under the =HookTable= mutex it is about to mutate under. The client never lists-then-acts.

   This is not decoration on (2). Ambiguity detection performed client-side still leaves the resolve-then-act window: the answer is correct when it is computed and stale when it is used. Doing both under one lock closes the ambiguity and the window together, and it costs nothing, because every one of these verbs already needs a server round trip to do its actual work.

   *And it is not a new pattern — it is the one the subsystem next door already uses.* =RemoveTimerRequest= is =struct { name: []const u8 }= (=message.zig:170=), and =handleRemoveTimer= resolves it server-side with =tt.remove(parsed.value.name)= under the timer table's own lock (=server.zig:420=). So *timers address by name over the wire and resolve server-side; hooks address by id and resolve client-side.* This change makes hooks consistent with timers. Note that the two precedents are distinct and both are needed: =TimerTable.add= (=timers.zig:331=) is the precedent for *uniqueness*, =handleRemoveTimer= for *resolution*. Cited separately so a future reader can check each in one grep.

   *This requirement constrains how =HookTable= must be shaped, and getting it wrong hangs the store rather than failing a test.* =HookTable.lock= is =while (!self.mutex.tryLock()) std.atomic.spinLoopHint()= (=hooks.zig:103=), over a =tryLock= that is =@cmpxchgStrong(.unlocked → .locked)=. The mutex is *non-reentrant and has no owner check*, so a thread that already holds it and tries to take it again does not panic and does not deadlock-detect — it spins forever. And nine of =HookTable='s public entry points acquire the lock — seven directly (=addWithCursor=, =remove=, =removeByName=, =findIdByName=, =count=, =updateCursor=, =snapshot=) and two transitively (=add=, =addFull=, both delegating to =addWithCursor=). So a server-side resolver written the obvious way — take the lock, call =findIdByName=, mutate — spins on its second line.

*Three of those seven are readers*, and that is what makes the failure total rather than local: =snapshot= is a reader, and it is the one the daemon calls.

   The consequence is worse than a wedged connection. The daemon's =pollAndExecute= calls =snapshot=, which takes the same lock, so one such request permanently wedges *the entire hook subsystem* and burns two cores spinning, with no error anywhere. That is the failure mode of the incident this document exists because of, re-created by the fix for a different one.

   So the shape is fixed, not a matter of taste:

   - =HookTable= exposes *one public entry point per verb*, taking a reference rather than an id: =HookRef = union(enum) { id: u64, name: []const u8 }=. Each entry point locks *once*, resolves inside, mutates inside, calls =saveLocked= inside, and returns the resolved id.
   - Resolution is an internal =resolveLocked(ref) !u64= that *never takes the lock* and assumes it is held. It scans the whole array — which is also what makes =error.Ambiguous= detectable, so making it non-locking and making it ambiguity-aware are the same edit.
   - The =*Locked= suffix is the in-file convention for exactly this and is already documented that way: =saveLocked= carries "Must be called with lock held" (=hooks.zig:384=), and =topic.zig= uses =tipForPatternLocked= alongside its unlocked variant.
   - *No public =HookTable= method may be called while the table lock is held* — not by another =HookTable= method, and not by a server handler. The property is about the lock, not about who the caller is: =add= and =addFull= delegate to =addWithCursor= today and are safe precisely because they take no lock of their own, so a rule phrased as "no public method may call another" would forbid a benign existing delegation while permitting nothing extra.
   - *Lock order is =TopicManager= before =HookTable=, never the reverse* — see [[#lock-order][Lock ordering]].

   Note that the existing precedent at =server.zig:306–310= — =lockForHookRegistration()= / =tipForPatternLocked()= / =addWithCursor()= — looks like a counterexample and is not: the lock held there belongs to the =TopicManager= and the mutator locks the =HookTable=. *Two locks, no re-entry.* It is the right pattern for that pairing and the wrong one to copy here, where the resolve and the mutation are on the same table.

   That site is doing more than avoiding re-entry, though, and reading it only as "two locks" is what hid the next problem for two revisions: *it establishes a lock order*, and this document's entry points can invert it. See [[#lock-order][Lock ordering]] immediately below.

*** <<lock-order>>Lock ordering: =TopicManager= before =HookTable=, never the reverse

/[Superseded: 2026-08-03 — revision 5 specified a =HookTable= entry point that resolves and mutates under one lock, and separately specified that =hook enable= "prints a bound on the backlog before acting", where the bound is =nextOffset() − cursor= or =non_marker_count − cursor= — *=TopicManager= state*. The natural implementation computes it inside the entry point, which takes the =TopicManager= lock while holding the =HookTable= lock. Shipped code at =server.zig:305–311= takes the opposite order on the default =hook add= path. Two threads, opposite orders, both =tryLock= spins: the same permanent silent two-core wedge as the re-entry case, reached by a different route, and *criterion 28h does not catch it* because it runs the verbs serially and an inversion needs two threads.]/

*The order is =TopicManager= → =HookTable=.* It is not a free choice: =handleRegisterHook= already takes it on the default =--from tail= registration path, that path is shipped and load-bearing (it is what makes a new hook observe only future events), and reversing it there would reintroduce the race =hook-registration-cursor.org= was written to close.

So, for every verb in this document:

- *Nothing calls into the =TopicManager= while holding the =HookTable= lock.* No exceptions, including for a value that is only going to be printed.
- A verb that needs =TopicManager= state for *display* computes it *after* the =HookTable= entry point has returned, using the id it returned. =hook enable='s backlog bound is display-only and an upper bound already ([[#reversibility][why]]), so computing it a moment later costs nothing. "Before acting" means before the *replay*, which is what the operator cares about and what criterion 29 tests — not before the state change.
- A verb that needs =TopicManager= state *to decide what to write* takes the =TopicManager= lock *first* and holds it across the =HookTable= call, exactly as =handleRegisterHook= does.

**** =hook enable --from tail= is the case that needs the second form, and it has an ordering trap of its own

It has to resolve a hook (=HookTable=), compute that hook's tip from its pattern (=TopicManager=), and write the tip to its cursor (=HookTable=) — so it cannot be one critical section in either order. The sequence is:

1. =HookTable=: resolve the ref, read the hook's pattern, and *set =state = "disabled"= with =disabled_reason = "enable-in-progress"=*, then =saveLocked=. Returns the id and a copy of the pattern. This is the section that carries the B5 property — name resolution and the decision it authorises are atomic — and it is also what makes the hook quiescent for steps 2–3.
2. =TopicManager=: =lockForHookRegistration()=, =tipForPatternLocked(pattern)=.
3. =HookTable=, *still holding the =TopicManager= lock*, addressed *by the id from step 1*: set =cursor = tip= and =state = armed= together, clear =disabled_reason=, then =saveLocked=.

*Step 1 must quiesce the hook, not assume it is already quiescent.* /[Superseded: 2026-08-03 — revision 6 said step 1 should "leave =state= as it is", on the reasoning that tick step 1 skips =disabled= hooks before the fetch. That is true and it is not enough: =hook enable= is defined to work on a *quarantined* hook too, and a quarantined hook is eligible for dispatch as soon as =next_attempt_at= passes — which can be during steps 2–3. The quiescence was a property of the *state the caller happened to start from*, not of the sequence, so the sequence was correct only for the case that had been tested.]/ Writing =disabled= in step 1 makes it a property the sequence establishes, for every starting state.

Step 3 must set the cursor and arm the hook *in the same critical section*, and the whole of steps 2–3 must stay under the =TopicManager= lock. Otherwise there is a window in which the hook is =armed= with its old cursor, and the daemon polls every 500 ms: it would dispatch the entire backlog that =--from tail= exists to skip — the replay flood, delivered by the flag that opts out of it. Holding the =TopicManager= lock across step 3 also means no publish can interleave between the tip read and the arm, which is the same guarantee =handleRegisterHook= gives and for the same reason.

The distinguished =disabled_reason= is not cosmetic. If the store dies between steps 1 and 3, the hook is left =disabled=, which is the safe direction — it fails closed, and it is recoverable with a second =enable= — and =enable-in-progress= tells whoever finds it that it was not disabled by expiry, by =gc= or by an operator. A bare =disabled= with no reason would be a mystery on a store carrying six fleets' hooks.

Step 1 and step 3 are two =HookTable= critical sections, and that is acceptable where the B5 window was not, because *step 3 is addressed by id rather than by name*. A hook removed in between yields =error.NotFound= and no action; it cannot resolve to a different hook.

Plain =hook enable= (no =--from tail=) needs none of this: one =HookTable= entry point, then the display bound computed afterwards from the returned id.

   It is also the cheaper design, which is worth stating because it reads like a concession to a review and is not one. The three verbs are new opcodes whose request bodies must be designed in this document either way, so ={ id: ?u64, name: ?[]const u8 }= versus ={ id: u64 }= is a field choice on a struct that has to be written regardless — not new surface. The id-only alternative is *more* expensive: it forces an extra =list_hooks= round trip per invocation plus the scan logic, which is exactly the code =handleHookRm= already contains and which this document is trying not to replicate four more times.

   The line is drawn at =hook rm= deliberately. Changing =unregister_hook 0x08='s body would be a breaking change to an existing opcode, and that *would* be creep. So the store ends up with two name-resolution semantics — atomic for the three new verbs, windowed for =rm= — which is a real asymmetry, accepted because ambiguity is the safety property, the window is narrow, and closing it costs a protocol break on a verb this document does not add.

   It also decides what happens to =removeByName= and =findIdByName=, which today are first-match, uncalled, untested — and self-locking. *Delete them, or refactor them into non-locking =*Locked= helpers with ambiguity detection added.* /[Superseded: 2026-08-03 — revision 4 offered "either wire them up with ambiguity detection added and test them, or delete them". The wire-them-up branch as written is *unimplementable*: they take the lock themselves, so a resolver holding it spins forever. Wiring them up unchanged is not one of the options.]/ Leaving a self-locking first-match helper sitting next to four new callers is how both defects — the ambiguity and the hang — would propagate into the verbs meant to fix them.
4. *Destructive verbs take ids only.* =gc --purge= accepts =<id>…= and nothing else — which is also the answer to =--purge='s shape, so the two close together.

Why each of the new verbs makes this worse than =hook rm= alone did:

- =hook disable guard= disables an unpredictable one of two, prints success, and *leaves the other firing*. The operator believes the job is done. That is the decisive failure mode for this whole item — a hook that should have stopped keeps working — arriving through a door that has nothing to do with R1 or R2.
- =hook enable guard= is worse, because it is a *recovery* path: after an incident the operator re-arms one of two and believes recovery is complete.
- =hook renew guard= extends the wrong hook's TTL and lets the right one expire — a silent reclamation performed by the command that exists to prevent one.
- =gc --purge … guard --yes= irreversibly deletes an unpredictable hook, and the stated reason =--purge= exists is that it survives a downgrade.

And the population is not contrived: five of the sixteen live hooks belong to fleets that name their own, and fleet naming conventions converge by construction — =notify=, =guard=, =tick=, =watch=. Two fleets independently choosing =notify= is the expected case, not the unlucky one.

*** Two adjacent facts that belong here

- *Auto-generated names are not a workaround.* The default is ={pattern}-{id}=, which collides after the =next_id= reset that [[#load-hardening][criterion 5]] describes. Backfilling names for the nine unnamed live hooks would therefore *need* change (1) first, not instead of it.
- *Ids are not stable identifiers across a =next_id= reset either.* The load-path hardening fixes the cause, but a runbook or script holding =#193= addresses a different hook after such a reset. Four new verbs are about to be addressed by id, so this is worth saying once: ids are stable in normal operation and are not an audit key across a registry loss.

** Reversibility <<reversibility>>

*** =ever hook enable <id|name>=

The name form refuses ambiguity and cannot address the nine live hooks with =name: null=; see [[#names][Name addressing]].

Sets =state = armed=, =consecutive_failures = 0=, =next_attempt_at = null=, =last_error = null=, =disabled_at = null=, =disabled_reason = null=.

=expires_at= is handled by cases, *not* cleared unconditionally:

| Was disabled by           | =expires_at= after =enable=                                                        |
|---------------------------+------------------------------------------------------------------------------------|
| =expired=                 | cleared, unless =--ttl= given — re-arming into an instant re-expiry is a trap      |
| anything else, TTL future | *preserved unchanged* — the registrant's bound survives an unrelated disable       |
| anything else, TTL past   | *refuse*: print the stored =expires_at= and require =--ttl <dur>= or =--clear-ttl= |

/[Superseded: 2026-08-03 — the first revision cleared =expires_at= on every =enable=. That is right for the expiry case and wrong everywhere else: a rig that registered =--ttl 8h= (exactly the discipline this document argues for) would have its bound silently removed by an operator disabling and re-enabling the hook for an unrelated reason, turning a bounded registration into the immortal debris the document exists to prevent — via the document's own recovery command.]/

=ever hook disable <id|name>= is the inverse, with =disabled_reason = "operator"=. It does not touch =expires_at=.

*** What "with its cursor" actually means

The cursor is *not touched* by disable, by expiry, by quarantine, or by enable. Concretely, for an event published while the hook was disabled:

- The event is still in the log — Ever never deletes it on a hook's account.
- On =enable=, the hook resumes from its stored cursor, so *that event is delivered*, along with every other matching event since. Delivery is bounded at 100 events per poll cycle and 16 concurrent children.
- This can be a large burst. =ever hook enable= therefore *prints a bound on the backlog before acting*, and accepts =--from tail= to skip it and resume at the head instead. For an exact-topic hook the number is exact: =non_marker_count − cursor=. For a prefix/wildcard hook it is =nextOffset() − cursor=, which counts *unscanned log entries across all topics*, not matching events — on this store the log holds ~116,700 events across dozens of topics while a given prefix hook matches a small fraction. It must therefore be printed as an upper bound (=up to N events pending=), and the wording must not imply the hook will fire N times. Computing the exact figure would mean the full-log scan this whole document is trying to avoid.
- Default is to replay, because the stated non-goal is that nothing is lost silently. =--from tail= is the explicit opt-out, and it reuses the vocabulary =hook add= already has.

One consequence worth stating plainly rather than discovering: re-enabling a long-disabled prefix/wildcard hook restores its contribution to the full-log rescan until it catches up. On a store without round-4 item 1's fix, that is the incident's pathology re-armed on purpose. =enable= should say so in its output when the pending count is large.

Wire protocol: four new request/response pairs. The last opcodes in use are =hook_logs = 0x0F= and =hook_logs_ok = 0x8F= (=src/protocol/message.zig=), so the new pairs are *=0x10–0x13= / =0x90–0x93=*, in the order =hook_gc=, =hook_enable=, =hook_disable=, =hook_renew=. Existing =list_hooks_ok= gains the new fields. The old-client half of compatibility is free — =decodeBody= sets =ignore_unknown_fields=, so a client built before this change ignores them. The new-client half is *not* free: =protocol.HookInfo= (=message.zig:144=) must gain the same thirteen fields with the same defaults, or a new client talking to an older store fails to decode a response that legitimately omits them. See [[#record-fields][Record format]].

** <<reason-strings>>Reason strings

Fixed vocabulary, so that scripts and reviewers can match on them.

=disabled_reason=: =expired= (daemon), =operator= (=hook disable=), =gc-cwd-missing=, =gc-command-missing=, =gc-quarantined= (all =gc --yes=), and =enable-in-progress= — the transient written by step 1 of [[#lock-order][=enable --from tail=]], which is only ever observed if the store dies mid-sequence and tells the finder that nothing decided this hook was dead. The =gc-= prefix is not decoration — it is how a reader tells at a glance that a human consented, which after the [[#why-gc-only][daemon/operator split]] is the distinction that matters.

=last_error=: =exit=, =signal=, =cwd-missing=, =spawn-failed=, =timeout=, =shutdown=. The last two do not increment =consecutive_failures= (see [[#daemon-signals][Signals the daemon sent itself]]).

** <<downgrade>>Downgrade

Measured, not assumed. An older binary reading a file written by the new one:

1. parses successfully (=ignore_unknown_fields = true=);
2. ignores =state=, =expires_at=, =consecutive_failures= and the rest;
3. polls *every* hook, including the disabled ones, because it has no concept of state;
4. rewrites =hooks.json= without those fields on the first cursor update — measured to happen within one poll cycle of the first matching event.

Every disabled hook re-arms, every TTL is erased, and the failure history is gone. There is no way to prevent this from the new binary's side, because the old binary does not check a version field. What this document can do, and does:

- write =version: 2= so a *future* reader can detect the round trip;
- make =ever hook gc= (report mode) the documented pre-downgrade step, since its output is the only record of what was disabled and why;
- provide =--purge=, because removal is the only reclamation a downgrade cannot undo.

This must be stated in the release notes for the change. A downgrade is one-way and lossy.

* Design Details

** <<rejected-static>>Rejected: stat the command path before spawning

The triage draft proposes "on dispatch, stat the resolved command first: unrunnable means record the failure and disable rather than spawn-and-fail". Rejected as the *sole* criterion, for the reasons in [[#gc-rules][R2]]: =hook.command= is a shell fragment, 9 of 16 live hooks have a non-path first token, =stat= says nothing at all about anything reached through =PATH=, and =stat= and =execve= are two syscalls at two instants with no atomicity between them. The static check survives as one half of a conjunction evaluated by =gc=, never on its own and never in the daemon.

The =cwd= check *is* done before spawning, because =cwd= is a stored absolute path with exactly one consumer and no ambiguity — but it only records a failure, it does not disable.

** Rejected: reaping on lag

Covered under Non-Goals; the structural reason (polymorphic cursor) is worth repeating here because it is not obvious from the draft: comparing =Hook.cursor= to the log head is only meaningful for prefix/wildcard hooks. For an exact-topic hook the cursor is a per-topic skip count and the comparison is a category error. Any implementation tempted to add "lag" to the GC input set should be sent back to =hooks.zig='s =Hook.cursor= doc comment.

** <<rejected-ratio>>Rejected: a failure *ratio*

Hook #186 failed 139 times consecutively and then succeeded on a run of comparable length without intervention. A ratio computed over any window containing both is meaningless, and a ratio computed over the failure run alone is 100%. Consecutive count, reset on success, is the only accounting that distinguishes "broken" from "flaky" — and the reset is what makes it self-healing.

** <<tick-ordering>>Ordering inside the daemon tick

/[Superseded: 2026-08-03 — the first revision listed the =cwd= check as step 4 of five and asserted "steps 1–4 must all precede the fetch" and "step 4 is per-tick, not per-event". Those are mutually inconsistent: before the fetch there is no event and no offset, so "advance the cursor exactly as a spawn would" had no defined value, and the only per-tick advance available for a prefix hook is =nextOffset()=, which would consume the entire backlog on the first tick after a =cwd= vanished. Resolved below in favour of *per-event, after the fetch*.]/

=daemonLoop= gains no new phase. Inside =pollAndExecute=, per hook, in order:

1. =state == "disabled"= → skip. *No fetch.*
2. =expires_at= reached → transition to =disabled=, log once, skip. *No fetch.*
3. =next_attempt_at= in the future → skip. *No fetch.*
4. *Fetch* the batch (up to 100 events).
5. For each event in the batch, immediately before the fork: =stat(cwd)=. On =ENOENT=, set =cwd_missing_since= if unset, record the failure (once per cycle, per [[#counting][the counting rule]]), advance the cursor as a spawn would, and move to the next event. On success, clear =cwd_missing_since= and fork as today.

R2 has no step, because it is not a daemon rule — =gc= evaluates it. The only thing the daemon does toward it is record =last_exit_status=, and classify a 127 with a qualifying, absent token as attributable ([[#attributable][what counts]]).

Steps 1–3 precede the fetch, and that is what criterion 14 and the "move the quarantine check after the fetch" mutation check both test. *Step 5 is per-event and necessarily follows the fetch*, because it stands exactly where the fork stands and needs the same event and offset the fork would have had.

The consequence, stated because it bounds the damage: a hook whose =cwd= disappears loses *at most one batch of events per poll cycle* and *contributes at most one failure per cycle*, so it reaches K in K cycles, exactly like any other failing hook. It does not accumulate failures without matching events, and it does not consume a backlog it never fetched. Both of those were true under the withdrawn per-tick reading.

** Persistence pressure

=HookTable.saveLocked= rewrites the whole file on every mutation, and =updateCursor= already calls it per delivered event. Failure accounting adds writes on the failure path. This is not a new problem and this document does not solve it, but the implementation must not add a save per *tick* — only per state transition and per delivered event, as today.

** <<scope-boundary>>What this does not fix

The incident's CPU burn came from =fetchPatternByOffset= walking the whole log for hooks whose pattern never matches. This document reduces that cost only as a side effect: a disabled hook is not polled, and a quarantined one is polled hourly instead of twice a second. But:

- a hook that *never fires* can never accumulate failures, so *no daemon mechanism here will ever quarantine or disable it*. It is reclaimable only by TTL, or by an operator running =gc=. The incident's most expensive hooks by scan lag (=#17=, =#19=, =#157=, =#158=, all at cursor 0) were in exactly that category — and R1's "never dispatched" branch is specifically there so that =gc= can still prove their =cwd= is gone and offer them to an operator. That branch is the one place this document reaches the incident's actual cost driver, and it reaches it only through a human.
- the reduction depends on someone having run =gc --yes=, or on a TTL having been set at registration. There is no unattended path from "dead" to "not polled".

The general fix is =ever--hook-scan-cursor-and-lag= (round-4 item 1: advance the cursor on scan). The two are complementary and neither substitutes for the other. Do not justify this document with the 2,004,113-events-per-cycle figure; that number belongs to item 1.

* <<repoint-coupling>>Coupling with =ever--hook-repoint-and-resilience=

The triage draft says to land this with round-3's =ever--hook-repoint-and-resilience.org= — "or the repoint path has nothing to repoint from". *That document is not scheduled in this batch and will not be implemented alongside this one.* This design therefore stands alone. What that costs, precisely:

** Already landed from that draft

Its third goal — a =--from tail= default so "follow new events only" is a declaration rather than offset arithmetic — *shipped*. At this base, =ever hook add= with neither =--from= nor =--from-beginning= sends =start_cursor = null= and the server resolves the tip under the publish lock (=main.zig= =handleHookAdd=; =air/v0.1/hook-registration-cursor.org=, History 2026-04-21 and 2026-04-28). Only the first two goals remain open.

** What is degraded without the repoint half

1. *A disabled hook can only come back at its original command.* There is no =hook update=, so a hook whose script moved must be removed and re-added, which loses the cursor (a new registration starts at the tip). =enable= restores the registration, not a corrected one.
2. *Events arriving while a hook is broken are still lost.* The =cwd= guard advances the cursor without spawning, matching what a spawn that exits 127 does today. The alternative — freezing the cursor — is the time bomb round-3 names explicitly: the moment the script returns, the hook replays the whole backlog. Round-3's answer is a separate "attempted" cursor, and that is the repoint half's design to make. *Reversible in this document means the registration comes back, not the missed events.* Quarantine is a partial exception: while a quarantined hook is not yet due it fetches nothing and its cursor stands still, so events in that window are deferred rather than dropped — but the attempt that ends the window still advances the cursor over its batch whether or not the dispatch worked.
3. *No "skip and warn" on a missing command.* This document's answer is a =gc= report plus an operator's =--yes=, which is slower than skip-and-warn and needs a human. A store that wants the hook to keep itself alive across a script's disappearance needs round-3.

** What a later repoint implementation must inherit from this design

Three requirements, stated so that whoever implements repoint does not have to reverse-engineer them:

1. A successful =hook update= must set =state = armed=, =consecutive_failures = 0=, =next_attempt_at = null=, =last_error = null=, =disabled_reason = null=. Otherwise a repointed hook stays quarantined or disabled and the repoint appears to do nothing.
2. If repoint introduces a separate "attempted" cursor, failure accounting must key on *delivery* outcomes only. Counting both an attempt and its delivery would double the effective K.
3. =state= is a string with unknown values tolerated (treated as =armed=, logged once). Repoint may add its own state without a coordinated release.
4. If repoint adds a per-hook =--timeout=, a kill originating in =checkTimeouts= must start counting as a failure *for hooks that declared one*, because the bound was then consented to. Hooks with no declared timeout keep the exclusion in [[#daemon-signals][Signals the daemon sent itself]].

** =once= hooks

=hook.once= predates all of this and interacts badly with every new state, so the interaction is specified rather than left to be discovered. In shipped code, =processHook= calls =hook_table.remove(hook.id)= immediately after the *spawn*, before any outcome is known. So a =once= hook that fails is deleted anyway, and can be neither quarantined, nor disabled, nor recovered.

That is the one place where this document's headline — "nothing is deleted automatically, ever" — is already false in shipped code, and it is false in a way this document does not fix. The rules:

- A =once= hook *can* carry a TTL, and expiry disables it before it ever fires. That is the only reclamation that reaches it.
- The =cwd= guard applies: if =cwd= is =ENOENT=, no fork happens — and because the removal is coupled to the spawn, *the hook is not removed either*. It records a failure and stays registered, so a =once= hook is the one case where the guard also prevents a silent self-deletion.
- A =once= hook cannot reach K by dispatching, because it is gone after the first dispatch. It can reach K through the =cwd= guard.
- =gc= treats a =once= hook exactly like any other: R1 can reclaim it, R2 effectively cannot (it never survives a dispatch to record a 127).
- Making removal-on-success rather than removal-on-spawn is a behaviour change this document does not make. It belongs with the attempted-versus-delivered cursor split. Flagged here so it is not silently inherited as acceptable.

* Acceptance

Each criterion is checkable from this document alone, against a store built from the change, with no access to the author. "Isolated store" means a store started with its own =--data-dir= and a port other than 7890.

*Pacing convention, which several criteria depend on.* Because =consecutive_failures= increments at most once per hook per poll cycle ([[#counting][How "consecutive" is counted]]), any criterion that says "drive the hook to N failures" means *N matching events published at least one poll interval (500 ms) apart*. Publishing N events at once produces *one* failure, not N — the hook spawns the whole batch before the first reap. Where a criterion below says "5 paced events" this is what it means, and a criterion that publishes them together is testing something else.

** Migration and durability

1. *No-op on an existing store.* Take a =hooks.json= written by the pre-change binary containing at least three hooks with different =cursor= values. Start the new binary against it. =ever hook list= reports the same number of hooks, the same ids, names, patterns, commands and cursors, and every hook shows state =armed=.
2. *Round trip.* After (1), publish one event matching one hook so a save occurs. Re-read =hooks.json=: every row now carries =state="armed"=, =consecutive_failures=0=, =last_exit_status=null=, =expires_at=null=, and the file carries =version: 2=. No pre-existing field changed except =cursor=.
3. *Disabled survives restart.* Disable a hook (=ever hook disable <id>=), stop the store, start it again. =hook list= shows it =disabled= with the same =disabled_reason=, and publishing a matching event produces no new file under =data/hooks/= and no new process in =hook ps=.
4. *Quarantine survives restart.* Drive a hook to =quarantined= (below), stop and start the store, and confirm =consecutive_failures= and =next_attempt_at= are unchanged in =hook list= and in =hooks.json=.
5. *Unparseable file is not destroyed.* Corrupt =hooks.json= (delete one required key from one row). Start the store. It logs an error naming the file, renames it to =hooks.json.unparseable-<ms>=, and starts empty. Registering a new hook does *not* overwrite the renamed file. *This criterion regresses today: at =142d5e66= the same input silently takes 7 hooks to 0, logs nothing, and the next registration rewrites the file with =next_id= reset to 1.*
6. *Unknown state is loud and safe.* Hand-edit one row to =state: "future-state"=. On start the store logs a warning naming that hook id and the value, and the hook behaves as =armed=.
   - *6a — Oversize is not corruption.* Generate a valid =hooks.json= larger than 1 MB (roughly 1,900 hooks at thirteen new fields, or pad one =command= string). Start the store. It logs an error naming the file size and the buffer size, does *not* rename the file, and does not start the hook daemon with a partial table. Distinguishing this from criterion 5 is the point: the two inputs are both "parse failed" and must take different paths.
   - *6b — =HookInfo= tolerates omission.* Build a client from the change and point it at a store built before it (or hand-craft a =list_hooks_ok= body omitting all thirteen new fields). =ever hook list= renders every hook with state =armed= and zeroed counters rather than failing to decode.

** Backoff and quarantine

7. *A filter hook is never quarantined for declining events.* *This is the criterion this design most needs.* Register a prefix hook =fleet.= whose script's last statement is a guard — =printf '%s' "$EVER_DATA" \vert{} grep -q done && <act>= — with *no* trailing =exit 0=. Publish six paced =fleet.worker.status= events, then one =fleet.worker.done=. All seven dispatch, the six declines each exit 1, the =.done= is acted on *immediately and not after a backoff*, and the hook is =armed= throughout with =consecutive_failures= 0. Repeat with the =case=-matched variant (a matched branch whose last command is the predicate): same result. *Measured at =142d5e66=: both shapes produce six consecutive exit-1s while working correctly, so a K that counts generic non-zero exits fails this criterion by construction.*
   - *7a — Non-zero is still visible.* After (7), =hook list= shows the hook =armed= with =nonzero_exits= 6 and =last_exit_status= 0 (the =.done= dispatch succeeded). The signal is displayed; it is simply not an input.
8. *K is 5, and 5 means five attributable failures over at least 60 s.* A hook whose =cwd= has been deleted, driven by 5 paced events, is =armed= after 4 and =quarantined= on the 5th, with =hook list= showing a next-attempt about 30 s out. *Drive the same five failures inside one second and the hook is still =armed=* — the 60 s floor is not satisfied.
   - *8a — A batch is one failure, not many.* Publish 5 matching events *simultaneously* to an always-attributably-failing hook. All 5 spawn (5 new files under =data/hooks/=), and =consecutive_failures= afterwards is *1*, not 5. This is the criterion that pins the counting rule; without it an implementer is free to choose either semantics.
   - *8b — A success in the batch wins.* Point a hook at a command that succeeds on even offsets and fails attributably on odd ones, and publish 4 events together. After the batch is reaped, =consecutive_failures= is 0, =state= is =armed=, and =last_success_at= is set.
8. *The curve.* From =quarantined=, successive failures produce next-attempt gaps of approximately 30 s, 1 m, 2 m, 4 m, 8 m, 16 m, 32 m, 1 h, and then 1 h indefinitely. Checkable from =next_attempt_at= in =hooks.json= without waiting out the whole curve.
9. *Quarantine never becomes disable on failure evidence.* Leave a hook failing attributably for at least 200 consecutive paced dispatches. It is still =quarantined=. No amount of failure, and no duration of failure, moves it to =disabled= without an operator.
   - *9a — Expiry is the stated exception.* A =quarantined= hook that also carries a TTL *does* become =disabled= at expiry, with =disabled_reason = "expired"=. This is intended and the invariant is scoped to failure evidence; a criterion asserting the opposite would be testing the wrong sentence.
   - *9b — One badly-timed sample does not disable a hook under repair.* Drive a hook to =quarantined= at the 1 h ceiling. Delete its =cwd=, wait for exactly one scheduled attempt, then restore the directory before the next. Run =ever hook gc=: the hook is *not* reclaimable, because =cwd_missing_since= was cleared by the next successful =stat=. *This is the case that would have killed hook #186 during its three-day repair window under revision 1.*
10. *Self-healing.* Repair the failing command so it exits 0. Without any operator command, the hook fires at its next scheduled attempt, and afterwards =hook list= shows =armed= with =consecutive_failures= 0.
11. *Observable difference.* With one hook =quarantined= and one =disabled=, both with working commands, publish matching events and wait past the quarantined hook's next-attempt time. The quarantined hook fires; the disabled hook does not. This is the whole distinction.
12. *Signal deaths count.* A hook whose command kills itself with =SIGKILL=, driven by 5 paced events, reaches =quarantined=, and =last_exit_status= is =-9=. *This regresses today: at =142d5e66= such a dispatch produces no log line at all, because =(status >> 8) & 0xFF= is 0 for a signal death.*
   - *12a — The daemon's own kills do not.* A hook whose command sleeps 310 s is killed by =checkTimeouts= at 300 s. After 5 such dispatches it is still =armed=, =consecutive_failures= is 0, =last_error= is ="timeout"=, and =hook list= shows a =TIMEOUTS= tally of 5. *Without this exclusion the same fixture quarantines, which would take any hook that legitimately runs over five minutes off the air for an hour on a timeout nobody opted into.*
   - *12b — Shutdown does not quarantine the store.* Start three long-running hooks, stop the store while they run, start it again. All three are =armed= with =consecutive_failures= 0.
13. *Backpressure is not failure.* Saturate =MAX_CONCURRENT_HOOKS= with long-running hooks and let another hook's events be deferred. That hook's =consecutive_failures= stays 0.
14. *A quarantined hook does not scan.* On a store with a large log and *no other hooks registered*, quarantine one prefix hook at a 1 h next-attempt and compare the store's read-syscall rate against its idle baseline with no hooks at all. The two must not differ. (=/proc/$PID/io= =syscr= is process-wide and the store also reads for TCP/HTTP work, so the criterion is "no increase over an idle baseline", not "zero".) Measurable without =strace=, as in the incident's notes:

#+begin_src bash
a=$(awk '/^syscr/{print $2}' /proc/$PID/io); sleep 3
b=$(awk '/^syscr/{print $2}' /proc/$PID/io); echo $(( (b-a)/3 ))
#+end_src

** The =cwd= guard, and the limits of automatic action

15. *The guard does not fork, and does not disable.* Register a hook from a directory, delete the directory, publish 5 paced matching events. No child process is spawned for any of the 5 (nothing new appears under =data/hooks/=), =last_error= is ="cwd-missing"=, =consecutive_failures= is 5, and the hook is *=quarantined=, not =disabled=*. *This is the criterion that pins the daemon/operator split: an implementation that disables here has re-introduced the withdrawn design.*
   - *15a — The guard is per-event, not per-tick.* With the same hook, publish nothing at all for 10 poll cycles after deleting the directory. =consecutive_failures= stays at its previous value — a hook with no matching events accumulates no failures, however long its =cwd= has been gone.
   - *15b — The guard bounds cursor loss.* With the same hook, note the cursor, publish 3 paced events, and confirm the cursor advanced by exactly 3 event-positions — not to the log head.
16. *No unattended disable of any kind, on any evidence.* Take the strongest possible case: a hook whose command is an absolute path to a deleted script, whose =cwd= is also deleted, driven by 200 paced events. It ends =quarantined= at the 1 h ceiling. *No store-side mechanism moves it to =disabled=.* Only =gc --yes= does. Run the whole of the rest of this section against a store on which =gc= has never been invoked and nothing is ever disabled except by TTL.
17. *No static-only disable.* Register hooks with commands =echo hi=, =sh -c 'exit 0'= and =true= (any command resolved through =PATH= and present on any POSIX host — do not use a fixture that needs the ACE stack installed). None is ever disabled, none is quarantined while it exits 0, and none appears in =gc='s reclaimable section. *A rule that stats the first token would flag 9 of the 16 hooks on the reference census below.*
18. *Only ENOENT.* A hook whose command path exists but is not executable exits 126; it is *never quarantined* (126 is a generic non-zero exit and not attributable) and =gc= does not list it as reclaimable. A hook whose =cwd= is unreadable due to permissions on a parent directory (=EACCES= from =stat=) is forked normally — the guard does not trigger — and =gc= does not list it.
19. *Expiry disables, does not delete.* =ever hook add --ttl 30s <pattern> -- <cmd>=; after 30 s the hook is =disabled= with reason =expired=, still present in =hook list=, and the store logged the expiry *exactly once* (not once per 500 ms tick).
   - *19a — =--ttl= is in the right unit.* =ever hook add --ttl 1h= produces an =expires_at= about 3,600,000 ms in the future, not 3,600. Stated as its own criterion because =timers.parseDuration= returns *seconds* and =expires_at= is *epoch milliseconds*, and the 1000× error presents as "the TTL criterion is flaky" rather than as a unit bug.
20. *No default TTL.* A hook added without =--ttl= has =expires_at: null= in =hooks.json= and is never expired.
21. *Renew.* =ever hook renew <id> --ttl 1h= on a hook with a TTL moves =expires_at= forward by about an hour. =ever hook renew <id>= on a hook with no =expires_at= fails with a non-zero exit and changes nothing.
22. *Lag is never an input.* A hook whose cursor is millions of events behind the head, whose command and =cwd= both exist and which has never failed, is =armed=, is not listed as reclaimable by =gc=, and is not flagged.

** =hook gc=

23. *Dry run is the default and is inert.* On any store, run =ever hook gc= twice. Both invocations print byte-identical output, exit 0, and leave =hooks.json='s mtime and contents unchanged.
24. *Evidence is printed, and it is pasteable.* Every line in the RECLAIMABLE section names the rule (=cwd-missing= / =command-missing=) and the concrete evidence — the path that returned =ENOENT=, the recorded =last_exit_status=, the failure count. Every path is printed *exactly as stored*, with no =~= abbreviation, so a reviewer can paste it straight into =stat= and get the same answer.
   - *24a — The evidence is the store's, not the client's.* Run =ever hook gc= from a machine, or a directory namespace, where the hooks' =cwd= and command paths *do not exist*, against a store where they do: on a second host via =-a=, or simply after renaming the paths out from under a client that is not the store. The report is *empty*. An implementation that stats client-side reports every hook on the store as reclaimable, and this is the only criterion that catches it.
25. *The 15-minute floor is wall clock, not a failure count.* A hook whose =cwd= was deleted 5 paced events ago is =quarantined= but *not* reclaimable, because =now − cwd_missing_since < 15 min=. Wait out the window with the directory still absent and it becomes reclaimable. *A hook whose directory is deleted and recreated inside the window ends =armed=, with =cwd_missing_since= back to =null=, and never appears in the reclaimable section* — the =rm -rf && mkdir= rig-rebuild case.
   - *25a — R2 needs the observed 127, not just the missing path.* Register a hook whose command is an absolute path to a script and delete the script *before any event matches*. =gc= lists it under FLAGGED FOR REVIEW, never RECLAIMABLE, because =last_exit_status= is null. Now drive it to K paced failures and past the 15-minute floor: it moves to RECLAIMABLE. Separately, a hook whose script *exists* and exits 127 deliberately never appears in either section, at any failure count.
   - *25b — A never-dispatched hook is flagged, never reclaimable.* Register a hook on a pattern nothing will ever match, delete its directory, and let it sit. It never fails and never quarantines (criterion 15a). =gc= lists it under *FLAGGED FOR REVIEW* with its registration age and "never succeeded", and *=gc --yes= does not touch it*. =gc --include-flagged --yes=, or =ever hook disable <id>=, reclaims it. *This is how the incident's =#17/#19/#157/#158= class is reached — visibly, and only with a second explicit act.*
   - *25d — W1c has an age floor.* Repeat 25b with a hook registered less than 24 hours ago: it is *not* listed under W1c at all, and =gc --include-flagged --yes= does not disable it. This is the branch with no second observer, so the age floor is the only thing standing between a rig that registers a hook before creating its directory and an operator sweeping the flagged list.
   - *25c — Two observers, not one.* =gc= must re-=stat= at the moment it runs, not trust =cwd_missing_since=. With a hook whose =cwd_missing_since= is two hours old but whose directory now exists, =gc= reports it in neither section.
26. *Quarantined is flagged, not reclaimed.* With a hook at 20+ attributable consecutive failures whose command and =cwd= both exist: =gc= lists it under FLAGGED FOR REVIEW; =gc --yes= does not touch it; =gc --include-flagged --yes= disables it.
   - *26a — Working hooks are never candidates.* On the reference census below — 16 hooks, none with a missing =cwd=, none with a missing absolute command path, none with a TTL — =ever hook gc= reports *zero* entries in the RECLAIMABLE section.
   - *26b — The flagged line answers the operator's question.* Every FLAGGED line carries =last_success_at= as an absolute timestamp *and* a relative age, or "never succeeded" plus the registration age. Two hooks identical in every other field but with last successes ninety minutes and four months ago must render differently.
27. *=--purge= needs typed-out ids.* =ever hook gc --purge --yes= with no ids refuses and changes nothing; there is no =--all= and no state selector. =--purge <id> --yes= naming an =armed= or =quarantined= hook refuses *the whole invocation* and changes nothing, even if other named ids would qualify.
   - *27a — =--purge= needs the hook to have been disabled for an hour.* =--purge <id> --yes= on a hook disabled 5 minutes ago refuses, prints =disabled_at= and the remaining wait, and exits non-zero. The same command an hour later succeeds.
   - *27b — =--purge= dry-runs.* =ever hook gc --purge <id>= without =--yes= prints the hook's id, name, pattern, command as stored, =disabled_reason=, =disabled_at= and its age, says =1 would be removed, 0 removed=, and leaves =hooks.json= byte-identical.
28. *=--yes= only disables.* After =ever hook gc --yes= on a store with reclaimable candidates, the hook count in =hook list= is unchanged; only states changed. The =disabled_reason= values begin with =gc-=, distinguishing them from =expired= and =operator=.

** Name addressing

- *28a — Duplicate names are refused at registration.* =ever hook add t --name guard -- /bin/echo A= then =ever hook add t --name guard -- /bin/echo B= — the second fails with a non-zero exit, names the existing hook's id, and registers nothing. *This regresses today: at =142d5e66= both succeed silently, which is measured in [[#names][Name addressing]] and is what =TimerTable.add= already refuses for timers.*
- *28b — Ambiguity is refused at resolution.* Construct a store that already contains two hooks named =guard= (write =hooks.json= directly, since 28a now prevents creating one). Each of =ever hook enable guard=, =hook disable guard=, =hook renew guard= and =hook rm guard= exits non-zero, prints *both* candidate ids, and changes nothing. *This regresses today: =hook rm guard= removes an unpredictable one and reports success.*
- *28c — The unpredictability is real, so the criterion is not academic.* On that same store, =hook rm <first id>= then =hook list=: the array order changes, because =removeByName= uses =swapRemove=. A criterion that assumes "first match" means "lowest id" or "oldest" is wrong.
- *28d — Destructive verbs take ids only.* =ever hook gc --purge guard --yes= is rejected as a malformed argument — =--purge= accepts ids and nothing else — regardless of whether =guard= is ambiguous.
- *28e — Unnamed hooks are addressable by id.* 9 of the 16 live hooks have =name: null=. Every new verb works on them by id, and the name form reports "not found" rather than matching a null name.
- *28f — Resolution is server-side.* Run =ever hook enable somename= against a store and capture the wire traffic (or instrument the client). *Exactly one* request is sent, carrying the name; there is no =list_hooks= call and no second connection. An implementation that lists, scans and reconnects fails this criterion even if it detects ambiguity correctly, because the check and the act are then in different critical sections.
   - Hand-craft a =hook_enable= body with *both* =id= and =name= set, and another with *neither*. Both are rejected with =ErrorCode.bad_request= (400) and change nothing. "Exactly one set" is an invariant, and an invariant with no stated response to its violation is the shape that produced B1.
- *28g — The dead helpers do not survive as they are.* =HookTable.removeByName= and =findIdByName= have no call sites at =142d5e66=, not even in tests, and *both take the table lock themselves*. After the change, either both are gone, or both have been refactored into non-locking =*Locked= helpers exercised by the tests for 28b. *"Wired up unchanged" is not an available outcome* — see 28h for why it cannot be.
- *28i — Lock order survives concurrency.* Start the store with the test-only widening described below.   *The widening.* =ever start= takes a hidden =--lock-probe-delay-ms=, default =0=, which inserts a sleep of that length *after acquiring the first of the two locks* on each of the two paths — =handleRegisterHook= after =lockForHookRegistration()=, and the =hook enable= entry point after taking the =HookTable= lock. At =50= the two orders are forced to overlap and *one* interleaving suffices: against a correct build both commands return, against the mutated build both spin and the cap kills them.

  Why this rather than deriving an iteration count from "the mutation fails reliably": the count would have to be calibrated by measurement, on *this* host, which runs many concurrent agent sessions — the same reason the fleet's benchmarking rule requires a minimum over twenty interleaved runs rather than a single pass. A count calibrated on a quiet machine is wrong on a loaded one and vice versa, and a must-run mutation check that fails probabilistically is worse than none, because the first false pass teaches everyone to re-run it. The cost of the widening is honest and worth naming: *it puts a test affordance in a production code path.* At =0= it is one compare-and-branch, and the mitigation is the next clause.

  - *28i-bis — the affordance is not what makes it pass.* Run 28i again with the flag absent. Both commands still complete. A build that passes only with the widening enabled has the ordering wrong somewhere the widening happens to serialise.
- *28j — =--from tail= does not replay, from either eligible state.* Publish 50 matching events, then =ever hook enable <id> --from tail=. *Zero* new files appear under =data/hooks/= for the historical events, and the next event published afterwards does fire. *Run it twice: once with the hook =disabled= beforehand, and once with it =quarantined= and its =next_attempt_at= already in the past* — that is, due for dispatch on the very next tick. Both must behave identically.

  The quarantined run is the one that matters and the disabled run cannot substitute for it: tick step 1 skips a =disabled= hook before the fetch, so a disabled hook is quiescent whatever the implementation does between resolving and arming. A quarantined hook is not, so this is the only criterion that distinguishes an implementation which *establishes* quiescence in step 1 from one which merely inherits it from the caller's starting state. An implementation that arms before writing the tip fails here and passes criterion 30 on a quiet store.
- *28h — Name resolution does not hang the store.* From a store with several hooks, run each of =hook enable <name>=, =hook disable <name>=, =hook renew <name>= *under a wall-clock cap* — spawn, wait with a timeout of a few seconds, kill on expiry. Each must return. Then, still within the cap, confirm the hook daemon is alive by publishing a matching event for an unrelated hook and seeing it fire. *This criterion must bound its own probe and fail on timeout: the defect it catches is a spin on a non-reentrant mutex, which produces no panic, no error and no log line — an unbounded test would hang and produce no evidence.* An implementation that resolves by calling a self-locking helper while holding the lock fails this and wedges the whole hook subsystem, because the daemon's own =snapshot= takes the same lock.

** Reversibility

29. *Enable restores the registration and the cursor.* Disable an *exact-topic* hook. Publish 3 matching events. Run =ever hook enable <id>=. It prints =3 events pending= before acting, and the hook then fires for all 3, oldest first, producing 3 new files under =data/hooks/=. The hook must be exact-topic: for a prefix/wildcard hook the printed figure is =nextOffset() − cursor=, an upper bound over *all* topics, and it equals 3 only on an otherwise idle store.
   - *29a — The prefix bound is labelled as a bound.* Repeat with a prefix hook on a store carrying unrelated traffic. The output says =up to N events pending= and N exceeds the number the hook actually fires for. A criterion asserting equality here would be wrong.
30. *=--from tail= opts out.* Repeat (29) with =ever hook enable <id> --from tail=. The pending count is still printed, no historical event fires, and the next event published *after* the command does fire.
31. *Enable clears the failure counters.* After (29), =hook list= shows the hook =armed= with =consecutive_failures= 0, no =next_attempt_at= and no =disabled_reason=.

   - *31b — Enable refuses a stale TTL.* Register with =--ttl 30s=, =hook disable= it before expiry, wait past the 30 s, then =hook enable=. The command *refuses*, prints the stored =expires_at=, and requires =--ttl <dur>= or =--clear-ttl=. Neither of those two forms refuses.

** Concurrency

Failure counters are written on the daemon thread at reap and read on server threads by =hook list= and =gc=. Per the fleet rule, the counting tests (unit 8, criteria 7a/7b/13) must also run under =zig build test -Doptimize=ReleaseFast=; a torn read of =consecutive_failures= is exactly the class of defect that only shows up there.

The locking criteria (28h and 28i) belong in the same set, for a different reason: the defects they catch are spins on non-reentrant mutexes, and whether a given build reaches one can depend on inlining and on how the optimiser arranges the =tryLock= loop. Neither may rely on a debug-build assertion, because =std.atomic.Mutex.tryLock= has no owner check and asserts nothing on re-entry.

*Both live at the integration level, not the unit level, and that is a deliberate consequence of the failure mode rather than a preference.* A test for a spin has to be able to give up, and only a test that owns a child process can. Inside the test binary there is nowhere to put the bound: the runner has no per-test timeout, =build.zig= adds none, and =std.Thread.join= has no deadline — so a unit test for this class cannot fail, it can only hang, and in hanging it silences every other test in the binary. Whatever else is done here, *no test for a lock defect may be written in a form that cannot time out.*

** Bounded probes

Any test that waits for a hook to fire must bound its own wait and fail on timeout rather than hang. Any test that reads =hooks.json= while the store is running must retry until it parses — the file is written by =open(TRUNC)= then =rename=, and a read racing the write can legitimately see an empty file, which parses as "no hooks" and is indistinguishable from the failure under test.

* Open questions

1. *Four constants are asserted, not derived*, and they are listed together so a reviewer can attack them as a group rather than hunting: =K = 5=; the 60 s floor on the K streak; the 15-minute floor on =gc='s R1/R2; and the one-hour minimum time-in-=disabled= before =--purge=. 3. *Should =hook new='s scaffold emit a trailing =exit 0=?* This document deliberately does not require one: the whole point of [[#what-counts][Why a non-zero exit is not evidence]] is that Ever must not depend on a shell convention it cannot enforce. But a scaffold that emits it anyway would make the intent visible to the person writing their first filter hook, at no cost. That belongs to =hook-ergonomics/= and is noted, not specified.
