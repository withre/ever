#+title: Multi-Process Access to a Single Store
#+state: draft
#+FILETAGS: :store:core:

* Summary
Allow two or three processes to share one data directory safely — a shell running an embedded Ever, plus a UI or terminal attached to the same store. Three separable changes: refresh the in-memory index from disk so readers stop going stale, span the append critical section across processes so writers stop destroying each other, and make the library's concurrency guarantee explicit rather than accidental.

* Motivation

** Answering the question directly: why is the index not written back?

Because it is not state. =TopicIndex= is =\{ offsets: ArrayList(u64), non_marker_count: u64 \}= per topic — a map from topic name to the global offsets belonging to it, plus a count. Every byte of it is reconstructible from the log, and the log is already the durable, shared, on-disk source of truth. The data directory contains only =*.log=, =ever.lock=, =hooks.json= and =timers.json=; there is no index file because the index is a cache.

*Persisting it would not fix the problem it appears to fix.* The stale-reader defect is not that a process loses its index — it is that a running process never *notices* another process's appends. Writing the index to disk leaves that untouched: process A still holds its own in-memory copy and still never re-reads. It would convert one coherence problem into two, because the log and the index would then both have to agree across processes, and the index is the derivable one.

So the direction here is the opposite: keep the index derived, and make it *catch up* cheaply.

** What is actually broken today

*** Readers go stale, silently and permanently
=TopicManager.rebuildIndex= runs once at init. Appends update the index in memory. A second process's appends are therefore invisible to the first *forever*. Nothing crashes and nothing warns — a reader simply returns a truthful-looking answer computed from a snapshot that stopped advancing. That silence is what makes it worse than a crash.

*** Writers destroy each other
=Log.append= reads =self.next_offset= from process-local memory, encodes, and writes positionally at =seg.size= — all under a =std.atomic.Mutex=, which is in-process only. Two writers assign identical offsets and write at identical file positions; the later write destroys the earlier. This is not an edge case, it is what two writers do on their first concurrent append.

*** The only thing preventing both is a lock in the wrong layer
=flock(LOCK_EX|LOCK_NB)= is taken in =main.zig= =startServer=. There is no locking anywhere in =src/store/= or =src/net/=. So the guard sits *above* the library boundary: a consumer that imports Ever and writes gets no protection at all — not loosened, absent. Embedding is already the unsafe case, before any change contemplated here.

This reframes the work. It is not "relax a guard so multiple processes can share". It is "put a guard where none exists, and let the two entrypoints choose different ones".

** Scale target
Two or three processes: one shell running an embedded Ever, another UI or terminal attached to the same directory. Explicitly *not* N processes.

** Goals
- A reader in one process observes another process's appends within a bounded, cheap check
- Two or three concurrent writers cannot assign the same offset or overwrite each other's records
- The library and CLI entrypoints may choose different concurrency guarantees, deliberately
- Each of the three changes can land independently and be useful alone

** Non-Goals
- Distributed consensus, leader election, or N-writer scaling. The 2–3 process target is what makes the cheap mechanisms below sufficient; none of them generalise, and that is deliberate.
- Persisting the index to disk. Argued against in the Motivation as the multi-process mechanism. It remains legitimate as a *startup-time* optimisation — =rebuildIndex= is a full scan of every event, and the live store is already past 119,000 — but that is a performance feature to be argued on its own terms, in its own document, and it trades an append-only recoverable structure for a mutable corruptible one.
- Transactions across multiple publishes. Named as a longer-term direction, out of scope here.
- Changing the offset model (global monotonic u64) or the on-disk record format.
- Removing =sync_on_append=, or the swallowed-fsync defect it interacts with. Tracked separately.

* Proposal

Three pieces, in dependency order.

** Piece 1 — Incremental index refresh (fixes stale readers)

The catch-up loop already exists. =rebuildIndex= walks =offset = 0= to =log.nextOffset()=, reading each event and folding it into the index. *The same loop started at the last-indexed offset instead of zero is an incremental tail scan.* Nothing new needs inventing; it is currently only ever invoked with a start of zero.

Two details decide whether it is correct:

*** The trigger must come from disk, not memory
=Log.nextOffset()= returns =self.next_offset=, which is in-memory and set at init. Process A's =nextOffset()= is therefore exactly as stale as its index — using it to detect growth would compare a stale value against itself and always conclude "nothing new". Growth must be detected by =stat=-ing the segment files. Nothing re-stats after init today.

*** New segment files must be discovered, not just growth in known ones
If the other process rolls over =max_segment_size=, it creates a *new* segment file that this process has never opened. =Log.init= already contains the routine for this: scan the directory for =*.log=, sort, open, =stat= for size, build the position index. A refresh is that routine re-run against the current directory, plus a re-=stat= of segments already open.

*** The refresh has two layers, and both are required

There are two independent derived structures, each with its own rebuild loop, and a refresh that updates only one is silently wrong:

| Layer          | Structure                                   | Existing loop                                    | Resume from                |
|----------------+---------------------------------------------+--------------------------------------------------+----------------------------|
| =Log=          | per-segment byte positions, =next_offset=   | =buildPositionIndex= — =while (pos < seg.size)=   | last indexed byte position |
| =TopicManager= | topic → offsets, =non_marker_count=, deletions | =rebuildIndex= — walks =0..log.nextOffset()=      | last folded global offset  |
| =HookTable= / =TimerTable= | registrations and cursors       | =load()= — reads the whole json                  | (re-read; not a walk)      |

The first two are already resumable walks that happen to start at zero; neither needs new traversal logic.

The third is a different shape and is easy to overlook because it is not part of "the index" — but it has the identical defect. =HookTable.load()= is called once from =init= and never again; =TimerTable= likewise. So *hook and timer registrations are as stale as the event index.* A hook registered by one process is invisible to an already-running daemon in another, and the =cursor= each side believes a hook holds diverges immediately. Any =shared= mode that does not refresh this layer supports reading each other's events but not each other's hooks.

The consequence of missing the second layer is concrete: *tombstone detection lives in the =TopicManager= loop.* A =Log=-only refresh would pick up another process's new records but never notice that one of them deleted a topic, so this process would keep serving a topic the other has destroyed.

*** The two layers must refresh atomically with respect to readers
If =Log= advances =next_offset= before =TopicManager= has folded those events, a reader can observe a tip that the topic index does not yet cover — a fetch for an offset the index has no entry for. Both layers must advance under the same lock acquisition, so no reader observes the intermediate state.

*** One choke point, not nine
There are nine public reader entry points on =TopicManager=: =tipForPattern=, =tipForPatternLocked=, =hasTopic=, =hasTopicLocked=, =listTopics=, =fetch=, =fetchAfterOffset=, =fetchPatternByOffset=, =fetchPattern=. Sprinkling a freshness check across all nine guarantees that the tenth, added later, forgets it.

Put the check in one place — at lock acquisition — so every reader inherits it by construction rather than by discipline. This mirrors the shape the hook table already uses (one locked entry point per verb).

*** Cost
When idle: one =stat= per segment per read. When behind: a scan proportional to the number of *new* events, not to the log. Both acceptable at this scale, and the refresh can be rate-limited (at most once per N milliseconds) if the =stat= turns out to matter.

** Piece 2 — Cross-process append lock (fixes write collisions)

The critical section is precisely: read =next_offset= → encode → write at =seg.size= → advance =next_offset= and =seg.size=. Today a process-local mutex spans it. Widen the same section to an OS-level lock so it spans processes.

*** Why this is affordable
The append path already pays an fsync per publish (=sync_on_append= defaults true), measured at roughly 42 ms and independent of payload size. Acquiring and releasing a file lock is microseconds. The lock is *noise* against a cost the design already accepts — which is what makes a cross-process critical section viable here without consensus, and why the 2–3 process target does not need anything cleverer.

*** It depends on Piece 1
After acquiring the cross-process lock, a writer's in-memory =next_offset= and =seg.size= may be stale, because another process appended while it was waiting. It must refresh from disk *inside* the lock before assigning an offset. That is Piece 1's machinery, so Piece 1 lands first. Piece 2 without Piece 1 would take a lock and then write at a stale position — the same corruption, now with a lock held.

*** Lock file
Use a dedicated lock file rather than reusing =ever.lock=, whose current meaning is "a server owns this directory". Overloading it would conflate "a server is running" with "an append is in flight" and break the existing =status= probe.

** Piece 3 — Explicit library entrypoint contract

Today the difference between the CLI and the library is accidental: the CLI happens to take an flock in =startServer=, and the library happens to take nothing. Make it a choice.

Expose the concurrency mode in =TopicManager= config, so an embedded consumer opts in to cross-process safety and a single-process CLI can skip the cost:

#+begin_src zig
pub const Concurrency = enum {
    /// One process owns this directory. No cross-process locking.
    single_process,
    /// Several processes may share it. Refresh-on-read and a
    /// cross-process append lock.
    shared,
};
#+end_src

The CLI's =store start= keeps its =flock= and selects =single_process=, preserving today's behaviour and cost exactly. An embedded consumer selects =shared=. What each guarantees is documented, rather than being an emergent property of which entrypoint you happened to use.

* Design Details

** Interaction with the existing =ever.lock=
=ever.lock= currently means "a server process owns this directory", and =status= probes it to report whether a server is running. If several processes may legitimately share a directory, that flock can no longer be exclusive in =shared= mode, and the =status= semantics need restating — probably "how many attached" rather than "held / not held". This is the part most likely to surface follow-on work.

** Interaction with hooks and timers

=HookTable= and =TimerTable= persist to =hooks.json= and =timers.json= with their own in-memory state, and have the same staleness property as the index. Two processes both running the hook daemon would double-fire every hook, so a =shared= store must assume a single hook/timer daemon.

*** The case that will actually happen: hooks on an embedded store

The double-fire is the obvious hazard and it is not the likely one. An embedded consumer has good reason *not* to run the hook daemon at all — =HookDaemon= forks and execves =/bin/sh=, which a TUI process holding the terminal in raw mode should not do. So the realistic topology is: one process embeds the store and writes events but runs no hooks, and a user who wants hooks reaches for the obvious remedy — =ever start --data-dir <the embedded store's directory>=.

*Today that silently does nothing, and reports success at every step.*

1. =ever start= takes =flock(LOCK_EX|LOCK_NB)= and *succeeds*, because the embedded store took no lock — the flock lives in =startServer=, above the library. There is no contention and therefore no warning.
2. The daemon builds its index once at init and never refreshes.
3. =HookDaemon= discovers events through =self.topic_manager.fetchPatternByOffset= / =fetch= — the in-memory index, not the log.
4. The embedding process appends. The daemon's index never advances, so those events do not exist as far as it is concerned.
5. No hook ever fires. =ever hook list= shows the hooks, =ever hook ps= shows no failures, the server logs look healthy.

The user gets a clean start, a correct-looking hook registry, and a hook system that never fires — with no error at any stage. This is the same shape as the other silent failures in this project: a success receipt for something that did not happen.

It is also the strongest argument for Piece 1. Incremental refresh is not a nicety for readers; it is the difference between hooks working and hooks silently not working, in the topology an embedded consumer will actually adopt.

*** What the contract must therefore say
Until Piece 1 lands, =ever start= against a directory that another process is writing is *not supported* and must not be presented as the way to add hooks to an embedded store. Once Piece 1 lands it becomes the supported answer, provided exactly one process runs the hook and timer daemons. Stating both halves matters, because the unsupported version is the one a user reaches for first.

** What this deliberately does not attempt
Fan-in with two or three writers is served by Piece 2. Genuine multi-writer scaling, ordering guarantees across processes beyond "offsets are unique and monotonic", and transactions are all out of scope. If the process count grows past a handful, the honest answer is that this design stops being appropriate rather than being tuned.

* Open Questions
- Refresh trigger granularity: per read, or rate-limited? Measure the =stat= cost against the 100 ms poll the subscription path already performs before optimising.
- Should =shared= mode also cover =HookTable= / =TimerTable=, or is single-daemon a permanent restriction?
- Does =fetchPattern= over a refreshed index need any ordering guarantee it does not have today?
